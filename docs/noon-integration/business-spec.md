# Noon Integration Specification for ERPNext

Nov 1, 2026 · Mohamed Amir (business owner). Reference for any rule not restated here: `docs/bosta-integration/business-spec.md`.

## 1. Objective and Scope

Merchants handle Noon FBPI orders only through the Sales Order and the Delivery Note, and ERPNext never holds a state that Noon does not hold.

- **In scope:** marking items out of stock, creating and cancelling Noon shipments from the Delivery Note, AWB handling, shipment status tracking, and invoice upload, for Noon FBPI warehouses.
- **Warehouse type:** Noon only exposes order APIs and webhooks for FBPI warehouses. FBN and plain FBP warehouses are blocked at setup with a clear message, so they do not fail later in a confusing way.
- **Carrier rule:** Noon orders always ship through Noon.
- **No separate Shipment document:** the Delivery Note holds all shipping data, as in the Bosta specification.
- **Out of scope:** returns and RTO beyond the existing Sales Return behavior, COD and settlement reconciliation, other carriers, and any change to how Noon-originated order cancellation works today.

## 2. Agreed Principles

ERPNext and Noon must always show the same state, so every change waits for Noon's confirmation and every retry starts by asking Noon.

1. A Delivery Note cannot be Submitted unless Noon has confirmed that the shipment exists.
2. A Delivery Note cannot be Cancelled unless Noon has confirmed that the shipment is cancelled.
3. An item leaves the Sales Order only after Noon confirms it is out of stock.
4. Ask Noon first, then act: before any create or cancel, the system asks Noon for the shipment's current state. The Retry and Check Noon actions follow this same rule, so a second shipment is never created by accident.
5. Noon is the source of truth for shipping status. Employees cannot edit it.
6. Anything received from Noon (AWB, shipment data, log entries) is committed to the database on its own before any error is raised, so a rolled-back save cannot erase it.
7. An unknown result never triggers a blind second create or cancel.
8. Changes made outside ERPNext, for example in Seller Lab, cannot be prevented. They are detected by webhook, Refresh Shipment, and the nightly reconciliation, and reported through Notifications and Needs Attention.
9. Use what ERPNext already provides: partial Delivery Notes, Update Items, Close, native attachments, and the application's existing logs. No new document types unless a section below says so.

## 3. Sales Order: Mark as Out of Stock

The employee marks an item out of stock from the Sales Order, and the item leaves the order only after Noon confirms.

1. A **Mark as Out of Stock** action is available on an item row of the Sales Order.
2. The action is blocked if the item is in a Draft Delivery Note. The message names the Delivery Note and asks the employee to remove the item from it first. It is also blocked if the item is already in a submitted Delivery Note, because Noon only accepts it before a shipment exists.
3. A confirmation dialog states that the action is final at Noon: the item cannot be fulfilled later even if it is restocked, and Noon may apply cancellation charges.
4. The request goes to Noon with a loading indicator (`Sending to Noon...`).
5. **Success:** the item is removed from the order through the native Update Items action, any stock reservation for it is released, and a small success message is shown.
6. **Confirmed failure:** an error dialog shows Noon's message with a Retry button. The item stays in the order.
7. **Unknown result (timeout or dropped connection):** the dialog says the result is unknown. Retry first asks Noon whether the item is already cancelled. If it is, the flow continues at step 5 without sending the request again.

If Noon confirms but the local Update Items step fails, the item is flagged in Needs Attention and only the local step is retried. The request to Noon is never repeated.

## 4. Delivery Note Interface

The Shipping section of a Noon Delivery Note holds the AWB, the Noon data, and the actions, and nothing in it is calculated from a Shipping Rule: a Noon note clears the Shipping Rule together with the tax row that rule added, and hides the field. Noon returns no shipment id, so there is no shipment reference field.

| Field | Purpose | Editable |
| --- | --- | --- |
| Shipping Provider | Noon (default for Noon orders) | No |
| Noon Shipment Number | Equals the Delivery Note name and is sent to Noon as the unique shipment number | Read only |
| AWB Number | Typed by the employee, or generated by Noon | Until generated or until the shipment is created |
| Generate AWB through Noon | Checkbox placed directly under AWB Number | Until the first generation |
| Shipping Status | Derived from Noon's item statuses: Acknowledged, Shipped, Out of Stock, Cancelled or Mixed | Read only |
| Last Sync At | Time of the last update from Noon | Read only |
| Last Integration Error | Short text of the latest error | Read only |

**AWB and checkbox rules**

- Checkbox not ticked: the employee types the AWB of their own courier. The courier sent with a typed AWB is always `noon`.
- Checkbox ticked: the AWB field becomes read only and stays empty until Noon generates it during Submit.
- Once an AWB has been generated or the shipment exists, both the checkbox and the field are locked. This stops an employee from untick-and-retype, which would leave a generated AWB unused.
- A typed AWB must not already exist on another Delivery Note that is not cancelled.

**Items**

- The employee may remove rows or reduce quantities so the shipment holds only part of the order. This is the native partial-fulfilment behavior, and the remaining items go into a later Delivery Note.
- The system keeps total delivered quantity within the Sales Order quantity.

**Actions on the Delivery Note:** Refresh Shipment, Check Noon (visible only when a result is unknown), and Upload Shipment Invoice.

## 5. Create the Noon Shipment on Submit

Submit starts a background job that sends the shipment to Noon. The Delivery Note becomes Submitted only if Noon confirms: once the shipment is Created the job submits the note itself, as the user who pressed Submit (decided 2026-11-02). The text below is the original step design; the commit rules and duplicate prevention still hold.

1. **Validate:** Noon is the provider, the warehouse is FBPI, an AWB is present or the checkbox is ticked, and the shipment has at least one item.
2. **Lock** the Delivery Note so a second click or a second user cannot start a parallel attempt. The screen shows `Sending to Noon...`.
3. **Ask Noon first:** get the shipment by warehouse and shipment number. If it exists, skip to step 6.
4. **AWB:** if the checkbox is ticked and no AWB is stored yet, request one from Noon and commit it to the Delivery Note at once. A retry reuses this AWB and never requests another.
5. **Create** the shipment with the shipment number, the AWB, and the items of this Delivery Note, then wait for Noon's answer.
6. **Confirmed success:** commit the Noon data on its own (AWB, status, log entry), then let the Submit finish.
7. **Confirmed failure:** raise an error. The Delivery Note stays Draft and the error dialog offers Retry.

A shipment that already exists at Noon skips straight to committing its data, so a retry never creates a second one.

Why the commit in step 6 matters: an error raised in `before_submit` rolls back the whole save, which would erase the AWB and shipment data that Noon already holds. This is the standard Frappe behavior and must be confirmed on the development bench.

If Noon succeeded but the job's local submit fails afterwards (negative stock, credit limit, authorization), the Delivery Note stays a Created Draft with the Noon data kept and the reason in Last Integration Error. Needs Attention shows it as a Carrier Exception ("shipment created, Delivery Note not submitted"), and so does any Created draft older than 15 minutes (built). A person submits it natively (Created is all `before_submit` needs), so no second shipment is created.

**Shipping label:** Noon documents no label endpoint, so no label is fetched or stored.

## 6. Errors, Unknown Results and Duplicate Prevention

Every call to Noon ends in one of three results, and only a confirmed result lets the document move forward.

| Result | Meaning | What the employee sees | System action |
| --- | --- | --- | --- |
| Confirmed success | Noon accepted the request | Small success message | Save data, continue Submit or Cancel |
| Confirmed failure | Noon rejected the request | Error dialog with Noon's message and Retry | Document stays as it was |
| Unknown | Timeout, dropped connection, or no conclusive answer | Dialog explaining the result is unknown, with Check Noon | Ask Noon for the current state before anything else is sent |

- **Check Noon** gets the shipment from Noon. If the shipment exists, the flow continues as a success. If Noon says it does not exist, Retry becomes available. If the answer is still inconclusive, the dialog says so and no new create is sent.
- **Duplicate prevention** comes from three things: the shipment number is stable (the Delivery Note name), the system always asks Noon before creating, and the Delivery Note is locked while an attempt is running.
- A Delivery Note that is amended after cancellation gets a new name, so its shipment number is new as well.
- Errors shown to employees are written in plain words. API keys, tokens and signed requests never appear in dialogs or logs.

## 7. Status Updates and Reconciliation

Shipping Status follows Noon through three channels, and the nightly reconciliation is the safety net that keeps both sides identical.

**Webhooks**

- Verify the sender with whatever authentication Noon supports, and record each event before applying it.
- Noon delivers events at least once, so a repeated event is ignored.
- An older event never moves the status backwards. Use Noon's event time if it is provided, otherwise a fixed status order.
- An event for a shipment whose Delivery Note is not Submitted yet is ignored. The next Refresh or reconciliation corrects the status.

**Refresh Shipment (button on the Delivery Note)**

- Visible only when a shipment number is stored. It gets the shipment from Noon and updates Shipping Status, Last Sync At and the other read-only Noon fields.
- It never edits the items of the Delivery Note. If Noon's items differ from ours, or Noon shows the shipment cancelled, the case goes to Needs Attention.

**Nightly reconciliation (11:59 PM, system time zone)**

| Check | Action |
| --- | --- |
| Submitted Delivery Note with no shipment at Noon, or a cancelled one | Needs Attention |
| Shipment at Noon whose Delivery Note is Draft or Cancelled | Needs Attention |
| Status or items differ between ERPNext and Noon | Status is updated automatically, item differences go to Needs Attention |
| Order cancelled or items cancelled at Noon while still open in ERPNext | Needs Attention, using the order list to catch missed webhooks |
| Operations left in an unknown state | Ask Noon and resolve, otherwise Needs Attention |

Only the status is fixed automatically. Everything else is reported, because automatic repairs are how duplicate shipments get created.

## 8. Cancellation

The Delivery Note is cancelled in ERPNext only after Noon has confirmed that the shipment is cancelled.

The system sends the cancellation in `before_cancel`, after asking Noon for the shipment's current state. Noon cancels the whole shipment, never part of it, so changing the items or the AWB of a created shipment means cancelling it and creating a new one from an amended Delivery Note.

| Noon state or answer | Action |
| --- | --- |
| No shipment was ever created | Cancel the Delivery Note normally |
| Noon confirms the cancellation | Continue cancelling the Delivery Note |
| Shipment is already cancelled at Noon | Treat as success and continue, without sending another cancel |
| Noon says the shipment cannot be cancelled in its current state | The Delivery Note stays Submitted and the dialog shows the status and Noon's reason |
| Temporary error or unknown result | The Delivery Note stays Submitted, dialog with Retry. Retry asks Noon first |
| Noon cancels, but the local cancellation fails | Needs Attention. Retry only the local cancellation and never resend the cancel to Noon |

- **Which states allow cancellation** is learned from the Noon sandbox, and the Cancel action shows the rejection reason whenever Noon refuses.
- **Cancelling the shipment also cancels its items at Noon (documented, UNVERIFIED).** Noon's API reference (`docs/noon-integration/noon_api_full.md`, CancelShipment) says: "Cancels an existing shipment. All items included in that shipment will also be canceled". If that holds, the order sync then sees the units as `MP_ITEM_STATUS_CANCELLED` and cancels the Sales Order (all units) or shrinks it (some units) by itself, and the units may not be shippable again. ERPNext never calls UpdateOrder or any order-level path for a note cancel. The Cancel confirmation (submitted note and the draft Cancel Noon Shipment button) warns about this in plain words. If Noon cancels the shipment but keeps the units `CONFIRMED`, a Cancellation Unknown note cannot be proven cancelled by a refresh and stays Cancellation Unknown (a known stuck state; Retry or a person decides).
- **Cancelled by Noon or in Seller Lab:** the Delivery Note stays Submitted, Shipping Status is updated, and the employee receives a Notification and a Needs Attention item. A submitted note is cancelled automatically (decided 2026-11-01) once a read (webhook, Refresh, nightly) shows every unit cancelled at Noon, with no Noon call; a linked submitted document that blocks it leaves the note submitted with the reason in Needs Attention for the employee to resolve.
- The existing handling of orders cancelled by Noon is unchanged.

## 9. Invoices

Invoice upload is a backup step. It never blocks Submit, Cancel or any other flow.

- **Upload Order Invoice** is a button on the Sales Order and calls Noon's order invoice endpoint.
- **Upload Shipment Invoice** is a button on the Delivery Note and calls Noon's shipment invoice endpoint.
- The invoice file is saved in the native Attachments of the document the button was used on, and then sent to Noon.
- The document records that an invoice was uploaded and when. A second upload supersedes the first, and the upload carries an idempotency key, so a retry of the same upload is safe. Pressing the button again shows a warning first.
- If the order changes after an upload, the system notifies the employee that the invoice may need to be uploaded again. Nothing is re-uploaded automatically.
- A failed upload shows the standard error dialog with Retry. It does not affect the shipment.

Open question: is the file attached by the employee, or generated from the Sales Invoice print? The design works either way.

## 10. Notifications, Needs Attention and Logs

Employees are told through the application's existing Notifications and Needs Attention list, and every call to Noon is written to the application's existing logs.

**Needs Attention items**

- Noon confirmed an out-of-stock item but the local update failed.
- A Delivery Note is Draft while Noon holds its shipment.
- A Submitted Delivery Note has no shipment at Noon, or Noon shows it cancelled.
- Noon cancelled the order, an item, or the shipment on its own.
- Noon cancelled the shipment but the local cancellation failed.
- Items or status differ between ERPNext and Noon after a Refresh or the nightly reconciliation.
- An operation is still unknown after a check.
- An order changed after its invoice was uploaded.

**Notifications** go to the responsible employee for the same events when they come from a webhook or from the nightly job.

**Logs** record the operation (out of stock, get shipment, create, cancel, AWB, invoice), the document, the shipment number, the result, the HTTP status and Noon's error code, the time, and the user who started it. Secrets and tokens are never logged, and personal data is kept to what is needed.

## 11. Sync Risks and Edge Cases

The highest risk is Noon data lost to a rollback, and the rest are handled by asking Noon first and by the nightly reconciliation.

| Case | What goes wrong | Handling |
| --- | --- | --- |
| Rollback after Noon succeeded | AWB, shipment data and logs vanish while Noon keeps the shipment | Commit Noon data on its own before any error is raised (section 5) |
| AWB generated, create fails | The AWB is consumed and a new one would be wasted | Store the AWB at once, reuse it on retry, and lock the checkbox |
| Created or cancelled in Seller Lab | ERPNext and Noon disagree without any ERPNext action | Webhook, Refresh Shipment, nightly reconciliation, then Needs Attention |
| One item cancelled by Noon inside a shipment | Shipment-level checks look fine while items differ | Compare items, not only status, in Refresh and reconciliation |
| Item marked out of stock while in a Draft Delivery Note | Draft still holds an item Noon cancelled | Blocked in section 3 |
| Submit twice or two users at once | Parallel create attempts | Lock the Delivery Note, ask Noon first |
| Webhook arrives before Submit finishes | Event has no Submitted Delivery Note to update | Ignore it, the next Refresh or reconciliation corrects the status |
| Webhook repeated or out of order | Wrong or flapping status | Ignore duplicates, never move the status backwards |
| Duplicate AWB on two Delivery Notes | Scanning problems at Noon | Check against other non-cancelled Delivery Notes |
| Invoice changed after upload | Noon holds an outdated invoice | Notify the employee (section 9) |
| Order cancelled by Noon with open Delivery Notes | Items still being prepared for a dead order | Reconciliation order-list check, then Needs Attention |

## 12. Sandbox Checks and Acceptance Criteria

The points below are assumptions to test with sandbox orders before release, and none of them blocks the design.

**To verify in the sandbox**

- Which shipment states allow cancellation, and what Noon answers when it refuses.
- Whether creating a shipment twice with the same shipment number returns the first one or fails.
- What get shipment returns for a cancelled shipment, and whether it includes a last-update time.
- Whether marking the same item out of stock twice is harmless.
- Webhook details: authentication, event identifiers, the list of statuses and their order.
- Whether a generated AWB expires or can be released if unused, and whether create shipment can generate the AWB itself.
- What happens to a shipment when Noon cancels one of its items.
- After the first real CancelShipment (all UNVERIFIED; Noon documents that the shipment's items are cancelled too): `GetFbpiOrder` for the order shows each unit's `mp_status`, `integration_status` and `cancellation_reason_code`; what `GetShipment` answers for the cancelled shipment; whether a new CreateShipment for the same units works; whether a webhook is sent and how long it takes; which shipment states refuse a cancel; whether a repeat cancel of an already cancelled shipment is safe.
- Invoice endpoints: when upload is allowed (a second upload supersedes the first, known from Noon's documentation).
- Rate limits, and how the session behaves on expiry or a 401.
- On the ERPNext side: that an error in `before_submit` rolls back the save, that the over-delivery check catches an item removed by Update Items, and that Update Items releases the stock reservation.

**Acceptance criteria**

- [ ] Mark as Out of Stock is blocked for items in a Draft or submitted Delivery Note.
- [ ] The item leaves the Sales Order only after Noon confirms, and a failure shows the error dialog with Retry.
- [ ] An unknown out-of-stock result is checked with Noon before any resend.
- [ ] Selecting Noon removes the shipping rule and lets the employee choose the items and quantities of the shipment.
- [ ] The AWB checkbox sits under the AWB field and locks the field, and both lock after generation.
- [ ] A duplicate AWB across Delivery Notes is refused.
- [ ] Submit never completes without Noon's confirmed shipment, and `Sending to Noon...` is shown.
- [ ] A timeout never creates a second shipment, and Check Noon resolves it.
- [ ] Noon data survives a failed Submit and is reused on retry.
- [ ] Cancel never completes without Noon's confirmation, and a refusal shows the status and reason.
- [ ] If Noon cancels and ERPNext fails, only the local cancellation is retried.
- [ ] Webhooks update Shipping Status, duplicates are ignored, and old events do not move it backwards.
- [ ] Refresh Shipment updates the Noon fields and sends item differences to Needs Attention.
- [ ] The 11:59 PM reconciliation finds both directions of drift and reports them.
- [ ] Both invoice buttons attach the file, record the upload, and never block another flow.
- [ ] Every call to Noon is logged without secrets.
