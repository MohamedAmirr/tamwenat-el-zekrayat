# UI customization guide

How to change the Desk UI of `marketplace_integrations`. Shared rules (permissions, verification, version compatibility) are in `docs/frappe-best-practices.md`. JS gotchas are in `docs/frappe-conventions.md` ("Client scripts") and the project skill `.claude/skills/frappe-desk-ui/SKILL.md`. This guide does not decide which modules to keep or remove; it gives the method.

## Workspace and sidebar customization

- Workspaces, Sidebar documents and Docks are standard documents synced by `bench migrate`. The importer reimports a file only when its `modified` is newer than the DB row, so bump `modified` on every edit. Details and the Frappe 16.51+ Sidebar format: `docs/frappe-conventions.md` ("App-level folders auto-synced by `bench migrate`").
- Role-filtered navigation (#326): Sidebar and Sidebar Item have no roles field; an item shows when the user can read its target (a Workspace through its `roles`). A Section Break whose items are all filtered out still renders its header, so give every section at least one item for every role that sees the shell, or merge sections. The first item is the landing item: keep it one every platform role can open (Home = Workspace `Tamwenat Marketplaces`, whose roles include the three platform roles). Workspace shortcuts are filtered per user the same way (`get_shortcuts`), but Workspace header blocks are NOT, so workspace content avoids static per-platform headers (a Talabat User would see empty "Shopify"/"Noon"/"Bosta" headings); the Marketplaces Workspace keeps only neutral headers (guard: `tests/test_navigation.py`).
- Dock mount: the Marketplaces and Bosta rail entries come from `dock/marketplace_integrations/marketplace_integrations.json` (`mount_on: erpnext`, one Sidebar row each, icon and title required). Rows are appended after ERPNext's own rows. A site or user with a saved erpnext Dock layer drops entries it does not name, so on such a site add them in Manage Dock. Our Dock row and shell icons (`store`, `truck`) are Lucide stroke ids (not every Lucide-looking name exists: `home` does not, `house` does). ERPNext's own dock rows use `*-soft` ids from `module-icons.svg` (frappe and erpnext `public/icons/`); no `store-soft`/`truck-soft` exist, so how our icons look beside ERPNext's soft ones is a browser check. The icon test accepts an id from the Lucide or either module-icons sprite.
- One module per shell (#326): the Marketplaces shell uses module `Marketplace Integrations`, the Bosta shell its own Module Def `Bosta` (`modules.txt`, folder `bosta/` holding `sidebar/bosta/bosta.json`). Frappe 16.52 resolves a Workspace route to the first shell whose module lists the workspace (`module_for_workspace` in `sidebar.js`; `workspaces` is attached per module in `sidebar.py`), so two shells sharing a module opened the wrong one: the Marketplaces Dock icon landed on the Home workspace and the Bosta shell took over. Shells under different modules also no longer share Custom Sidebar layers. The Bosta doctypes stay in module `Marketplace Integrations`; they still open in Bosta because the Bosta shell lists them (`ShellIndex.resolve`), and `tests/test_navigation.py` pins this. `bench migrate` creates the Module Def (`sync_module_defs`) but does not import the new `bosta/` folder on that same run (the module map is cached from the old `modules.txt`), so the `post_model_sync` patch `patches/v0_0/import_bosta_module_sidebar.py` refreshes the map and imports the Sidebar; a new module in `modules.txt` always needs such a patch. `User.block_modules` and Module Profile now need `Bosta` blocked separately from `Marketplace Integrations`.
- A shortcut without a `stats_filter` reopens the user's last-used filters. Give filtered or "show all" shortcuts an explicit `stats_filter`.
- Dev and prod can drift in Frappe version. Check both before depending on newer framework UI (Sidebar doctype); see `docs/frappe-best-practices.md` (Version compatibility).
- Sync check: after `bench migrate` on a fresh test site, the workspace and sidebar must appear without manual steps.

## Forms, lists, reports, custom pages

- Order of preference: standard field/setting, then report, then form or list script, then a custom page. A custom page is the last resort because it carries its own permission, translation and layout work.
- Forms and lists: use `doctype_js`/`doctype_list_js`, never edit core. Use the patterns in the `frappe-desk-ui` skill.
- Reports: filter by the user's permissions (`frappe.get_list`, not `get_all`, for user-facing rows).
- Custom pages: set the page's roles, authorize every server call, and render server values escaped.
- Sales Order list hover card (#325, `public/js/order_hover_card.js`): lists EVERY item of the order, no cut-off (a 45-item order works). Each line: 40 px thumbnail (Sales Order Item `image`; neutral box when absent, unsafe or failed to load), name, item code and quantity (both in `bdi dir="ltr"`); the Shopify SKU text is not shown. The area has a header "Items (N)", a 320 px max height, scrolls (`overscroll-behavior: contain`, so the wheel at the list end does not scroll the page and close the card). Frappe's hover card never takes keyboard focus (Tab from the subject link closes it), so keyboard users scroll the list in the Details dialog (the area has `tabindex="0"` for that). Shopify CDN pictures (`cdn.shopify.com`) are requested small with `width=96` added in JS (`thumbnail_url`; other hosts and file paths unchanged, an existing `width` is kept). Image URLs are validated on the server (`safe_image_url`) and again in JS (`safe_image`; file paths may hold a space and an apostrophe); load failure is handled by an `error` listener (`wire_images`), never an inline `onerror`. A "Delivery Address" section follows "Customer" (plain-text lines from the server, each escaped in JS and wrapped in `<bdi dir="auto">` so mixed Arabic/English lines keep their direction, `overflow-wrap: anywhere`; omitted when empty; the Details dialog shows the same). Details: `docs/marketplace-integrations/architecture.md` ("Order hover card").
- Loading, empty, success and error states are required on every async screen. Errors show the server message escaped, with a recovery action where one exists.

## Readable references in lists

- Prefer native settings: `title_field` + `show_title_field_in_link` on the target doctype, and `in_list_view` / `in_standard_filter` on real fields. Formatters are client display only; sorting, filtering and search must stay on real stored fields (`search_fields`).
- Frappe falls back to the docname in list and link display when the title field is empty (`Document.get_title()` itself returns `''`), so keep the title field filled (see `MarketplaceOrder.before_save`).
- Set `hide_name_column: true` in the list settings of a doctype with a `title_field`, or Frappe adds a second `ID` (docname) column next to the readable subject. Keep the docname reachable (form, search, plus the row tooltip from the shared `public/js/list_row_name.js` helper: `frappe.require` it in `onload` and guard against it missing; do not copy it per list). Link report columns get titles in one batched query; Dynamic Link columns get none, so send a label from the report and render it escaped in `<bdi dir="ltr">`.
- Do not repeat the title value as a list column: the Marketplace Order list shows the platform order number as the subject; `external_order_id` and `order_code` stay on the form and in `search_fields` but are not `in_list_view`.
- The Sales Order list exposes the Marketplace Platform and Marketplace Order External Order ID through stored Custom Fields; keep these as real fields so sorting and standard filtering work. The Sales Order list no longer shows `custom_shipping_status_summary` (the Bosta delivery counts) as a column: the Status and Payment columns replace it (see "Sales Order Status and Payment columns" below). The Bosta tab, handover state and bulk create were retired in epic #413 (#408).
- Carrier status in the lists (Bosta states, Noon Shipping Status): the Delivery Note list gets an extra column by setting `in_list_view` on the Custom Field `custom_shipping_status` (fixture, needs `bench migrate`; a list script cannot add a column) and formatting it with `settings.formatters` (`delivery_note_list.js`); ERPNext's native status column is untouched. The Sales Order list wraps ERPNext's `get_indicator` once (marker `__mi_list_extended`) with the new Status pill, see "Sales Order Status and Payment columns" below (the old carrier-status indicator and its Partially Delivered rule were removed from the Sales Order list; `carrier_status.js` still serves the Delivery Note list, where `carrier_status.test.js` pins every Shipping Status option to a color). The summary is still written for Bosta and Noon notes by `integrations/bosta/statuses.py::update_sales_order_summary` and read by the hover card.
- Delivery Note Shipping section (epic #413): a neutral shell `public/js/delivery_note_shipping.js` (intro per Integration Status, the "Sending to <carrier>..." dialog that Submit waits on with 2-second polling, Check / Refresh buttons, a Shipping status indicator with text) and a per-carrier file (`delivery_note_bosta.js`: Pick Bosta City dialog, Fetch Bosta Label) that registers with `frappe.marketplace_integrations.shipping.register_carrier`. A carrier may register `pick_city(frm)`: when the request answers `needs_city` (the server could not fill the city) the shell stops Submit and calls it. The section itself is always visible because the native Carrier (`transporter`), AWB / Tracking No (`lr_no`) and Transport Receipt Date (`lr_date`) live in it (moved by the `field_order` Property Setter; a section hidden until a carrier is chosen could never be used to choose one). Carrier-managed fields (COD pair) use a `depends_on` that reads `frappe.boot.marketplace_shipping_carriers` (server `boot_session`), never a hard-coded carrier. Columns: identity (Carrier, AWB, receipt date, delivery id, reference), status (Noon Carrier Status/Error, Integration Status, Shipping Status), then COD/city/label/sync/cost. The `before_submit` handler returns a promise and sets `frappe.validated = false` on failure; after Created it calls `frm.reload_doc()` because the worker bumped `modified`. The Shipping section sits right after the header section (before Accounting Dimensions); anything inserted after a header field would drag the header's posting-date and company columns into it. The sending dialog has "Close, keep sending"; an Unknown result offers Check with Bosta in the same dialog; a server refusal is parsed from `_server_messages` and shown escaped; `custom_cod_amount` and `custom_cod_confirmed` go read-only once the shipment started, and editing the COD ticks COD confirmed. Carrier text (the stored error, the Check answer) is escaped where it is rendered. The Submit wait must be checked in a browser pass. Return pickup (#411): the shell's wait dialog is `send_and_wait(frm, carrier, submitting)`, shared by the native Submit (`submitting` true) and the Bosta button "Request Bosta Return Pickup" (false: its texts do not mention submitting). The shell drives a return only when `custom_return_source` is "Customer Return Pickup" (`carrier_name`), and a return's Submit never waits. `custom_return_source` is editable on a draft return (read-only once a pickup started or for "Returned by Bosta"); `custom_returned_cod` shows only for a Bosta pickup return; the outbound COD pair is hidden on returns. The button flow must be checked in a browser pass (Arabic, RTL). Live COD prefill: only while the Delivery Note is being CREATED (`frm.is_new()`), and only when `frappe.boot.marketplace_shipping_carriers` includes Bosta, `delivery_note_bosta.js` asks `api/bosta_shipments.get_default_cod` (POST; the form's grand total and each row's Sales Order only; checks read on Delivery Note and, when exactly one Sales Order is referenced, on it; at most 200 rows; builds a transient document, never saves). It asks when the carrier becomes Bosta (`transporter` / `transporter_name`), on refresh of a new Bosta note (for example one made from a Sales Order), and, debounced 400 ms, when item rows, taxes and charges (including the shipping charge), shipping rule or discounts change (ERPNext assigns `grand_total` without a field event, so these events are hooked instead), until the person types an amount (`frm.__cod_typed`; COD confirmed is ticked by default since 2026-11-09, so it no longer gates the prefill). A saved note is never prefilled by the browser: the server sets the COD on insert (`computed_cod` in `_apply_cod_rule`) unless the person typed an amount: the handler then sets the hidden Check `custom_cod_typed` = 1 on the new form, which makes the server keep the amount. "Cancel Bosta Shipment" on a draft (when `frappe.model.can_delete("Delivery Note")`) calls the native delete, whose `on_trash` cancels the shipment at Bosta first, and opens the Sales Order after it. The amount is written with `frm.set_value` under a guard flag so the `custom_cod_amount` handler does not read it as the person's edit; a typed or confirmed amount is never overwritten; an answer for another document is ignored, and an answer for a changed carrier, items or total is dropped and asked once more. The field description says "Filled from the order: <amount>. You can change it." until the person edits the amount, the note is saved or it stops being new. Leaving Bosta clears only the amount the prefill wrote. The state lives on `frm`, which Frappe reuses across documents, so it is reset in `onload` and whenever `frm.doc.name` changes, and a pending timer never writes into another note. Browser pass needed (English and RTL).
- Marketplace Account form, Shopify only: the "Shipping Method Rules" editable-grid table (`shopify_shipping_method_rules`, columns Shipping Title and Delivery Days) sits under Delivery Lead Days; it is plain Frappe, no custom JS. Its description says unmatched orders use Delivery Lead Days. The Sales Order list delivery countdown is unchanged.
- Marketplace Account form, Shopify only (#526): a "Pull Missing Images" button (`configure_shopify_images`), shown only on a saved account with a connection and Marketplace Account write. It confirms, queues `api/shopify_item_images.queue_pull_missing_images`, and opens the shared `ShopifyCatalogPushStatus` dialog with `IMAGE_OPTIONS` (rows link to `/app/item/<item>`; a pulled image counts as "Updated"). Existing Item images are never replaced.
- Platform column as a pill (Marketplace Order, Marketplace Account, Sales Order lists): `platform` on the first two and the Custom Field `custom_marketplace_platform` on Sales Order are already list columns; the list scripts only add a `settings.formatters` entry that calls `platform_badge.formatter`. Colors: Noon yellow, Shopify green, Talabat orange, every other value grey (`platform_badge.test.js`). The pill is wrapped in a `filterable` link with `data-filter`, so the native click-to-filter on the platform still works (no loss), and carries a tooltip `"<translated column label>: <translated value>"` (escaped). Platform colors are brand colors, not status colors; in the Marketplace Account list, where a status indicator sits beside the pill, Talabat orange and Shopify green resemble status colors (a disabled/closed/ok account), so read the status from the indicator, not the platform pill. The pills use `.indicator-pill`, which Frappe 16.52 deprecates in favour of `.es-badge`; the app's other pills use it too, so this stays consistent and all move together later. Tests stub `frappe.utils.escape_html` with Frappe's real mapping (it encodes `'`, backtick and `=` as `&#39;`, `&#x60;`, `&#x3D;`), so `data-filter` is asserted as `field,&#x3D;,value`. Frappe appends `doctype_list_js` hook files after the doctype's own `<name>_list.js`, so Marketplace Order and Marketplace Account (own list scripts) look the helper up per row and fall back to escaped plain text; the wiring test is `test_order_hover_card_js_wiring.py`. The Delivery Note list has no platform column: Delivery Note has no platform field (only a Sales Order one), so adding it needs a new stored field and a decision on how it is filled.
- Sales Order Status and Payment columns (branch `feat/sales-order-list-statuses`; data source and rules: `docs/marketplace-integrations/architecture.md`, "Status and Payment columns on the Sales Order list"): two separate columns for every order, one meaning per pill, text plus colour (gray waiting, blue ready, orange on the way, violet delivered but unpaid, green done, red only for a problem). Violet, not yellow: Frappe 16.52's badge (`frappe.ui.badge`, `badge-legacy-colors.css`) draws `yellow` and `orange` both as amber, so the two would look identical; the valid badge themes are gray, blue, green, amber (= orange), red and violet. Both columns use the same `es-badge` markup. Status replaces the native indicator (`get_indicator`, shown in Frappe's own "Status" column) for a submitted order that is not Closed / On Hold / Cancelled / Draft and has no advance payment pending; ERPNext's own pill stays for those. Labels: Not prepared yet, Ready, waiting for pickup, On the way, Delivered, payment not received, Delivered and paid, Delivery problem, Waiting for Stock, and the red Needs Attention (#533) shown before all of them (hover title = the order's own `custom_attention_reason`, set on the badge through `frappe.ui.badge` so it is escaped; click filters `custom_needs_attention,=,1`; the form header, a red `set_headline_alert` banner and the Mark as Resolved button are in `public/js/sales_order.js`). Delivery problem is red with two tips (returned or lost parcel; a failed delivery attempt for Bosta exception codes, "follow up with Bosta") and shows only when the newest live Delivery Note is the problem one. Payment is a real list column backed by the hidden Custom Field `custom_payment_display` (a list script cannot add a column; the field is never written): Paid by marketplace (Talabat and Noon orders, from the Sales Order's `custom_marketplace_platform`), Paid in advance, Paid (invoice), Partially paid (#534: any advance above 0 below the total; hover = the amount still owed; an orange pill, and a delivered partially paid order reads Delivered, payment not received), Pay on delivery. Every pill has a `title` with the meaning and the next step (the Status badge's fixed Frappe title is replaced in the DOM after each render), and each of the two headers gets a small "?" button (`aria-label`, 24 px target) that opens a legend dialog of all its states. The pills load from ONE server call per list page; until it answers the rows of that page (marked in `settings.before_render`) read "Loading...", a row nobody asked about (Quick List) keeps ERPNext's indicator, and if the call fails ERPNext's indicator stays and Payment is empty. Requests are numbered: an older answer arriving after a newer one is ignored, and a failure only hides answers older than itself. Every Status pill carries a real filter (`status,=,<native status>`, like ERPNext's own pill), never an empty one. The Payment column holds no stored value, so its header loses sorting (`data-sort-by` removed) and it is empty in Report View and in exports, where list formatters do not run; Frappe still offers it in the sort selector and the column picker. The Sales Order FORM header also calls the list's `get_indicator`; it keeps ERPNext's indicator because a full document has a `doctype` key and a list row does not. A saved List View Settings field list or saved layout may hide the Payment column until reset. Browser pass (English, Arabic RTL, keyboard on the "?" buttons) pending the user; checklist in `docs/user-actions.md`.
- Delivery Note Carrier column: `transporter` (the native Carrier link to Supplier, relabelled by a Property Setter) is a standard field and not a list column by default. The Property Setter `Delivery Note-transporter-in_list_view` (`in_list_view` = 1, `fixtures/property_setter.json`, listed in `hooks.py` `fixtures`; needs `bench migrate`) makes it one without touching ERPNext. `delivery_note_list.js` adds `transporter` to `add_fields` and formats it with `platform_badge.carrier_formatter`: Noon yellow, Bosta red, every other courier grey, same filterable link, escaping and tooltip as the platform pill. Empty carrier shows nothing. A saved List View Settings field list or list layout hides the new column until reset.
- Sales Order delivery countdown column ("Earliest Delivery Date", Custom Field `custom_earliest_delivery_date`, Date, read only, `in_list_view`, fixture; formatter `format_delivery_countdown` in `sales_order_list.js`): the field holds the EARLIEST item delivery date because ERPNext sets the header `delivery_date` to the latest item date. The sync gives it its first value when it builds the order (Noon: earliest line date; Shopify and Talabat: the order's delivery date), outside the hashed snapshot. After that `services/sales_order_delivery.py::sync_earliest_delivery_date` (Sales Order `validate` and `before_update_after_submit`) always derives it from the item rows of a marketplace order, for staff edits (Draft save, "Update Items") and for the system's own changes (a line removed by the sync). It assigns the value only when the earliest item date differs from the stored one, so an edit that leaves the earliest date unchanged does not write the field. A header-only date edit does nothing (ERPNext resets the header to the latest item date). The order's own delivery date for a linked order is still frozen by the sync snapshot; only this countdown field follows the item dates. The pill shows only for an open marketplace order (submitted, `To Deliver` or `To Deliver and Bill`, platform set; the "To Deliver" and "To Deliver and Bill" statuses only); every other row is empty. Text from the whole-day difference to today (`frappe.datetime.get_diff`/`get_today`): 2 or more days green "In {0} days", tomorrow orange "Tomorrow", today orange "Today", overdue red "Overdue 1 day" / "Overdue {0} days" (separate strings, so the singular reads right in English and Arabic). The tooltip is the date in the user's format. The column is a real list column, so a saved List View Settings field list or saved layout may hide it; reset those settings if it is missing.
- Never use a mandatory field with a default as `title_field` (the default is dropped on new docs, see `frappe-conventions.md`).
- The subject link is plain text: it takes no HTML from a formatter.

## Scoped styling

- Add CSS only when no standard control does the job. Scope every rule under a class owned by this app (for example a wrapper class on your page or dialog), never bare element selectors or global overrides.
- Use Frappe's CSS variables for color and spacing so light/dark and RTL keep working. No inline `left/right`; use logical properties (`margin-inline-start`).
- Ship CSS through the app's `public/` assets and hooks; no editing of framework CSS.

## Role-based navigation versus authorization

Navigation only controls what staff see, never what they can do. Authorization and its verification: `docs/frappe-best-practices.md` (Permissions, Verification).

## Arabic, RTL, accessibility, responsive

- Translations: `docs/frappe-conventions.md` (Translations). Check RTL alignment, icon direction, number/date formatting and truncated text.
- Keyboard operable with visible focus, labelled inputs, indicator colors paired with text.
- Check a phone-width viewport and a desktop width for any custom page or dialog.

## UX principles

Source note: these come from the internet (NN/g, Baymard, PatternFly, Material, W3C, Frappe docs), user-approved 2026-10-22, and were read from search summaries, not fully verified. Repo rules and the installed framework win on conflict.

- Reversible actions: offer undo or soft-delete; confirm only serious or irreversible actions to avoid dialog fatigue. https://www.nngroup.com/articles/ten-usability-heuristics/
- Error messages: plain language, say what is wrong and the fix, e.g. "Bosta rejected the city. Pick a city and retry", not "Error 400". https://www.nngroup.com/articles/error-message-guidelines/
- Bulk actions: show the bulk toolbar only when rows are selected; with pagination, say that "select all" covers the current page only; show progress and per-row success/failure results. https://www.patternfly.org/components/table/design-guidelines
- Forms: validate on blur, not while typing; clear the error as soon as it is fixed; prevent errors with defaults and constraints. https://baymard.com/blog/inline-form-validation
- RTL: mirror direction icons (arrows, progress); do not mirror numbers, phone numbers, charts or non-directional icons. https://m2.material.io/go/design-bidirectionality
- Bidi text: wrap SKUs, URLs and phone numbers in `<bdi dir="ltr">` or use `dir="auto"` (source partly dated). https://w3c.github.io/i18n-drafts/articles/inline-bidi-markup/index.en
- WCAG 2.2 AA additions: click targets at least 24x24 CSS px; a focused element must not be hidden by sticky bars or dialogs. https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/
- Cheap evaluation: heuristic evaluation with NN/g's 10 heuristics and the fillable workbook. https://media.nngroup.com/media/articles/attachments/Heuristic_Evaluation_Workbook_1_Fillable.pdf
- Frappe (official docs): the sidebar never grants permission, entries a user cannot open are hidden; changing the sidebar for everyone needs the Workspace Manager role; workspace access is set per workspace by roles. https://docs.frappe.io/framework/user/en/desk/navigation/sidebar and https://docs.frappe.io/framework/user/en/desk/navigation/workspace.md
- Open question (unverified, ask staff): Arabic-Indic (٠١٢) vs Western (0-9) numerals; Arabic type size and line-height are not sourced.

## Module decision matrix

Used when someone asks to simplify the UI. Decide per module, with the dependency check first.

| Decision | Meaning | When | Dependency check before doing it |
| --- | --- | --- | --- |
| Keep | No change | Staff use it, other code depends on it | None |
| Hide | Remove from workspace, sidebar or desktop only | Not needed for daily work, still reachable by URL | Does any flow link to it? Does the server still allow access (intended)? |
| Restrict | Change roles or permissions so some staff cannot use it | Some roles must not see or act on it | Which roles lose access; which jobs, APIs, reports or links run as those users; permission tests for both roles |
| Uninstall | Remove the module or app | Nothing depends on it and data is archived | Imports, hooks, fixtures, Link fields from other doctypes, scheduled jobs, patches, reports, translations; backup and a tested rollback |

Rules:
- Hiding is not restricting, and neither is uninstalling. Say which one you mean.
- Uninstall is destructive: it needs explicit user approval, a backup, and a rollback plan (restore point plus the revert commit).
- Scope of removal and any permission change is the user's decision. Record the decision and the dependency findings in the issue.

## Browser acceptance checks

The user performs the real-browser pass on the dev site using this checklist, not from unit tests. Agents prepare accounts, data and the checklist, and must report browser checks as "not done by agent, pending user".
1. Log in as an ordinary staff user and as Administrator.
2. Open the screen from navigation, then by direct URL, then from a list view.
3. Exercise the main action, the empty state and an error.
4. Repeat in English and in Arabic (RTL).
5. Keyboard-only pass: tab order, Enter and Escape in dialogs.
6. Narrow viewport pass for custom pages and dialogs.
7. Screenshot when the change is visual and will be reviewed.
8. For a hidden item: confirm the item is gone from navigation and the server still enforces permissions on its URL and API.

Agents report browser checks as "not done by agent, pending user"; never substitute test results for them.

## Deployment and rollback

- UI JS/CSS changes ship through the app; deploys follow `docs/frappe-cloud-publish.md`. Synced standard documents (workspace, sidebar, desktop icon) update on `bench migrate` with a newer `modified`.
- Browser caches: JS assets need a build/cache clear, and if a change doesn't appear, hard refresh or run `bench clear-cache` (form meta cache: `docs/frappe-conventions.md`, doctype_js bullet). Say what the deployer must run.
- Rollback: revert the commit and redeploy; for synced documents, the reverted file needs a newer `modified` than the DB row, otherwise migrate skips it. For permission or workspace changes made by fixtures or patches, write the reverse change before shipping.
- Take a backup before migrating a site with real data.
