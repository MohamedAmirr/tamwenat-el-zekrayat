# Frappe / ERPNext conventions

Reference for any custom app work in this project. Applies once a custom app exists under `apps/<app_name>/`.

Cross-cutting rules (permissions, data integrity, background work, verification) live in [`frappe-best-practices.md`](frappe-best-practices.md); Desk UI guidance in [`ui-customization.md`](ui-customization.md).

## Never touch core

Never edit files inside the `frappe` or `erpnext` apps directly — those changes are lost on upgrade and untracked. All customization goes in:
- A custom app (new doctypes, business logic, overrides via hooks), or
- Framework-native customization tools (Custom Field, Property Setter, Client Script, Server Script, Custom DocPerm) — these are exportable as **fixtures** in the custom app so they're version-controlled.

This applies to any project-specific change to an existing ERPNext doctype, form, workflow, or behavior — not just schema edits. Covered by this rule: Custom Fields on standard doctypes (`Sales Order`, `Sales Invoice`, `Item`, `Customer`, etc.), form/UI behavior changes, client scripts, server-side validations/hooks, custom buttons/actions, and integration-specific fields (order source, external order IDs, marketplace references, integration statuses). All of it must be reproducible by installing/migrating the custom app on a fresh site — via fixtures, hooks, patches, migrations, or installation logic — never by hand-editing a core file or repeating manual production configuration.

Before modifying anything that looks like an ERPNext core file, check whether the requirement can be done through the custom app instead, in this order:
1. Custom Fields / Frappe customization mechanisms
2. Hooks and DocType event handlers
3. Client scripts or custom JS shipped by the app
4. Fixtures, patches, migrations, or installation logic
5. Frappe-provided overrides, only when genuinely necessary

Direct core modification is a last resort and must be explicitly flagged to the user and documented if it's ever used — see "Show GitHub issue content..." and "Ask before deciding" in the root CLAUDE.md for the same standard applied to irreversible/structural decisions.

## App layout

```
apps/<app_name>/
  <app_name>/
    hooks.py
    modules.txt
    <module_name>/
      doctype/
        <doctype_name>/
          <doctype_name>.json     # schema
          <doctype_name>.py       # server controller
          <doctype_name>.js       # client script (optional)
          test_<doctype_name>.py  # unit tests
```

## Doctype conventions

- Doctype **name**: Title Case, human-readable (`Sales Order`, `Member Card`). The folder/file name is the snake_case slug of that (`sales_order`).
- Field `fieldname`: snake_case, matches the Python attribute (`doc.customer_name`).
- Prefer the Frappe ORM over raw SQL: `frappe.get_doc`, `frappe.get_list`/`get_all`, `frappe.db.get_value`, `doc.save()`/`doc.submit()`. Reach for `frappe.db.sql` only when the ORM genuinely can't express the query, and always parameterize (`%s`, never string-formatted SQL). `get_all` bypasses user permissions, see [`frappe-best-practices.md`](frappe-best-practices.md).
- Controller hooks (`validate`, `on_submit`, `before_save`, etc.) go in `<doctype_name>.py` on the `Document` subclass — don't scatter business logic into API endpoints when it belongs on the doctype.
- A `title_field` that has a static default loses its default on new docs (`frappe/model/create_new.py`): never use a mandatory field with a default as `title_field`; this broke Bosta creation in #324.
- Naming series / autoname: prefer built-in `naming_series` or `autoname` in the JSON over custom Python naming unless there's a real reason.
- Base autoname on whichever field(s) form the record's **stable identity — never a field meant to change after creation.** The failure mode differs by autoname type, both confirmed directly against Frappe's source (`naming.py`/`base_document.py`), not assumed: for `autoname: field:X` (a single field mirrors `name`), `_sync_autoname_field` force-reverts any edit to `X` back to what `name` implies, on every save — the edit silently fails. For `autoname: format:...` (including a **custom `def autoname(self): self.name = ...`** controller method, needed when the identity fields need encoding beyond simple template substitution — e.g. to avoid a separator-collision risk, see the next bullet), `name` is only computed once, at insert (`set_new_name`) — Frappe never recomputes it on update. So changing an identity field on an existing record *does* persist the field's new value, but `name` silently goes stale/misleading relative to it. Either way, don't build the identity out of a field meant to change.
- Frappe has **no native composite/multi-field unique constraint.** For "field A + field B must be unique together" where neither alone is the record's identity, add a hidden (`hidden: 1`, `read_only: 1`) field with `unique: 1`, computed in a `before_save()` hook. **Don't join the values with a plain separator** (`f"{a}-{b}"`) unless you can prove neither field's real values can ever contain that separator — e.g. a bare `-` is a real collision risk for anything that might hold a UUID or a hyphenated code (`item="A-B", vendor="C"` and `item="A", vendor="B-C"` both produce `"A-B-C"`). Use an unambiguous encoding instead, e.g. `frappe.as_json([a, b])`, and give the field an explicit `length` generous enough for the combined encoded size. This gets a real DB-level unique index — a `validate()`-time `frappe.db.exists()` check alone is a check-then-insert race, not atomic.
- Any field storing an **opaque external identifier or secret** (API keys, external SKUs/IDs, tokens — anything whose exact bytes matter and is never rendered as HTML) must set `"ignore_xss_filter": 1` in its JSON. `Document.save()` runs HTML/XSS sanitization on any field value containing `<`/`>`, Password fields included, and will silently strip characters that merely *look* like an HTML tag — a real Talabat client secret was corrupted this way in production testing (a `<...>` substring silently deleted on save, no error). This is a real, confirmed footgun, not a hypothetical. The **`JSON` fieldtype is not exempt either** — Frappe's `_sanitize_content()` runs over its serialized string value the same as any other field, so any JSON field storing external free text (e.g. a Talabat promotion name, or any other platform-sourced array/object rendered nowhere as HTML) needs `"ignore_xss_filter": 1` too, not just Data/Text/Password fields.
- Prefer **expression-based autoname** (`"autoname": "PREFIX-.#####"` — a literal prefix plus Frappe's built-in running-counter placeholder, no `format:`/field-reference needed once it contains `#`, confirmed against `naming.py`'s `set_name_from_naming_options`) when the record's identity fields shouldn't become `name` at all — e.g. because an external ID may change, or because encoding two fields into `name` risks the separator-collision class of bug described above. This computes `name` once at insert, from nothing but a shared counter — completely decoupled from any document field, so there's no naming-vs-identity coupling to reason about at all. Combine with a hidden `unique: 1` key field (same pattern as composite uniqueness above) for the actual business-identity constraint. Also set `"naming_rule": "Expression"` explicitly in the JSON alongside `autoname` — Frappe's `patch_old_naming_expressions` migration doesn't backfill this for hand-authored doctype JSON, so without it Desk shows an empty naming rule on the doctype's Settings, and a careless save from Desk could clear `autoname` outright.
- Any field feeding a hidden `unique: 1` composite/secondary key computed in `before_save()` (see above) must have **its own normalization done inside the key-computation function itself**, not left to Frappe's field-level normalization (e.g. `_validate_selects()` for `Select` fields, which strips/validates against `options`). That normalization runs in `_validate()`, which fires *after* `run_before_save_methods()` — i.e. after `before_save()` has already computed and stored the key from the raw, pre-normalization value. A value like `" Talabat "` would then be hashed untrimmed but persisted trimmed, silently decoupling the key from the row it identifies (confirmed directly: `document.py`'s `insert()`/`save()` call order is `_validate_links()` → `run_before_save_methods()` [`validate()`, `before_save()`] → `_validate()` [`_validate_selects()`, `_validate_mandatory()`, ...]). `_validate_selects()` is also skipped entirely under `frappe.flags.in_import`, so Data Import is a second path that bypasses it. Normalize (`cstr(...).strip()`, and reject/placeholder rather than silently stringifying `None`) inside the shared key function so it can't diverge from what ends up stored, regardless of validation order or whether some validation step gets skipped.
- Because core's `_validate_links()` runs *before* your controller's `validate()`/`before_save()` (previous bullet), a hand-written Dynamic Link existence check in your own `validate()` is normally dead code on the ordinary insert/save path — core's own `LinkValidationError` always wins the race first. A test asserting only `assertRaises(frappe.ValidationError)` around such a scenario will stay green even if you delete your own check, since core's exception is a `ValidationError` subclass too. If you want a test that actually proves your own check does something, either assert on the specific message/exception type, or bypass core's check with `.insert(ignore_links=True)` / `flags.ignore_links = True` and confirm your own check still fires — the same applies to a hand-written mandatory-field check racing against core's `_validate_mandatory()` (use `ignore_mandatory=True` to bypass core there).
- A **`Dynamic Link` field** (`fieldtype: "Dynamic Link"`, `options: <fieldname of the Link-to-DocType field>`) gets its target-document-exists check run automatically by Frappe core, in `_validate_links()` — confirmed in `frappe/model/base_document.py`'s `get_invalid_links()`. This runs *before* your controller's own `validate()`/`before_save()` (both on insert and on update), using whatever's in the `options` field as the target doctype: `frappe.db.get_value(self.get(df.options), docname, ...)`. So it already guarantees "this document literally exists in that doctype's table" without any hand-written check — but if the `options` field (e.g. a `connection_doctype`-style field) is unset while the Dynamic Link field has a value, the error is a generic `"{label} must be set first"`, not your own wording. Writing an explicit check in `validate()` anyway (`frappe.db.exists(self.connection_doctype, self.connection)`) is still worthwhile for a friendlier, doctype-specific error message and as defense-in-depth against any code path that sets `flags.ignore_links`.
- Because `_validate_links()` (previous bullet) runs before any controller hook, a field that a Dynamic Link's `options` depends on (e.g. `connection_doctype`) must be defaulted somewhere that *also* runs before `_validate_links()` — not just in `validate()`/`before_insert()`, both of which fire too late and only ever produce core's generic "`{label}` must be set first" error instead of your default ever taking effect. The one controller hook that reliably runs early enough for every construction path is `__init__()` itself (see `Marketplace Account.__init__()`/`set_connection_doctype()` for a worked example: it overrides `__init__`, calls `super().__init__(*args, **kwargs)`, then defaults the field). This covers `frappe.get_doc({...})` (dict construction) and `frappe.get_doc(doctype, name)` (load-from-db, since `super().__init__()` already runs `load_from_db()` for that path) — but it does **not** cover `frappe.new_doc(doctype)` followed by plain attribute assignment (e.g. `doc.platform = "Shopify"`), since `__init__` runs before the caller ever assigns anything, with the dependent field (`platform`) still blank. There is no single hook that closes that last gap generically; a caller using that construction pattern needs to either re-call the defaulting method itself after assigning the dependent field, or set the Dynamic Link's `options` field directly, before `insert()`/`save()`.
- A **`Data` field with no explicit `length` silently defaults to `varchar(140)`** (confirmed directly against the installed `frappe/model/base_document.py`'s DB-type map). This is a real trap for any Data field meant to store a full generated URL (site base URL + a long dotted method path, e.g. `get_url(TALABAT_CATALOG_WEBHOOK_PATH, ...)` persisted on `Talabat Connection`): it fits comfortably in local dev against `http://dev.localhost:8000/...`, but a longer real deployment host (e.g. a tunneled/proxied domain) or a longer method path pushes the same value over 140 characters, and `Document._validate_length()` raises `frappe.exceptions.CharacterLengthExceededError` on save/insert rather than silently truncating. Give any Data field storing a full URL (or any other value whose length isn't bounded by a short, known vocabulary) an explicit generous `"length"` in its JSON — same fix already used for a hashed composite-identity key field — instead of relying on the 140-char default fitting by coincidence in whatever environment happened to be tested first.
- A **Single DocType is not a valid Dynamic Link / Link target for "a specific record"** — confirmed directly against a real Single (`Talabat Settings`, before its #37 migration to the non-Single `Talabat Connection`): both Frappe's own core Link validation and a hand-written `frappe.db.exists(doctype, name)` check assume a normal per-row table (`tab<DocType>`) and query it by `name`. A Single has exactly one implicit record whose canonical "name" equals the doctype name itself — there's no way to legitimately reference "a specific Single record" the way a normal Link works, and passing any other value raises an unhandled `ProgrammingError` (Frappe tries to query a `tab<DocType>`-style table that doesn't exist for a Single) rather than a clean validation error. If a doctype needs multiple independently-configurable rows referenced by a Link/Dynamic Link — e.g. one credential set per external account/connection — it must be a normal (non-Single) DocType from the start, independent of whatever validation-mechanism detail is in play.
- ERPNext's `AccountsController.set_missing_item_details()` (`erpnext/controllers/accounts_controller.py`) **re-runs on every subsequent `validate()`**, not just the first `set_missing_values()` call a caller makes explicitly — every `.insert()`/`.save()` of a Sales Order/Quotation/Delivery Note/Sales Invoice/Purchase equivalent calls it again internally. For each Talabat-sourced/fetched field it considers, it only overwrites a child row's value when that value `is None` **or** the field is in its own hard-coded `force_item_fields` tuple (`item_group`, `brand`, `stock_uom`, `is_fixed_asset`, `pricing_rules`, `weight_per_unit`, `weight_uom`, `total_weight`, `valuation_rate` — confirmed directly against the installed source, not assumed). Critically, `rate` and `price_list_rate` are **not** in that tuple: once a caller explicitly sets a non-`None` `rate`/`price_list_rate` on a child row (e.g. from an external system's historical transaction price rather than a live ERPNext Price List), that value survives every later re-validation/re-save of the same document without ERPNext silently refetching a current Item Price over it. This is exactly why `marketplace_integrations/services/sales_order_sync.py` (#85) can safely call `set_missing_values()` once for purely structural defaults (Item/UOM/conversion/accounts) and then override `rate`/`price_list_rate` afterward — but it also means any check for "is this value actually present" on such a field must test `is None` specifically, never falsy/zero (`if not value`), since `0` is a legitimate rate/price and would otherwise look "unset" and get silently refilled by a later pass for a *different* field that genuinely does need the `None` check to distinguish missing-from-zero.
- ERPNext's `TaxesAndTotalsMixin.calculate_item_values()` (`erpnext/controllers/taxes_and_totals.py`) **unconditionally re-rounds every `Currency`/`Float`/`Percent` child-row field down to that field's own precision, via `Document.round_floats_in()`, before it ever computes `amount = rate * qty`** — confirmed directly against the installed ERPNext 16.33.0 source and reproduced live in a bench console. This runs on every `calculate_taxes_and_totals()` call, including the one `AccountsController.validate()` reruns internally on every subsequent `.insert()`/`.save()` of the same document — so assigning a higher-precision Python value to a child row's `rate` (e.g. to preserve a division remainder before multiplying back by `qty`) is silently truncated back down to that field's normal precision the moment any totals recalculation runs, even though nothing about the assignment itself raised an error. Since neither `Sales Order Item.rate` nor `.amount` sets an explicit `precision` in ERPNext's own doctype JSON, both fall back to the site's `currency_precision` System Setting and are therefore numerically identical — meaning `rate * qty` can only ever land on a multiple of `qty * 10^-currency_precision`, and a genuinely non-evenly-divisible target amount (e.g. a total of `9.99` split across `qty=2`, where no 2-decimal rate produces that exact product) is **structurally impossible to reconstruct** through ERPNext's own rate-times-quantity computation, no matter how precisely the Python-side division was rounded beforehand. The fix is a **Property Setter** (never a doctype JSON edit inside `erpnext`/`frappe` — see "Never touch core") raising the specific field's own `precision` above `currency_precision`, exported as a fixture in the custom app; this is exactly what `marketplace_integrations/fixtures/property_setter.json` does for `Sales Order Item.rate`/`.price_list_rate` (`services/sales_order_sync.py`, #85). Because a Property Setter's `precision` override is global to the doctype/field, this is a site-wide display/storage-precision change (e.g. every Sales Order's `rate` column can now show trailing digits beyond 2dp), not one scoped to whatever service needed it — verify that trade-off is acceptable before reaching for this, rather than assuming a locally-computed higher-precision Python value alone will survive ERPNext's own totals recalculation.
- A Frappe **`Float`/`Currency`/`Int` column is `NOT NULL` at the database level** (confirmed directly against this app's own `Marketplace Order Item.fulfilled_total_price`, a plain `Float` field): there is no way to persist an actual SQL `NULL` in one of these fields through a normal document save — a `None` value assigned to it is silently coerced to `0`/`0.0` on write, exactly like any other framework default-coercion. This is a real trap for translating an external payload where "the source field was absent/null" is a meaningfully different case from "the source field was a real zero" (e.g. Talabat's `item.pricing.total_price`, which `docs/talabat-integration/openapi.json` does not mark `required` on `OrderItemPricing`) — a downstream `if row.some_numeric_field is None:` guard on that Frappe field is **dead code**, since the field can never actually contain `None` once persisted; it always reads back `0`/`0.0` either way, indistinguishable from a genuine zero. Capture the null-vs-zero distinction earlier, at the point where the raw external payload is first parsed (a raw `dict.get(...)` still legitimately returns `None`), and persist that distinction separately — e.g. a sibling `Check`/boolean flag field, as `marketplace_order_item.json`'s `fulfilled_total_price_missing` does for `fulfilled_total_price` (#85) — rather than trying to recover the distinction later from a column that structurally cannot hold it.
- Frappe fills an **unset `Select` field with its first option on insert only, not on update**. A mapper that never sets such a field stores the first option (for example `Marketplace Order Item.external_status` = "NOT_PROCESSED", `pricing_type` = "UNIT") on the first import, but a re-import that assigns `None` through the upsert blanks it to an empty string, and no default is re-applied. Anything that hashes or compares the row (the #178 debounce fingerprint) then sees an unchanged order as changed. `_apply_order_fields` and `_upsert_order_items` in `services/marketplace_orders.py` now fall back (via `_unset_value()`) to the field's default or first `Select` option when the incoming value is `None`, so insert and update store the same value. Do the same for any new upsert helper that writes a `Select` field it may leave unset (found by #178, 2026-10-07). The same applies to `Float`/`Currency`/`Int`/`Check` fields: the column holds `0` after insert, and assigning `None` on update makes Frappe's Version diff (`0 != None`) log "changed from 0 to null" on a `track_changes` doctype on every re-save, even though nothing changed (seen on every Noon "Refresh from Noon"); `_unset_value()` returns `0` for them. Also note `Document.save()` sets `flags.ignore_version = frappe.in_test`, so no Version rows are written under the test runner: a test asserting on Version history must `patch.object(frappe, "in_test", False)` around the save, or it passes without the fix.
- ERPNext's `update_child_qty_rate` (editing a submitted Sales Order's rows) checks write AND submit (`update_after_submit`) permission on the **session user** and `frappe.flags.ignore_permissions` does not bypass it (a failure is re-thrown as a `ValidationError`, not `PermissionError`); it also sets `child_item.description = d.get("description")`, so a `trans_items` row that omits `description` wipes it to None (send the existing value); `SalesOrder.update_status()` performs NO permission check (only ERPNext's whitelisted wrapper does), so call `doc.check_permission("submit")` yourself; omitting a row from its `trans_items` deletes that row (qty 0 is rejected unless `allow_zero_qty_in_sales_order` is on). `so.cancel()` succeeds with a linked advance Payment Entry but leaves it submitted with an unallocated amount, so check `advance_paid` before cancelling (observed on ERPNext 16.33, #179).

- ERPNext's `update_child_qty_rate` (the "Update Items" dialog on a submitted Sales Order) writes the **child rows first**: it saves changed `Sales Order Item` rows (`child_item.save`), inserts new ones (`child_item.insert`) and deletes removed ones (`d.cancel()`, `d.delete()`), and only then does `parent.reload()` and `parent.save()`. A parent-level `before_update_after_submit` / `validate` hook therefore sees no item difference. To block or react to item edits on a submitted order, register `doc_events` on the child doctype (`before_update_after_submit` for a changed row, because a child row of a submitted parent has `docstatus` 1 and `run_before_save_methods` runs only that hook for the `update_after_submit` action, never `before_save`; `before_insert`; `on_trash`) and look up the parent's `docstatus` yourself: a parent's own save writes its rows without row hooks, so draft creation and submit are not affected (#368, `services/noon_item_edit_guard.py`; verified ERPNext 16.51).

- **`update_child_qty_rate` reserves stock LAST, per row, and skips a short row silently** (source read, not run; see `docs/frappe-best-practices.md` #500): the parent's `on_update_after_submit` hook runs inside `parent.save()`, before the entries are cancelled and re-created, so a hook there sees the final rows against the OLD reservations. A whole-order rule ("never partly reserved") needs a check after the call (`order_reservation.reserve_or_wait(refuse_partial=True)`) and, for other callers, a flag set by the child-row hooks (`order_edit.guard_row_*` -> `guard_reservation`) so the parent hook runs only when rows really changed in that request. A form button added by ERPNext in two places (the "Update Items" button is added by its form script AND its controller `refresh`) cannot be removed reliably by one `remove_custom_button`: wrap `frm.add_custom_button` on the form instance for that label (`suppress_update_items`, #500). Do not add a Client Script record for it.

- Looking up a row by a free-text key with `frappe.db.get_value()`/`get_all()` on MariaDB's default `_ci` collation matches case-insensitively, so `external_reference = 'ABC-1'` finds the row stored as `'abc-1'`. For identity-based records (e.g. `Marketplace Product Mapping`), look up by the normalized identity key the uniqueness check uses (`mapping_identity_key`), never by the raw text field. Writing through a text lookup then silently overwrites the wrong row. `services/mappings.py::upsert_mapping_for_listing()` is the reference shape.
- A standard read-only field can be made editable on a submitted document with two Property Setters (`read_only` = 0, `allow_on_submit` = 1), shipped as fixtures; this works on v16 at runtime (`Sales Order.contact_mobile`, #277). Only the Customize Form UI refuses to enable Allow on Submit for a standard field, a Property Setter is not blocked. Check first whether ERPNext overwrites the field: `update_if_missing()` in `set_missing_lead_customer_details` only fills empty values, so a directly-set `contact_mobile` survives saves.
- Moving a **standard** field is not done with an `insert_after` Property Setter: `Meta.sort_fields()` honours `insert_after` only for Custom Fields. The native mechanism is the DocType-level `field_order` Property Setter (name `<DocType>-main-field_order`, `doctype_or_field` = DocType, `property_type` Text, value = JSON list of every standard fieldname, what Customize Form writes). Build it from the doctype's JSON order with the fields moved; custom fields are not listed and are placed by their own `insert_after` (so Custom Fields inserted after a moved field follow it). Fields ERPNext adds later are re-inserted after their previous neighbour, so it survives upgrades. Delivery Note `transporter`/`lr_no`/`lr_date` do this (AWB / Carrier, relabelled by `label` Property Setters). They now sit inside the carrier-neutral Shipping section; that section has no `depends_on`, because a section hidden until a carrier is chosen cannot contain the Carrier field (gate the individual fields instead). Fixtures are keyed by name in `hooks.py`.
- Form sections cannot nest, so "put these several native sections under one collapsed area" is done by moving their **fields** (not the section breaks) into one Custom Field Section Break (`collapsible` = 1) via the `field_order` Property Setter, using the native column breaks of the emptied sections to split columns. The emptied native sections stay in the list and hide themselves at runtime (`layout.js` `refresh_sections()` hides a section with no visible control). When the `field_order` list holds **every** field including Custom Fields, `Meta.sort_fields()` applies it verbatim ("all fields match" path); otherwise unlisted fields are slotted by neighbour or `insert_after`, so a stale or hand-reordered list (a Customize Form save can capture a scrambled order, as Delivery Note did) silently produces a broken layout: always regenerate the list from the doctype JSON order, check `len(frappe.get_meta(dt).fields)` equals the list length, and dump `get_meta` after migrate. A new-vs-saved difference comes from `depends_on` such as ERPNext's `eval:!doc.__islocal` on `per_installed`/`per_returned`; override with a `depends_on` Property Setter whose value is empty. Delivery Note "More" is the worked example.

- **`doc.db_set({...}, notify=True, commit=True)` is the way for a worker to write fields back to a document a person may have open**: it skips `validate` and every `doc_events` hook (so the write cannot re-trigger the handler that queued the worker), still bumps `modified` (a stale open form then gets a timestamp-mismatch instead of silently saving old values over the write-back) and, with `notify=True`, publishes `doc_update` so a clean open form refreshes. `frappe.db.set_value` also skips the hooks but never notifies open forms. Used by `integrations/noon/delivery_note_shipment.py::_write_back` (#391).
- **A `validate` guard on an existing document must decide "is this one of ours" from the stored copy (`doc.get_doc_before_save()`), not from the document being saved.** Ownership that depends on all child rows (every Delivery Note row comes from one Noon Sales Order) is lost the moment someone adds a row without that link, and the guard would then skip exactly the edit it exists to refuse (`delivery_note_shipment.saved_state`, #391). On ERPNext 16.51 a plain Stock User also cannot save a Delivery Note when the customer's group has a default receivable Account: `get_party_account` checks read on that Account (`account_perm_check`) and throws a `PermissionError`, so grant it or leave the group account empty (found on `test.localhost`, #391; test users get `Account: read`).
- **Desk form hooks for Cancel and Delete (Frappe 16.51, `public/js/frappe/form/form.js`, `model/model.js`).** Cancel has a clean hook: `before_cancel` runs after the native confirmation, may return a promise, and a `frappe.validated = false` set before it resolves stops the cancel. Delete has none: `Form.savetrash()` calls `frappe.model.delete_doc` (confirm, then `frappe.client.delete`) with no script event, so intercept it only by wrapping the method per form instance (see the Close precedent under Client scripts) or give the user a button for the pre-step and let the server hook (`on_trash`) refuse the delete. #393 uses the button plus the server guard. Recheck on any Frappe upgrade.

## hooks.py

- `doc_events` for cross-doctype side effects (e.g. reacting to a Sales Invoice submit) instead of monkey-patching core doctypes. It is preferred over monkey-patching/overrides, not over service functions, and this app registers none for catalog doctypes (`docs/frappe-best-practices.md`).
- `scheduler_events` for cron-style jobs; keep the job function itself in the app, not inline.
- `fixtures` to export/version Custom Field, Property Setter, Client Script, Custom DocPerm, Workflow, etc. so `bench migrate` on a fresh site reproduces them.
- `override_doctype_class` / `override_whitelisted_methods` are last resorts — prefer `doc_events` first.

- A `hooks.py` `scheduler_events` entry is only a Python-side declaration — it does not itself create the Scheduled Job Type record Frappe actually runs. Confirmed directly against this app's own #107 Shopify inventory sweep/reconcile jobs: the corresponding `Scheduled Job Type` documents are created/updated only by `bench migrate` (Frappe's own scheduled-job sync reading `hooks.py`), so a code deploy alone (without a migrate) leaves the old registration in place or missing the job entirely. Even once the `Scheduled Job Type` record exists, nothing actually runs unless the *site's* scheduler is enabled (`bench --site <site> scheduler enable`/`resume`, or Desk's System Settings) — a disabled scheduler silently no-ops every registered job, not just newly-added ones. Any change to `scheduler_events` (new job, changed cron, removed job) needs both a `bench migrate` and a scheduler-enabled check confirmed after deploy, not just after the first time the feature is added.
- **A `doc_events` handler (or any code that runs inside someone else's transaction) must not write rows it does not own.** A `frappe.db.set_value()` on another document takes a row lock held until the submitter commits, and a rollback of the submit would leave the write's intent queued for a change that never happened. Queue the write instead with `frappe.enqueue(..., enqueue_after_commit=True)` and a small job function that re-reads the rows. Do not use `frappe.db.after_commit.add()` for a write: the callback runs after the commit, so its own writes are not committed until some later commit.

## Permissions

- A Script Report needs the `report` permission type on its `ref_doctype` for every role that runs it (`frappe.has_permission(ref_doctype, "report")` in `desk/query_report.py`); the report's own `roles` list is not enough, and Administrator bypasses the check so the gap goes unnoticed. Add `"report": 1` to the doctype's permission row. Standard DocPerm rows re-sync from the JSON on `bench migrate`, but a doctype with Custom DocPerm rows (Role Permission Manager edits, or copies made by `add_permission`) uses only those and ignores the JSON.
- Default to the Role Permission Manager (exported as a fixture), not hardcoded permission checks, unless the rule is dynamic (e.g. "only the owning branch can see this").
- For dynamic rules, use a `permission_query_conditions` / `has_permission` hook in `hooks.py`, not ad-hoc checks scattered in controllers.

## Migrations

- Schema changes ship via the doctype JSON itself — `bench migrate` reconciles the DB schema from JSON automatically. You rarely hand-write DDL.
- Data migrations (backfills, renames, one-time fixes) go in `<app_name>/patches/<version>/<patch_name>.py`, registered in `patches.txt`. Patches must be idempotent — `bench migrate` can re-run on a site that partially applied one.
- Use `frappe.reload_doc(module, "doctype", "doctype_name")` inside a patch if it depends on a schema change from the same release.
- **`post_model_sync` patches run BEFORE fixtures are synced** (`frappe/migrate.py` order, Frappe 16.51 dev: pre-model-sync patches, `sync_all`, post-model-sync patches, `sync_jobs`, `sync_fixtures`, `sync_customizations`). A patch that needs a Custom Field or Property Setter that ships as a fixture finds it missing on the first migrate of a site; one that returns early then ("field not there yet") is recorded as done and never runs again. Create the field inside the patch from the fixture definition (`create_custom_fields`, see `patches/v0_0/backfill_sales_order_bosta_delivery_status.py`) instead of skipping. Recheck on any Frappe upgrade.
- A filter `["field", "is", "not set"]` on a `Currency`/`Float`/`Int` column matches `0` too (the column is NOT NULL and stores an unset value as 0), so it cannot find "never received" rows without also matching a real 0. Keep a separate timestamp or flag when the difference matters (`Bosta Shipment.shipment_fee_received_on`).

## Concurrency

- **RQ's `JobTimeoutException` (base `rq.timeouts.BaseTimeoutException`) subclasses `Exception`**, so a broad `except Exception` in a per-item or per-account sweep loop swallows the job timeout and logs it against whichever item was in flight. Put `except BaseTimeoutException: raise` before the `except Exception`. A MariaDB lock wait (1205) is a different thing: Frappe raises `frappe.QueryTimeoutError`, which is safe to retry a bounded number of times after rolling back to the savepoint (#478).

- `frappe.db.get_value(...)` followed by a separate `frappe.db.set_value(...)`/`doc.save()` is a **check-then-write race**, not an atomic guard — a concurrent writer can change the row between the read and the write, and the second writer's decision (made from the now-stale read) silently overwrites whatever the concurrent writer just committed. This is a real, observed bug class: `integrations/talabat/catalog_feedback.py`'s stale-job guard originally read a mapping's `last_sync_reference` and compared it in Python before writing, which a concurrent re-push (a fresh catalog submission moving the same mapping onto a new job) could race and lose silently. Where the actual guard condition can be expressed as a `WHERE` clause, make the mutation itself the atomic check: a single parameterized `frappe.db.sql("UPDATE ... SET ... WHERE name = %s AND <guard column> = %s", (...))`, then inspect `frappe.db._cursor.rowcount` (confirmed used the same way in Frappe core itself, e.g. `frappe/tests/classes/integration_test_case.py`) — `0` means some other writer already moved the row out from under the guard condition, `1` means this write's precondition genuinely held at the moment of the write, not just at some earlier read. A raw `frappe.db.sql()` UPDATE bypasses `Document` controller hooks entirely (same as `frappe.db.set_value()`) — deliberate for a pure system/background sync-state transition, not appropriate wherever `validate()`/child-table logic must run.
- A raw `frappe.db.sql()` UPDATE (unlike `frappe.db.set_value()`, which does this for you) **does not invalidate Frappe's document cache** — call `frappe.clear_document_cache(doctype, name)` yourself after a successful raw-SQL write, or a subsequent `frappe.get_cached_doc()` elsewhere in the same or a later request can return a pre-update copy of the row you just changed.
- A retry budget (e.g. "refresh the token and retry exactly once on a 401") must be scoped to the outer, caller-facing function and shared across every inner retry loop, not re-granted inside that inner loop — otherwise nested retries multiply the budget unexpectedly (an inner loop that itself retries N times could then spend the "one" refresh N times, once per inner attempt, if the budget lived inside the loop instead of outside it). Track the budget in a variable owned by the outer function and pass/share it into the inner loop instead of letting the inner loop initialize its own. See `ShopifyClient.execute()`'s `token_refresh_state` (`marketplace_integrations/integrations/shopify/client.py`) for a worked example: one 401-refresh budget shared across every throttle-backoff retry attempt within the same `execute()` call.
- Under MariaDB's `innodb_snapshot_isolation=ON`, a `FOR UPDATE` (or other locking) read that comes AFTER an earlier plain/consistent read in the *same transaction* can raise error 1020 (`ER_CHECKREAD`, surfaced by Frappe as `frappe.QueryDeadlockError`) if the locked row was committed after that earlier read established the transaction's read view — even when the earlier read was against a completely different table/row. MariaDB handles this the same way as a real deadlock: it rolls back the WHOLE transaction, which silently destroys any savepoint opened earlier in that same transaction, so a later `frappe.db.release_savepoint(...)`/`frappe.db.rollback(save_point=...)` call against that now-gone savepoint raises its own "SAVEPOINT does not exist" error. Retrying the locking read once (swallowing the 1020) does not fix this: the retry "succeeds" as its own fresh implicit transaction, but the *caller's* savepoint is still gone, so the caller's own bookkeeping blows up instead. Making the locking read the first statement *of the function that issues it* is not enough either (a lesson learned the hard way across #146's round-4 and round-5 review passes): MariaDB's read view is scoped to the WHOLE transaction, not to a function or a savepoint — a savepoint does not open a new read view, only `commit()`/`rollback()` does — so any earlier plain read anywhere else in the same still-open transaction (a caller's own setup reads before it ever reaches the locking function; a previous loop iteration's work; critically, **an HTTP client call counts too**, since an authenticated API client's `request()` typically re-reads its own connection/credentials doc — e.g. `NoonClient.request()`/`get_password()` reading the `Noon Connection`/`__Auth` row — on every single call) still establishes the transaction's read view ahead of the lock. The real fix is: **commit (or rollback) immediately before the lock, with nothing else — no read, no HTTP call, nothing — between that commit and the lock.** In practice this means the commit has to move to wherever the lock is actually about to run, not to some earlier "setup is done" point that looks safe but still has an HTTP call or another read in between; a lock-acquisition helper that commits as its own first statement (see `marketplace_integrations/integrations/noon/fulfillment.py::_lock_and_load_order()`) is a good way to guarantee this at every call site without each caller having to manage the commit placement by hand. Confirmed and fixed this way in `marketplace_integrations/integrations/noon/orders.py::import_order()`/`_import_order_isolated()`/`refresh_order()` and `marketplace_integrations/integrations/noon/fulfillment.py`'s `_lock_and_load_order()`/`run_create_shipment()`/`run_mark_out_of_stock()`.
- `Document.save()` → `update_children()` re-syncs EVERY `Table`/`Table MultiSelect` field on a document on every single save, by DELETING any child-table row whose `name` is absent from the in-memory copy currently being saved for that exact `parentfield` (confirmed directly against the installed `frappe/model/document.py`). This is a real concurrency hazard for any child table that a background job/worker can write to concurrently with a request that merely reloads and re-saves the same parent for an unrelated reason: if process A loads the parent (snapshotting today's child rows in memory), process B then inserts/commits a new child row via its own `append()`/`save()`, and process A's own later `save()` still runs — A's stale in-memory copy doesn't include B's row, so A's save silently deletes it, with no error on either side. A locking read (`frappe.db.get_value(..., for_update=True)` or an explicit `FOR UPDATE` query) taken as the first statement against the parent row, on both sides, is the fix — it forces whichever writer runs second to block until the first commits and then observe its already-committed child rows before building its own in-memory copy to save. See the concurrency-hardening work in `marketplace_integrations/integrations/noon/orders.py`/`fulfillment.py` (Marketplace Order's `noon_shipments`/`noon_shipment_units`/`noon_shipment_awbs` child tables, written by both the order-import poller and fulfillment actions) for a worked example, plus the 1020/snapshot-isolation gotcha above for why the lock has to be the FIRST statement, not just present somewhere before the save.

- **Row-lock order for an order and its Delivery Note: Sales Order first, then Delivery Note, then Bins** (`order_edit.apply_edit`, `carrier_shipments._submit_created`). Read the order names, commit, then lock; a path that locks the note first and then the order can deadlock with Edit Order. A `frappe.get_all(..., filters={"field": ["not in", [...]]})` keeps rows whose column is NULL or empty (Frappe wraps the column in `ifnull`; `db_query.py` `prepare_filter_condition`, Frappe 16.51), so no explicit handling is needed.

- **Known exception to "no row lock across an external call":** `request_platform_cancel` (`services/marketplace_outbound.py`) sends the Shopify `orderCancel` and Talabat cancel calls while holding the Marketplace Order row lock (the lock is what stops two staff cancelling the same order twice); it commits before the lock and right after the platform call. After that commit the Shopify job poll (`poll_order_cancel_job`: up to 3 polls, 2 seconds apart, so sleeping up to about 4 seconds) runs inside the web request, without the lock. A platform that is slow to answer therefore holds the order row and the request worker for the call's duration. Do not copy this for new work; it is accepted here because the marker must be recorded atomically with the platform's acceptance.

- **`or_filters` as a list of dicts only uses the first key of each dict** (`frappe.model.db_query` `get_filter()` takes `next(iter(f.items()))`), so `{"sync_blocking_doctype": X, "sync_blocking_document": Y}` silently filters on the doctype only. Pass filter triplets (`["field", "=", value]`) and post-filter in Python when two fields must match together (`services/sales_order_recheck.py::linked_marketplace_orders`, #364).
- **`frappe.db.set_value()` on a document that is being saved is overwritten by that save**: `Document.save()` writes the whole in-memory row, so a debounce bump written with `set_value` from inside `before_save` (or while the caller holds an older copy that it saves afterwards) is lost. Set the values on the in-memory document instead (`sales_order_sync._queue_resync_in_memory`, #364), and treat a `doc_events` bump as safe only because the order being synced is skipped and re-saved from a fresh copy.
- An `erpnext` Sales Order that has submitted Delivery Notes (a delivery and its return) **cannot be cancelled** (`LinkExistsError` through `update_child_qty_rate`-independent cancel check, verified ERPNext 16.51.1 on `test.localhost`, #364): a returned, marketplace-cancelled order is closed, not cancelled. Submitting a return Delivery Note does reduce the Sales Order item `delivered_qty`.
- **A `before_cancel` hook that cancels other documents must refresh the document being cancelled.** `Document.cancel()` sets `docstatus = 2` in memory and saves that copy after `before_cancel`, so figures the hook changed in the database meanwhile (delivered and billed quantities and percentages from cancelling a Delivery Note or Sales Invoice, via ERPNext's status updater) are written back stale. `order_cancel_cascade._refresh_in_memory` copies the stored header and item-row values onto the document. Do not `reload()` it (that resets `docstatus`). Also: `before_cancel` runs before ERPNext's link check (`check_no_back_links_exist`, after `on_cancel`), so it is the place to cancel what would otherwise block; `carrier_shipments.cancel` commits, so a hook that calls it cannot roll back what it did earlier (design for a resumable second attempt); and a `frappe.db.commit()` inside such a hook breaks the savepoint of a caller that cancelled the order inside one (`sales_order_sync`), so commit only when there is something to cascade.
- **A `doc_events` hook on one document that must cancel another (Delivery Note cancel -> Sales Order cancel) queues a job** (`enqueue_after_commit`) instead of cancelling inside the first document's transaction: a block on the second must not undo the first, and the first's `on_cancel` runs before its own commit. The job runs as the system and must exit when the target is no longer submitted (the loop guard).

## Whitelisted / API methods

- Expose Python functions to the client with `@frappe.whitelist()`; add `allow_guest=True` only for genuinely public endpoints.
- Validate/authorize inside the whitelisted function — being whitelisted is not itself a permission check.
- `frappe.throw()` / `msgprint` text is rendered as HTML by Desk. Any text that comes from a platform (Shopify `userErrors`, job errors, Bosta/Talabat messages) must go through `frappe.utils.escape_html()` before it is thrown; store the raw text in logs, escape only the thrown message (`services/marketplace_outbound.py`, `integrations/shopify/orders.py::cancel_order`).
- Return plain dicts/lists (JSON-serializable); don't return `Document` objects directly from list endpoints.

## XLSX export/import

- `frappe.utils.xlsxutils.make_xlsx(data, sheet_name, ...)` runs `handle_html()` on **every string cell**, which silently html2text-converts any value containing `<`/`>` — UNLESS `sheet_name` is exactly `"Data Import Template"` or `"Data Export"` (a hard-coded exemption pair in the installed `xlsxutils.py`, confirmed by reading it directly rather than assuming from another Frappe version). This bites any custom export of an HTML-bearing field (e.g. a Text Editor field like Item's `description`): exporting under any other sheet name silently mangles that field's content on every export, which then makes a round-trip "export → re-upload unedited → should report unchanged" check fail permanently for any row with real HTML content, even though nothing was actually edited. Use `sheet_name="Data Export"` (or build the file with `make_xlsx()` directly instead of `build_xlsx_response()`, since the latter reuses its `filename` argument as both the download filename *and* the internal sheet name) to get the exemption while still controlling the user-facing download filename separately via `frappe.desk.utils.provide_binary_file()`.
- To reject a stale row during an XLSX-driven bulk update (an edit made to a record after it was exported, now about to be silently overwritten), don't hand-roll a full duplicate of Frappe's own optimistic-concurrency check. Export the record's real `modified` value as a plain string column (`cstr(doc.modified)`, not the raw `datetime` object — passing a raw `datetime` to `make_xlsx()`/`xlsxwriter` writes it as a native Excel date, which loses sub-millisecond precision on round-trip and can produce false "modified" mismatches). On write-back, load the record normally (`frappe.get_doc(...)`), set `doc.modified` to that string **before** calling `.save()`, and let Frappe's own `Document.check_if_latest()` (the exact mechanism the Desk UI already relies on for its "this document has been modified since you opened it" warning) raise `frappe.TimestampMismatchError` for you if the DB's actual `modified` has since moved on. A hand-rolled comparison against a freshly-fetched `modified` is still worth doing explicitly wherever the write itself doesn't happen yet (e.g. a preview/dry-run step that must not call `.save()` at all) — but treat that as a friendlier-message companion to the built-in check at write time, not a replacement for it.
- A hand-rolled preview/validation pass for an XLSX-driven bulk importer (mandatory-field checks, Link-target-exists checks) is inherently **best-effort, not a substitute for the target doctype's own `validate()`/`.insert()`/`.save()`.** It cannot and should not try to replicate every controller-side rule — e.g. `Item`'s stock_uom-vs-Bin check, barcode uniqueness/check-digit validation, any custom mandatory fields, HTML sanitization that can silently change the stored value, or side effects like `item_group` changes rewriting `item_defaults`. Don't keep adding hand-rolled checks to close this gap (that's the over-engineered direction). Document this plainly in a comment near the validation function instead: a row previewed as new/changed with no error can still be rejected, or stored with different sanitized values, once the real write actually runs — apply is the sole authority on whether a write succeeds and what gets persisted. Every future XLSX importer for a real ERPNext doctype inherits this same gap and should carry the same disclaimer rather than rediscovering it. (The Item and mapping workbooks that first showed this were retired by #373 in favor of native Item Data Import with `services/item_listing_import.py`; prefer a Data Import provider over a new workbook.)
- Bulk-write loops that process one row/record at a time and must isolate one row's failure from the rest (report it as an error, but don't let its partial writes stick, and don't lose already-committed prior rows) should wrap each row in its own DB savepoint, not rely on a full-transaction rollback: `frappe.db.savepoint(name)` before the row's write, `frappe.db.rollback(save_point=name)` in the `except`, `frappe.db.release_savepoint(name)` on success (confirmed directly in `frappe/database/database.py`). Note there are **two different things named `savepoint`** in that module: the instance method above, and a separate module-level `@contextmanager` function `savepoint(catch=...)` (`from frappe.database.database import savepoint`) that wraps a `with` block and *silently swallows* any exception matching `catch` after rolling back — useful when you don't need the exception's message (e.g. `frappe/email/doctype/email_queue/email_queue.py`'s `@savepoint(catch=Exception)` decorator), but wrong for a bulk-import loop that needs to report *which* error happened per row: use the three-call instance-method form there instead so the exception is still visible to your own `except`.
- A logged-in ("Desk User"-having) user can end up with an **implicit `select` permission on a doctype they have zero explicit read/write/create permission on**, purely because some *other* role than the ones assigned to them has a `select: 1` DocPerm row on that doctype and Frappe's default "Desk User" role itself frequently carries `select: 1` on common doctypes (e.g. `Item` — confirmed directly against this site's `DocPerm` rows) so that ordinary Link-field lookups still work app-wide. `frappe.only_has_select_perm()` / `frappe.has_permission(doctype, "select")` returning `True` here means `frappe.get_list()` on that doctype **will still run and return full field data** for that user (permission is checked at the query-execution level via `DatabaseQuery.check_read_permission()` downgrading the required ptype to `"select"`, not by restricting which fields come back) even though `frappe.has_permission(doctype, "read")` correctly returns `False`. Don't assume "a user with no explicit role permission on doctype X" means `frappe.get_list("X", ...)` returns nothing for them — write/create-permission checks (which are *not* satisfiable by `select`) are the reliable gate to test against for "this user shouldn't be able to touch X" scenarios, not the visibility of a `get_list()` read. **Exception:** the four row-filtered doctypes (Marketplace Account, Order, Product Mapping, Sync Log, #322) have a `permission_query_conditions` hook, which `get_list` always applies: a user without a platform role gets `1=0` (strict row filtering), so this select-only leak does not apply to them.

- **Doc-less `frappe.has_permission(doctype, ptype)` never calls the `has_permission` hook** - only document-level checks (`doc=` or `doc.check_permission()`) run it. A hook that filters rows (such as the platform filtering in `permissions.py`) therefore does not restrict a doctype-level check: any user holding the role passes it. Endpoints that need row- or connection-level authorization must check against a document (`frappe.has_permission(doctype, ptype, doc=name, throw=True)`). `permission_query_conditions` applies to `get_list` but not to `get_all`, `frappe.db.*` or raw queries.

## Timestamps / timezones

- A child row appended to a parent (`parent.append("child_table", {...})` then `parent.save()`) with no `creation` of its own **inherits the PARENT's `creation`** (`Document.set_user_and_timestamp` in `frappe/model/document.py` copies `self.creation` onto any child without one). So a row's `creation` is not its own insert time. Anything that ages a child row by `creation` (e.g. the #164 stuck-Pending shipment check) must set `"creation": now_datetime()` explicitly in the appended dict, or use a dedicated timestamp field.
- `frappe.utils.get_datetime_str(datetime_obj)` **only formats a `datetime`'s own wall-clock fields — it never converts timezones**, even when the object it's given is timezone-aware. Confirmed directly against the installed `frappe/utils/data.py`: `get_datetime_str()` is a bare `datetime_obj.strftime(DATETIME_FORMAT)`. This is a real trap when parsing an external API's UTC timestamps (e.g. an ISO 8601 string with a trailing `Z`, like Talabat's `order.Order` payloads): `frappe.utils.get_datetime("2026-08-31T12:00:00Z")` correctly parses it into a UTC-*aware* `datetime` (Python's `datetime.fromisoformat`, which `get_datetime()` tries first, recognizes the `Z` suffix since 3.11) — but piping that straight into `get_datetime_str()` just restrings the same `12:00:00` digits, silently storing them as though they were already the site's local wall-clock time instead of UTC. Convert first with `frappe.utils.convert_utc_to_system_timezone(dt)` (shifts the wall-clock fields to `frappe.utils.get_system_timezone()`, i.e. System Settings → Time Zone) and only then call `get_datetime_str()` on the result. When writing a test for this, patch `frappe.utils.data.get_system_timezone` directly (e.g. to a fixed-offset, no-DST zone like `Asia/Kolkata`, or to `"UTC"` for an identity case) rather than relying on whatever the current site's System Settings happens to be — that keeps the assertion's expected value deterministic and independent of environment.

- **`datetime.astimezone(UTC)` on a naive datetime assumes the SERVER PROCESS zone, not System Settings.** `now_datetime()` and every Datetime field hold naive wall-clock values in the System Settings time zone, so `get_datetime(value).astimezone(UTC)` is only right when the server zone happens to equal the site zone (it did in dev containers on UTC and was off by the site offset otherwise). To send such a value to an API as UTC, attach the site zone first: `value.replace(tzinfo=ZoneInfo(frappe.utils.data.get_system_timezone())).astimezone(UTC)` (call it through the module so a test can patch `frappe.utils.data.get_system_timezone`). `integrations/shopify/orders.py::_as_shopify_timestamp` is the worked example (found with the Shopify "Sync Orders From" cutoff).

## Decimal formatting for external payloads

- A Python `Decimal`'s default string form (`str(decimal_value)`, and therefore any f-string/`.format()` interpolation of it) can render in **scientific/exponential notation** for very small or very precisely-scaled values (e.g. `Decimal("0.0000001")` stringifies as `"1E-7"`) — this is standard `Decimal.__str__` behavior, not a bug, but it silently breaks any external API field that expects a plain fixed-point numeric string and has no idea what `E-7` notation means (e.g. Shopify's GraphQL Admin API `Money` scalar, sent as a JSON string in `marketplace_integrations/integrations/shopify/catalog_push.py`'s `_format_money()`). Use `format(decimal_value, "f")` instead — the `f` presentation type forces fixed-point notation regardless of the value's magnitude/exponent, with no scientific-notation fallback. This applies to any `Decimal` serialized into a string-typed external field, not just this one Shopify case.

## Client scripts

- App-shipped JS lives next to the doctype (`<doctype_name>.js`) and ships with the app.
- JS for a doctype the app does not own (e.g. `Sales Order`) cannot sit next to the doctype: ship it as `public/js/<name>.js` and register it in `hooks.py` with `doctype_js = {"Sales Order": "public/js/sales_order.js"}`. The file runs as the doctype's client script (`frappe.ui.form.on(...)`), is read server-side into the form meta (`frappe/desk/form/meta.py::add_code_via_hook`), and that form meta is cached except in developer mode; `bench migrate` clears it. Core doctypes' own JS (ERPNext's `frm.cscript` controller) has no hooks for every action (e.g. Close on Sales Order has none): wrap the method (`frm.cscript.<method>`) once per form with an own-property wrapper that sets a flag, act on the next `refresh`, and clear the flag on every refresh. Scope the flag to the document (store `frm.doc.name`, not `true`) so a stale flag cannot prompt on a different document; a failed action leaves it set until the next refresh, and someone else performing the same action while it is set is an accepted residual case. Add an always-on Python test that reads the framework's JS (`frappe.get_app_path("erpnext", ...)`) and asserts the method and its call sites still exist, so an upgrade removing it is noticed. Wrap the file in an IIFE: `doctype_js` files share one scope with the core script. Do not call a whitelisted method the user may lack permission for from a form event: a failed permission check shows Frappe's "Not permitted" popup and re-routes regardless of any `.catch`, so gate with `frappe.model.can_read(...)` first. See `sales_order.js` (#183).
- Site-specific tweaks that shouldn't live in app code go in the **Client Script** doctype in the UI, then exported as a `fixtures` entry — don't hand-edit those JSON exports.
- A `frappe.ui.form.make_control()` Link control with no backing Frappe document has no model to update asynchronously — call `set_input()` to render a server-returned value directly, not `set_value()` (which updates the model async and leaves the input blank since there's no document for it to attach to).
- Frappe's Link control only fires the DOM `change` event on blur, not when a suggestion is picked from the awesomplete dropdown — bind `awesomplete-selectcomplete` too if you need to react to the pick immediately, or the UI will appear to do nothing until the user clicks elsewhere.
- A page-field (`page.add_field()`) Link control's `change` handler fires **twice** per pick: once on the programmatic selection, once again on the following native blur. Guard against double-firing (e.g. compare against a "current value" variable) if the handler does something expensive like refetching data.
- `frappe.DataTable` is bundled only with the report/web-form JS bundles — it is not available on a plain Desk page (`frappe.pages`). Build custom tabular UI there with plain DOM + `frappe.ui.form.make_control()` instead, or use `frappe.require()` to explicitly pull in whatever bundle actually contains it.
- Frappe renders several things as raw HTML client-side: Awesomplete/Autocomplete option labels (`.html()` in `controls/autocomplete.js`), `frappe.toast`/`frappe.show_alert` messages, and `set_disp_area()` (defined in `controls/base_input.js`, inherited by every text-ish control) for any fieldtype outside its escape whitelist (`Data`, `Long Text`, `Small Text`, `Text`, `Password`, `MultiSelect` — notably NOT `Autocomplete` or `Select`). Any value sourced from an `ignore_xss_filter` field or an external API must be run through `frappe.utils.escape_html()` at the point of interpolation into any of these — the field-level `ignore_xss_filter`/server-side sanitizer does not protect client-side rendering. For an Autocomplete field specifically, pass a df-level `formatter: (value) => frappe.utils.escape_html(value)` to escape the *display* value without touching the raw `value` a `set_value()` call needs.
- A **read-only `JSON`-fieldtype field is not covered by `set_disp_area()`'s escape whitelist either**, and — unlike `Autocomplete`/`Select` above — it has no dedicated entry in `frappe.form.formatters` at all: `frappe.form.get_formatter("JSON")` (`frappe/public/js/frappe/form/formatters.js`) falls back to `frappe.form.formatters.Data`, which returns the raw value completely unescaped, and that string is then inserted via jQuery `.html()`. Only a small fixed set of tags (`script`/`style`/`noscript`/`title`/`meta`/`base`/`head`/`link`) is stripped afterwards by `frappe.dom.remove_script_and_style()` — confirmed directly against the installed framework, not assumed — so a stored value containing e.g. `<img src=x onerror=...>` survives that strip and executes. `ignore_xss_filter: 1` (needed anyway to stop the server-side sanitizer from corrupting the field's bytes, see above) does nothing to protect this client-side render path. To render a specific JSON field safely, set a `formatter` **on the doctype's cached meta docfield itself** (`frappe.meta.docfield_map[doctype][fieldname].formatter = (value) => value ? `<pre>${frappe.utils.escape_html(value)}</pre>` : ""`), done once at the doctype's client-script top level — never inside a `refresh` form-event handler, which fires too late: `Form.refresh()` always calls `refresh_fields()` (which renders using whatever formatter is registered *at that moment*) before it fires `script_manager.trigger("refresh")`, so a `df.formatter` set inside `refresh(frm)` only takes effect starting from the *next* refresh, after the field has already rendered once unescaped. `frappe.form.formatters.Data`'s own `_apply_custom_formatter()` always re-reads `frappe.meta.docfield_map[doctype][fieldname].formatter` fresh, by name, on every render — not a value captured once at control-creation time — so registering it once, at module/script-load time (which Frappe guarantees runs only after that doctype's own meta is already fetched and cached), reliably covers every render of that field for the rest of the session. See `marketplace_order.js`'s `render_json_evidence_fields_as_escaped_text()` (#108) for the reference shape; also worth knowing (flagged but explicitly left unfixed by #108, since it predates that issue and its own fix belongs to a separate change) that this same gap already affects Talabat's own JSON fields on `Marketplace Order`/`Marketplace Order Item` (`latest_payload`, `discounts`, `additional_fees`, `promotions`, `barcodes`), none of which have this escaping applied yet. Registering it once at script-load time is not actually sufficient on its own, though: `frappe.meta.sync()` can reload/replace a doctype's cached field objects wholesale later in the same session (e.g. after a metadata refresh), which silently drops whatever formatter was attached to the old object — re-apply the same registration from an `onload` form-event handler too (which Frappe guarantees runs before that form instance's own `refresh_fields()` call, unlike `refresh`), so it's re-asserted idempotently on every form load rather than trusting the one script-load-time registration to survive for the rest of the session. Neither the script-load nor the `onload` registration reaches **Report View**, though: that renderer doesn't go through `frappe.form.formatters` at all, so a report built against one of these fields before any form of that doctype was ever opened in the session is not covered by this technique — don't claim "every render" is covered in a comment/doc near this fix; say Report View explicitly remains a gap (tracked as its own issue, not fixed as a side effect of the form-level fix).
- A **JSON-fieldtype** field's value on `frm.doc` (including inside a child-table row) is the **raw JSON string exactly as stored in the DB column, never pre-parsed into a JS array/object** by the framework. Confirmed directly against the installed framework: server-side, `Document.get_valid_dict()` (`frappe/model/base_document.py`) only serializes a Python `dict` *into* a JSON string on write (`json.dumps(value, ...)` when `fieldtype == "JSON" and isinstance(value, dict)`) — there is no corresponding reverse parse anywhere in `load_from_db()` when reading a document back out, and the client-side `ControlJSON` (`frappe/public/js/frappe/form/controls/json.js`) is just a `ControlCode` variant (an Ace/vscode-mode code editor for hand-editing the raw text), not a value transformer. The desk's `getdoc`/form-load payload is `JSON.stringify`'d once for the whole document; a JSON field's own string value survives that single outer parse as a string, not a nested object. Still write defensive client code rather than relying on this being permanent framework behavior across versions: check `Array.isArray(value)` first, only `JSON.parse()` a plain string, and treat a parse failure or any other shape as an empty/absent value rather than throwing. `marketplace_order.js`'s `parse_promotions()` (#84) is the reference shape.
- A global defined by a script loaded with `frappe.require()` (e.g. `frappe.ui.ShopifyCatalogPushStatus.INVENTORY_OPTIONS` from `shopify_catalog_push_status.js`) does not exist until that `frappe.require()` promise resolves. Reading it at the call site before the require (e.g. when building arguments for the call that will open the dialog) throws `Cannot read properties of undefined` on a fresh page load, while a test whose global mock already pre-sets it still passes. Read such globals inside the `.then()` callback of the `frappe.require()` that loads them, and have the test simulate the fresh load by having its `require()` mock define the global.
- A `frappe.call()` rejection (the `xhr` object) carries the server's own message as `error.responseJSON._server_messages`, which is a JSON array of JSON strings, each with a `message` (parse twice). The message is HTML-ish: decode entities and strip tags before showing it, and escape it again at render time. `error.message` is usually empty for these.
- **`silent: true` does not silence a 404 or 403.** `frappe.request.call` opens a modal ("Not found" / "Not permitted") for every HTTP 404 (`DoesNotExistError`, e.g. `frappe.has_permission(doc=<missing name>, throw=True)`) and for most 403s, whatever `silent` says; `silent` only skips the `_server_messages` dialog. A 417 (`frappe.ValidationError` / `frappe.throw`) is left entirely to the caller. For a background-style widget (hover card, inline panel) that must show its own error, check `frappe.db.exists` first and `frappe.throw` a plain message (`api/order_hover_card.py`). Verified Frappe 16.51.0 dev (`public/js/frappe/request.js` `statusCode` map).
- `RemoteDataGrid.go(page)` renders "No Data" for any page with zero rows. After a save removes the last row of the current page, re-render with `go(page - 1)` (repeating until a page has rows, then page 1) instead of `go(page)`. Probe each earlier page with `fetch_page()` before calling `go()` on it, so the grid never renders an empty page. This is the Talabat/Noon/Shopify Needs Mapping grid in `marketplace_products.js`.
- A `doctype_list_js` file for a doctype the app does not own (e.g. `Sales Order`, whose ERPNext list script already assigns `frappe.listview_settings["Sales Order"]`) is evaluated after the core list script, so assigning the whole settings object would replace ERPNext's indicators and hooks. Add to the existing object and wrap `onload` (call the original first), with a flag so a re-evaluation does not wrap twice. To reuse a `doctype_js` form script's code from the list, `frappe.require()` its `/assets/<app>/js/<file>.js` and export what the list needs on a `frappe.<app>` namespace; `frappe.ui.form.on` handlers are global and never reset, so guard the registration with a flag on `frappe.ui.form` or the form handlers run twice when both the list and the form load the file (#305, `sales_order_list.js` / `sales_order.js`).

- A Workspace **DocType shortcut's `stats_filter`** (a JSON object/array string on the `Workspace Shortcut` row) does two things, confirmed against the installed `shortcut_widget.js`: it becomes `frappe.route_options` when the shortcut is clicked (so it opens the list already filtered, e.g. `{"platform": "Talabat"}`), and it is the filter for the count badge Frappe shows on every DocType shortcut anyway. It is the way to ship per-platform/per-status list shortcuts in a workspace JSON without a Report.
- **A shortcut with no `stats_filter` is not "unfiltered".** `list_view.js` restores the last-used filters from User Settings whenever the list opens with no `route_options`, so a plain DocType shortcut reopens whatever filter the user last left on that list (e.g. a generic "Orders" shortcut opened Noon-only after visiting the Noon shortcut). Route options *replace* saved filters, but only when they parse to at least one filter. To force "show all", give the shortcut a neutral always-true `stats_filter` such as `{"name": ["like", "%"]}` (also keeps the count badge = total). Plain shortcuts to lists nobody else filters via shortcuts just show the user's own last filters, which is normal Frappe behavior.
- **Desktop Icon tile (app grid / sidebar header):** the tile image is chosen by `frappe.utils.get_desktop_icon` (and `desktop_icon.html`): first an SVG at `<app>/public/icons/desktop_icons/{solid,subtle}/<scrub(label)>.svg` (scanned by `boot.get_desktop_icon_urls`), else `logo_url`/`icon_image`, else a letter tile (first letter of the label, `bg_color` gray unless set to `blue`). The Desktop Icon's `icon` field does NOT draw the grid tile, so a Desktop Icon with only `icon` shows a grey letter. Ship both `solid` and `subtle` SVGs named after the label. The `icon`/`header_icon` fields on Workspace/Workspace Sidebar must be a real sprite id (Lucide `icon-<name>` such as `store`, or a timeless one such as `sell`); an unknown name like `shop` renders nothing. Standard Desktop Icon/Workspace/Workspace Sidebar JSON are re-synced on migrate only if the file's `modified` is newer than the DB row's, so bump `modified` when editing them.
- A whitelisted sync endpoint that reports an *expected* blocker as a returned `{ok: false, error}` (e.g. `api/marketplace_orders.py::sync_to_erpnext` -> `sync_sales_order()`) resolves the `frappe.call()` promise successfully. Bulk or "retry" UI built on `Promise.allSettled`/`.then()` must check `ok === false` on a fulfilled result, not only handle rejections, or blockers are reported as successes.

## Gotchas found in the Bosta Delivery Note work (epic #413)

- **Deleting a Custom Field leaves its column.** `frappe.delete_doc("Custom Field", ...)` removes the field but not the DB column (and not its Property Setters); a retiring patch drops the column itself (`alter table ... drop column`, guarded by `has_column`) and deletes the Property Setters for the field.
- **A Currency or Float cannot tell "never set" from 0** (unset is stored as 0), so "was this amount ever chosen" needs its own marker (a Check field), not a NULL trick. A `validate` that must keep a person's choice but refresh a default compares the posted value with `doc.get_doc_before_save()` and ticks the marker when they differ.
- **A background write of an unrelated field makes the open form stale.** `doc.db_set(..., update_modified=True)` / `frappe.db.set_value` bump `modified`, and the native submit that follows fails with "modified after you opened it". Writes the person did not make and need not see (an attached label, a carrier status on a draft) use `update_modified=False` (with `notify=True` an open form still refreshes); `update_modified=True` on a draft note is only right when the form must be reloaded first (the shipping script reloads before the native submit). `update_modified=False` is not the whole fix: a form copy loaded before the write still carries the old value, and a plain save posts it back. For fields only the app writes, restore the stored values in `validate` (`doc.set(f, doc.get_doc_before_save().get(f))`) instead of refusing the save or trusting the posted copy; do the same for a field on another doctype that the app summarises (Sales Order `custom_shipping_status_summary`).
- **Compare and write inside one lock.** A helper that commits at its start (to take a `for_update` lock as the next statement) releases the lock when it commits again; read the value you compare, and write it, between the lock and the next commit (`statuses._write_state`). A check done before the lock is a stale view.
- **Store untrusted text raw, escape once where it is rendered.** Escaping on write double-escapes in a report that escapes again and cannot be undone. Give a read-only Small Text that holds carrier text `ignore_xss_filter` so a later `doc.save()` does not rewrite it. `frappe.throw`/`msgprint`/`show_alert`/`set_intro` render HTML: escape the carrier text you pass them.
- **Never base a rule on counting Integration Request (or other log) rows:** Log Settings deletes them after 90 days. Keep the decision on a durable field of the document (`custom_carrier_reference`).
- `remove_orphan_doctypes` and the post-model-sync order: see `docs/frappe-best-practices.md`, Version compatibility.
- `make_sales_return` copies native `lr_no`/`lr_date` to the return note. Any lookup by tracking number must filter `is_return: 0`, and an auto-made return should clear them.
- A form `before_cancel` that calls an app endpoint which writes the note (bumping `modified`) must reload the doc before resolving, else the native cancel fails with "modified after you opened it". `frappe.validated = false` stops the cancel; delete has no client hook, so guard `on_trash` on the server.
- **A pre-check that mimics the native cancel must use the same `ignore_linked_doctypes`.** `Document.check_no_back_links_exist` honours `doc.ignore_linked_doctypes`; ERPNext's `DeliveryNote.on_cancel` sets it (GL Entry, Stock Ledger Entry, Repost Item Valuation, Serial and Batch Bundle) and cancels Packing Slips first. A pre-check run before `cancel()` without that list sees its own stock/GL rows as blocking links (`carrier_shipments.NATIVE_CANCEL_IGNORED_LINKS`).
- **Auto-cancel only on the transition you caused to be observed.** A status read may auto-cancel the note only when this read moved the status into Cancelled (or retries a Cancelled note that has a blocking error), never when the app's own cancel just wrote Cancelled. Never `frappe.set_user("Administrator")` inside a request: enqueue the cancel as a short job (`deduplicate=True` per note, `enqueue_after_commit=True`); the job runs as Administrator and keeps the race and idempotency guards.
- **ERPNext invoice cancel silently unlinks Payment Entries** when Accounts Settings "Unlink Payment on Cancellation of Invoice" is on (the default), leaving the money unallocated, so check payments explicitly (and that `outstanding_amount` equals the total) before cancelling an invoice from code.
- A contract hook that must run for notes no adapter owns (a person setting an app-only value) is `guard_always(doc)` on the adapter, called from `validate_delivery_note` for every adapter.
- A File shared by content hash: deleting one File row removes the disk file only if no other row has the same `content_hash`, so removing a loose upload after attaching a copy is safe; compare `saved.name != file_doc.name`, not `file_url`.
- **Workflow gotchas (#498, Frappe 16.52.0 dev).** (1) `before_workflow_action`/`after_workflow_action` are client form events only; the server has no such hook (use transition tasks, `workflow_methods` in hooks.py: sync tasks run inside the transition transaction, async ones are enqueued after commit as the pressing user). `frm.selected_workflow_action` is already null in `after_workflow_action`, so remember it in `before_`. (2) A Workflow state's `allow_edit` is enforced by the browser only; a direct API save is limited only by `validate_workflow` (a transition must exist from the stored state), so lock the field server-side if it matters. (3) Saving a Workflow fills empty `workflow_state` of the first state only for new docs; a new doc whose state is not the first state throws in `validate_workflow`, and existing rows need an explicit backfill BEFORE the Workflow is activated. (4) Submit/cancel puts the document in the FIRST state with the matching docstatus (`set_workflow_state_on_action`); a state's docstatus must match the document's or Frappe overwrites it. (5) `db_set`/`set_value` write no hooks, so a status written that way must write the stage in the same call. (6) A stale open form that carries an old stage is refused by `validate_workflow` ("transition not allowed"), not by the timestamp check, when a background write changed the stage without bumping `modified`. (7) Workflow Transition Tasks are named by their prompt/label; `Workflow State` names with a slash ("Returned / Failed") are accepted. (8) Post-model-sync patches run before fixtures, so a patch that backfills a Custom Field must create the field itself.
- Tests: do not name a mixin helper `_created`; `BostaFixtureMixin` keeps its tracked-docs list in `self._created`.
- To change a field of a submitted document (`allow_on_submit`) from a `doc_events` handler, assign it in `before_update_after_submit` (or `validate` for a Draft) so the same save writes it. Do not use `db_set` in `on_update_after_submit`: Frappe 16.52 runs `save_version` after `on_update_after_submit`, so the Version row is written anyway. The controller method runs before the `doc_events` handler, so ERPNext's own derived values (such as the Sales Order header `delivery_date`) are already final. "Update Items" (`update_child_qty_rate`) saves the child rows first, reloads the parent and saves it, so a before/after comparison of child rows sees no change; compare against the stored parent value instead.


## Customer phone lookup

- **`Customer.mobile_no` is Read Only and fetched from the primary Contact, but ERPNext also `db_set`s it exactly as typed when it creates that Contact on insert** (`create_primary_contact`), so the stored format varies (`+20 106-945 2847`, `01069452847`, ...). Never match it with `=`; clean both sides with `clean_phone_number()` and compare the full cleaned number in Python after a LIKE pre-filter with the last 7 digits in order (`%4%5%2%8%4%7%`; stored values may lack the country code, so do not build it from the full number). A Customer whose phone lives only on a Contact has no `mobile_no`. Free-text buyer phones must go through `services/phone_numbers.py::clean_phone_number()` before they are stored or matched (Frappe's phone pattern is digits and `+ - _ , . * # ( )` and space, at most 20 characters; the cleaner outputs only an optional `+` and ASCII digits 0-9, 7 to 15 of them, at most 16 characters; use explicit `[0-9]` classes, not `str.isdigit()`/`\d`, which accept superscripts and other scripts). Creation retries once without the phone if ERPNext still rejects it. In a savepoint helper re-raise transient errors (`is_transient_failure()`) and roll back with the `_rollback_*_savepoint()` pattern (ignore only "SAVEPOINT" errors). `get_all` defaults to 20 rows: pass `limit_page_length=0` when Python does the exact check.

## Translations

- A translation CSV goes at `<app>/<app_python_package>/translations/<lang>.csv` — directly under the app's Python package root, confirmed against `frappe.get_app_path(app, "translations")` (`frappe/translate.py`'s `get_translations_from_csv()`), which resolves to `apps/<app>/<app>/translations/`. This is **not** module-scoped the way `doctype/`, `report/` and `page/` are: a doctype/report/page lives under `<app>/<app>/<module_folder>/...` (e.g. `marketplace_integrations/marketplace_integrations/marketplace_integrations/report/...`, doubly nested here only because the one module happens to be named the same as the app), but `translations/` is a single app-wide folder one level up from that, at `<app>/<app>/translations/`. Putting the CSV inside the module folder by analogy with doctype/report/page (an easy mistake to make in an app with just one same-named module) means Frappe never finds it — no error, the language silently falls back to showing the untranslated source strings. No header row; each row is `source_text,translated_text` (optionally `,context` as a third column) with standard CSV quoting/escaping for embedded commas; `frappe.get_all_translations(lang)` (requires a dedicated client-side `bench console` call to force-refresh, since it's cached under `frappe.cache`'s `merged_translations` hash) is the quickest way to confirm a specific source string resolves before trusting the Desk UI.
- Frappe wraps workspace header/shortcut text in `__()` **against the plain visible text, not the raw HTML the block stores** — confirmed in `frappe/public/js/frappe/views/workspace/blocks/header.js`'s `set data()`: it calls `__(this._data.text)` once (a near-certain no-op, since the literal source string there is the full `<span class="h4"><b>...</b></span>` wrapper, which no translation CSV would ever match), then separately extracts the block's plain `innerText` and does `text.replace(only_text, __(only_text))` — it's this second, plain-text-only call whose result actually lands in the rendered output. A workspace shortcut's label goes through the same plain-text path via `base_widget.js`'s `set_title()` (`__(title)`). This means a translation CSV only ever needs the **plain inner text** of a workspace header (e.g. `"Tamwenat Marketplaces"`, not `"<span...>Tamwenat Marketplaces</span>"`) and the exact shortcut `label` string from the Workspace JSON — never the HTML.

- **Every user-facing string ships with its Arabic translation in the same PR.** Any new or reworded text a user can see — `_()`/`__()` messages, errors, confirmations, button and field labels, field descriptions, Select options, report/page/workspace labels — needs a matching row in `marketplace_integrations/translations/ar.csv`. A reworded string is a new source key: add its row and delete the stale row for the old wording. Keep `{0}`-style placeholders (including `{1!r}`) identical and in meaning order, and keep product/API names (Shopify, Noon, Bosta, Talabat, ERPNext, SKU, AWB, GID, Webhook) in Latin script. Reuse the terms already in `ar.csv` (e.g. Sales Order = أمر البيع, Marketplace Order = طلب السوق, mapping = ربط, Delivery Note = مذكرة التسليم, Credit Note = إشعار دائن, Payment Entry = قيد الدفع). Check coverage with `bench --site <site> get-untranslated --app marketplace_integrations ar /tmp/untranslated.txt` inside the dev bench; it must report only the known exception below. Write rows with a real CSV writer (Python `csv`), not by hand, so commas and quotes are escaped.
- **A source string containing a literal backslash-n (`\n`) cannot be translated through the CSV:** `get_translation_dict_from_file()` replaces `\n` with a real newline in both columns, so the key never matches. `get-untranslated` also prints it with `||||` in place of `\n`. Known case: the Noon Connection private-key description. Leave it untranslated, or reword the source without `\n`.

## App-level folders auto-synced by `bench migrate`

- **Sidebar (Frappe 16.51+):** an app ships a navigation sidebar as a standard `Sidebar` document at `<app>/<module folder>/sidebar/<name>/<name>.json` (module-rooted; `<app>/sidebar/<name>/<name>.json` if it has no module), synced on migrate like `doctype/`, `report/`. The old `<app>/workspace_sidebar/*.json` (`Workspace Sidebar`) is NOT imported any more. Keys: `doctype: Sidebar`, `name` = `title`, `module`, `app`, `standard: 1`, `header_icon`, `items` (Sidebar Item: `type` Link/Section Break/Spacer, `label`, `link_type`, `link_to`, `icon`, `child`, `indent`, `collapsible`, `keep_closed`, `filters`, `is_default_module`, ...). A filtered list link uses `filters` (a JSON list `[[doctype, field, "=", value]]`), not `route_options`: `filters` is part of the item identity and linked rows that differ only by `route_options` are silently collapsed. A standard row with no file is deleted as an orphan on migrate. A site upgraded from the old format already has a converted non-standard row with the same name; the file replaces it only if its `modified` is newer.
- **Dock + Sidebar shells (16.51+):** an app ships a Dock at `<app package>/dock/<app>/<app>.json` (`standard: 1`, `mount_on` the host app, e.g. `erpnext`; every row needs `icon` + `title`). Its rows are appended after the host's rows; a saved site/user Dock layer for the host drops entries it does not name. Dock shells (rows with `link_type: Sidebar`) are resolved with `resolve_sidebar(shell, user)`. Permission filtering: an empty Section Break survives (a section header with no permitted item stays visible, so give every role at least one item per section), and a Sidebar with no permitted item is dropped. One `module` per shell: Frappe resolves a Workspace route to the first Sidebar whose module lists that workspace (`workspaces` is per module in `resolve_sidebar`; `module_for_workspace` in `sidebar.js`), so two shells under one module make the first one win when the other's landing item is a workspace (the Marketplaces Dock icon opened the Bosta shell, #326). Give each shell its own Module Def (add it to `modules.txt` with a folder holding `sidebar/<name>/<name>.json`; migrate creates the Module Def via `sync_module_defs`, but NOT on the same run does it import the new folder: `sync_for` walks the module map cached in redis (`app_modules`, built from the old `modules.txt`), so the new module's files are skipped, and an existing row of the same name keeps its old `module`. Adding a module to `modules.txt` needs an idempotent `post_model_sync` patch that runs `frappe.cache.delete_value("app_modules")`, `frappe.setup_module_map()` and `frappe.modules.import_file.import_file_by_path(<file>, force=True)`; see `patches/v0_0/import_bosta_module_sidebar.py`, #326). Shells under one module also share Custom Sidebar module layers.
- That importer decides whether to reimport a file by comparing its `modified` timestamp against the DB row's (falling back to a content hash for DocType records). A Sidebar (or any other synced) JSON that's missing `creation`/`modified`/`modified_by`/`owner`/`docstatus`/`idx` gets treated as always-newer-than-DB, so every `bench migrate` deletes and reimports it — harmless functionally, but noisy and worth avoiding. Give it real timestamps and the standard Frappe document metadata fields, matching the format Frappe/ERPNext use for their own shipped fixtures (e.g. `erpnext/erpnext/stock/sidebar/stock/stock.json`). This cuts both ways once a real `modified` is in place: `is_db_timestamp_latest` treats an unchanged-or-older `modified` as not-newer-than-DB and **silently skips the import**, so any future hand-edit to the JSON must also bump `modified` (to a value newer than what's already in the DB on every site that has previously imported it) or the edit will appear to do nothing on `bench migrate`.

## Linting

- **`ruff` (pinned 0.14.10 in this repo's CI/pre-commit) does not raise a syntax error for Python-2-style `except A, B:`** (the old "catch `A`, bind the exception to a variable named `B`" syntax, removed in Python 3) — confirmed directly: a file containing it passes `ruff check` with "All checks passed!" while `python3 -m py_compile`/`ast.parse()` on the exact same file raises a hard `SyntaxError` at that line. This is a real, observed incident, not a hypothetical: `except TypeError, ValueError:` (meant as `except (TypeError, ValueError):`) was introduced by un-parenthesizing a previously-correct exception tuple, across 4 separate commits between 2026-10-06 and 2026-10-13 (`2ad8174`, `960dce8`, `5e44438`, `b90f515` — verified via `git log -S`), landing 14 occurrences across 7 files (`integrations/bosta/labels.py`, `integrations/bosta/statuses.py`, `integrations/noon/fulfillment.py`, `integrations/shopify/order_reconciliation.py`, `integrations/shopify/orders.py`, `services/marketplace_attention.py`, `services/sales_order_sync.py`) that sat merged on `dev` for 11 days before being fixed in `cb5f735`. An 8th instance (`order_mapper.py`) was caught independently on a separate branch before it ever merged. Every one of those modules was unimportable on the real site (any `import` of them, or anything importing them transitively, raised `SyntaxError` immediately), yet Stage 1 CI's `ruff check .` passed every time — at the time, that was this repo's only syntax-adjacent automated check. CI now also gates this with a `python -m compileall` step added specifically because of this incident (Stage 1 step 3; see `docs/ci.md`'s "Ruff does not catch every SyntaxError" for the CI-side account — this section is the incident narrative, that one is the gate). Don't treat a clean `ruff check` (or a clean `compileall`) as proof a file is bug-free — for anything touching exception handling (or other syntax uncommon enough that ruff's parser may be lenient about it), also run `python3 -c "import ast; ast.parse(open(path).read())"` (or just try importing the module in a `bench console`) before trusting a green CI run. All 8 affected files were fixed by replacing every `except A, B:` with `except (A, B):` — seven of them in `cb5f735`, the eighth (`order_mapper.py`) on the separate branch that caught it first.

## Tests

- A bare `unittest.mock.MagicMock()` standing in for a `requests.Response` (or any other object used via `with obj:`) does **not** return itself from `with mocked as x:` by default — `MagicMock` auto-specs magic methods including `__enter__`, but its default `__enter__` return value is a *fresh* child `MagicMock`, not the mock instance you configured `status_code`/`headers`/`iter_content`/etc. on. Code changed to use a response as a context manager (e.g. to guarantee it's closed on every code path) will silently receive that empty child mock as `x` instead, breaking every attribute access. Explicitly set `mock_response.__enter__.return_value = mock_response` (and `mock_response.__exit__.return_value = False`) in the test fixture/helper that builds the mock.
- `class Test<DocType>(IntegrationTestCase)` (from `frappe.tests`) in `test_<doctype_name>.py`, using `frappe.get_doc(...).insert()` fixtures per test, not shared global state. `FrappeTestCase` is deprecated as of Frappe v16 — use `IntegrationTestCase` for tests that touch the DB/site, `UnitTestCase` for pure-logic tests that don't.
- Run with `bench --site test.localhost run-tests --app <app_name>` inside the dev container — **always the dedicated `test.localhost` site, never `dev.localhost`** (tests commit permanently to whatever site they run on; see `docs/dev-environment.md`, "Running tests"). `$SITE_NAME` from `.env` is the prod-shaped stack's site, which can't run custom apps.
- To prove a hidden `unique: 1` composite-key field is enforced by MariaDB itself and not merely by your `validate()`-time precheck (relevant whenever `name` is independent/expression-based, so a duplicate-identity insert can't be relied on to collide on `name` the way a composite-string autoname would): set `doc.flags.ignore_validate = True` before calling `.save()` on an already-inserted document whose key field you've manually overwritten to collide with another row's. That flag makes `run_before_save_methods()` skip **both** `validate()` and `before_save()` together (confirmed in `document.py`) — so your own precheck and your own key-recomputation are both bypassed, and only the raw `UPDATE` in `db_update()` remains, which surfaces the real DB constraint as `frappe.UniqueValidationError` (or nothing, if the constraint isn't actually there).
- `IntegrationTestCase` auto-generates a generic test record for every doctype linked from the one under test's meta (including doctypes referenced only via a `Link` field like `warehouse`, not just fields you explicitly construct in a test). If that auto-generation transitively hits ERPNext's pre-existing Company/Fiscal Year overlap bug on this dev site (unrelated to whatever you're testing), add the offending doctype(s) to a module-level `IGNORE_TEST_RECORD_DEPENDENCIES` list and construct that dependency explicitly in the test instead — same pattern already used for `Item` in `talabat_product_mapping`'s tests and for `Warehouse` in `marketplace_account`'s.
- The failure above isn't necessarily "auto-generating a conflicting Company/Fiscal Year record" — for `marketplace_product_mapping`'s `sales_uom` (Link → UOM), the actual mechanism is that Frappe's test-dependency walker, while resolving `UOM` as a transitive Link target, imports `UOM Category`'s test module as a side effect (to check whether *it* has its own test-record requirements) — and that import itself (`erpnext/tests/utils.py`'s `ERPNextTestSuite`/`BootStrapTestData()`) runs at **module import time**, not record-creation time, and is what tries to create a colliding Fiscal Year. This means: (1) it's not just a doctype's *direct* Link fields that can trigger this — **any transitive Link-field hop** to a doctype whose test module imports `erpnext.tests.utils` can, so `IGNORE_TEST_RECORD_DEPENDENCIES` may need a new entry every time a new Link field introduces a fresh transitive path, even if that field's own direct target looks unrelated to Company/Fiscal Year; (2) `IGNORE_TEST_RECORD_DEPENDENCIES` only suppresses the *auto-generation* step for a scoped test run that starts its dependency walk from doctypes in your own app (e.g. `bench run-tests --app <app_name>` or `--module ...`) — it does **not** protect a whole-bench `bench run-tests` run, where the same transitive import can still be triggered by walking from some other app/doctype entirely.
- `IntegrationTestCase.doctype` is derived automatically by `UnitTestCase.setUpClass()` from the test file's own path/location (`frappe/tests/classes/unit_test_case.py`) — setting it as a class attribute on your test class has zero effect (it gets immediately overwritten), so don't add it as a convention.
- `IntegrationTestCase` only rolls back the DB **once, at class teardown** (`addClassCleanup(_rollback_db)` in `frappe/tests/classes/integration_test_case.py`) — not after every individual test method. Every test method in a class shares the same open transaction. A `make_connection()`/`make_<doctype>()` test helper with a **fixed literal default** for a field that later gets `unique: 1` (or already has it) will insert that same value more than once the moment two test methods in the same class both call the helper without overriding that field — even though each test "looks" independent. Give such helpers a call-unique default (e.g. `frappe.generate_hash()`-suffixed) for any field a real uniqueness constraint might land on, and only hardcode a literal value in the specific test that actually asserts against it.
- A test `tearDown` that deletes rows is only effective for rows still in the open transaction. Once the code under test calls `frappe.db.commit()` (directly, or via `db_set(commit=True)`, or a worker that commits per chunk), a `frappe.delete_doc`/`frappe.db.delete` in `tearDown` is itself uncommitted, and the class-level rollback undoes it — the committed rows come back. Such tests need an explicit commit in the teardown (a deliberate decision, since it persists whatever else the test left behind) or a unique-suffix fixture scheme that tolerates leftovers. Also: `frappe.db.delete` removes only the parent row; for doctypes with child tables (e.g. `Marketplace Order`) delete via `frappe.delete_doc(..., force=True)` so child rows are removed too.
- `Document.db_set(..., commit=True)` commits the **entire current transaction**, not just that one field's `UPDATE` — including any other row inserted earlier in the same test method (or, worse, earlier in the same `IntegrationTestCase` class, since rollback is class-scoped per the bullet above). A `commit=True` reachable from a test's exception/error path (used deliberately so status fields survive a `frappe.throw()`-triggered rollback in production — see `integrations/shopify/webhooks.py::sync_webhook_subscriptions()`'s except block) will permanently persist whatever else is sitting in that transaction to the real site DB the moment that test runs, surviving even a full `bench run-tests` run's teardown. This is how stray `Shopify Connection` test rows leaked into this project's dev site (discovered while adding a `unique: 1` constraint on `shop_domain` — four "Sync Webhooks ..." rows from `test_exception_during_sync_still_persists_error_status` were still present in the DB). If a route under test can reach a `commit=True` write, assume any DB row that test creates is permanent unless the test itself tears it down (or the site is scrubbed afterward) — the class-level rollback cannot be relied on for that test.
- A test module that lives **outside** any `doctype/` folder (e.g. a test file next to a whitelisted API module, like `api/test_noon_catalog.py`) gets `cls.doctype = None` from that same derivation (`_get_doctype_from_module()` looks for a `"doctype"` path segment and finds none) — so `IntegrationTestCase`'s auto-test-record generation never runs for it at all, and `IGNORE_TEST_RECORD_DEPENDENCIES` isn't needed (and isn't even supported there: `get_missing_records_module_overrides()` raises `NotImplementedError` if you set it on a doctype-less module that also has no dependencies to ignore). This makes API-level test modules simpler to write than doctype ones for this specific concern — construct whatever fixture documents the test needs directly, same as always, just without the Company/Fiscal-Year auto-generation hazard.
- **Permission fixtures: use `marketplace_integrations/tests/utils.py::make_role_user(self, label, {doctype: [ptype, ...]})`** (returns `(email, role_name)`) for every test that needs a user with specific permissions; never hand-roll Role/User/Custom DocPerm setup. Traps it exists for (verified in Frappe 16.32.0): (1) `frappe.permissions.add_permission()` / `update_permission_property()` call `setup_custom_perms(doctype)`, which COPIES every standard DocPerm row into Custom DocPerm when the doctype has none yet; from then on only Custom DocPerm rows apply (`Meta.set_custom_permissions`), so later permission changes in the doctype JSON are silently ignored on that site. (2) Inserting a `Custom DocPerm` row directly (no copy) makes that single row the ONLY rule for the doctype, so every other role loses access while it exists; grant only via `add_permission`. (3) Deleting a Role does not delete its Custom DocPerm rows (no `on_trash`; tests delete with `force=True`), so they must be removed explicitly, together with the standard-row copy `add_permission` created if the doctype had no Custom DocPerm rows before the test. (4) One row per role per doctype: `add_permission` is a no-op for a role that already has a row, so a second call cannot add more ptypes; use `update_permission_property` for the rest, and note that `read` and `export` always come with the row `add_permission` creates (so "write only" still includes read). The helper handles all of this: it records which doctypes already had rows, registers one cleanup that removes only what the test caused, and commits. Because it commits, **a test class using `make_role_user` must delete its own fixtures in `tearDown`** (a commit makes anything left to class-level rollback permanent).
- **Desk "Amend" ignores `no_copy`** (confirmed in Frappe 16.51 `public/js/frappe/model/create_new.js`: `is_no_copy = !from_amend && df.no_copy`, and Amend calls `copy_doc(fn, 1)`), and server-side `frappe.copy_doc()` defaults to `ignore_no_copy=True`. A `no_copy` field therefore does NOT stay empty on an amended document, only on Duplicate. For a `unique` field (e.g. `Payment Entry.custom_marketplace_transaction_id`) the amended draft carries the cancelled document's value and cannot be saved while that document exists; do not rely on `no_copy` alone to free a unique key for amendments.
- ERPNext's account-type restriction on a link field can be Desk-only: `Payment Entry.paid_to` is limited to Bank/Cash (Receive) only by `frm.set_query` in `payment_entry.js`; the controller does not check it. Code that creates the document server-side must enforce the rule itself.
- A Sales Order's outstanding for Payment Entry purposes is `(rounded_total or grand_total) - advance_paid` (`payment_entry.py::get_reference_details`, `validate_allocated_amount_with_latest_data`); allocating above it raises. With rounded totals enabled, never size an allocation from `grand_total`; a Receive entry can write the `grand_total - rounded_total` difference off with a `deductions` row (negative amount for an overpayment, to `Company.round_off_account`/`round_off_cost_center`) and still submit with `difference_amount` 0 (verified 16.50).
- **`enqueue_after_commit` jobs never fire inside a test.** In tests the transaction is never committed, so `enqueue_after_commit` jobs never fire; patch `frappe.enqueue` to call the job body.
- **A background job that writes a document the open form shows must bump `modified` and notify.** Use `doc.db_set({...}, update_modified=True, notify=True, commit=True)`. The form then needs `frm.reload_doc()` before it saves or submits again, or the save fails with a timestamp mismatch. A server action started from the form can pass `frm.doc.modified` and refuse when the stored copy changed (epic #413 `request_create`).
- **A unique Custom Field is a cheap idempotency key.** A unique-indexed Custom Field (Integration Request `custom_dedupe_key`) makes a duplicate insert raise `UniqueValidationError`/`DuplicateEntryError`; catch it to treat a webhook replay as a no-op. Native Integration Request grants only System Manager, so insert with `ignore_permissions=True` after your own permission check.
- **A `post_model_sync` patch that needs a Custom Field must create it itself.** Fixtures sync after patches, so the patch reads `fixtures/custom_field.json` and inserts the fields it uses (epic #413 `migrate_bosta_shipments_to_delivery_notes`).
- **Commit, then lock as the next statement.** MariaDB snapshot isolation: `frappe.db.commit()` then `get_value(..., for_update=True)` straight away, otherwise the lock reads a stale snapshot. Never hold the lock across an HTTP call.
- **A Desk Amend ignores `no_copy`** on fields, so clear carrier/system fields in `validate` when `amended_from` is set.
- **Pick a naming series in a `before_naming` doc event.** `Document.insert` runs `_validate_links` (so `fetch_from` values are already set), then `before_insert`, then `set_new_name`, whose first step is `run_method("before_naming")`; setting `doc.naming_series` there chooses the series. Frappe does not check `naming_series` against the Select options (`_validate_selects` skips it), so a new series works even before its option exists, but ship the option as a Property Setter anyway (form dropdown) and keep the existing default FIRST: `get_default_naming_series` returns the first option. Use the SAME Property Setter name (`<Doctype>-naming_series-options`) as a site's existing one, so the fixture import replaces its value instead of adding a second setter. Example: `services/platform_naming.py`.
- **Deleting the newest document gives its name back to the naming series** (Frappe reverts the series counter), so a later test or run is handed the same Delivery Note name. State keyed by that name outlives the delete and hits the new note: cache flags (`noon-shipment-invoice-inflight|<note>`, `noon-refresh-again|<note>`) and Integration Request rows (a `Cancel / Success` row hides a Carrier Cancelled Needs Attention item). Clear both at note creation and in cleanup (`noon/test_delivery_note_shipment.py::_draft_note`). A test that looks a note up by a fixed external id (`DELIVERY-1`, `TRK-1`) or whose job polls "every Created note" is also at the mercy of rows an interrupted or older run left on `test.localhost`: use ids built from `self.suffix` for lookups, and reset the test site when leftovers pile up.
- **ERPNext reads the customer's Address on every Delivery Note save**, so a test user who submits or saves a note needs `Address` read: Stock User/Manager alone are refused (`PermissionError` from `render_address`). Give such users Sales User as well. When a test patches `Document.check_permission` to simulate a refusal, restrict it to the doctype under test (`autospec=True`, delegate others to the real method): a blanket patch also blocks the Error Log insert in the code's own `except` path.
- **ERPNext mapper results carry `flags.ignore_permissions`, and Sales Invoice advances are not fetched by default.** `make_sales_invoice` sets `target.flags.ignore_permissions = True` (in `set_missing_values`), so an `insert()` of its result skips the user's rights: set the flag back to False and check create/submit yourself. It calls `set_advances()` only when `allocate_advances_automatically` is on (the field defaults to 0), so a paid Sales Order's Payment Entries are not applied unless you turn it on before `insert()` (validate then allocates them, up to `rounded_total` else `grand_total`). Also set `only_include_allocated_payments = 1`, or `set_advances` (which includes unallocated amounts by default) can pull an unrelated unallocated payment of the same Customer. ERPNext's `validate` totals the invoice BEFORE it allocates the advances, so `total_advance` and `outstanding_amount` right after `insert()` still show the full outstanding (seen in the bulk Delivery Note tests); only the submitted and reloaded invoice has the right totals, so check them there and roll back if it is still unpaid (source read in erpnext develop, `selling/doctype/sales_order/mapper.py` and `accounts/services/advances.py`; not yet run on 16.51.1, `services/bulk_delivery_notes.py`). On 16.51.1 the mappers are imported from `erpnext.selling.doctype.sales_order.sales_order`, the develop checkout moved them to `.mapper`.
- **Gotcha: `ruff check --fix` over the whole app rewrites unrelated files.** Run ruff on the files you touched, without `--fix`; `ruff format` is not applied uniformly in this repo.
