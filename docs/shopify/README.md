# Shopify integration

No single official downloadable spec exists for Shopify (unlike Talabat's checked-in `openapi.json`) — Shopify does not publish one. This doc is a manually maintained reference, sourced from `shopify.dev`, scoped to what's needed for the current work: the `Shopify Connection` doctype and its auth layer (tracked by #101). Extend this doc (or add sibling files) when catalog/order sync work is actually scoped — don't infer those endpoints from here yet.

This will back `Shopify Connection` in the `marketplace_integrations` app — see `docs/marketplace-integrations/architecture.md`'s "Connection design decision" for why Shopify gets its own typed doctype rather than a shared one.

## App type: custom app, single store (Tamwenat only)

This is a **custom app** for one specific Shopify store — not a public app distributed to multiple merchants. No merchant-facing OAuth install flow is needed.

## Auth model (current, since Jan 1 2026)

Shopify no longer allows creating custom apps from the store Admin UI ("Develop apps") with a static token. New custom apps are created via the **Dev Dashboard** (`https://dev.shopify.com/dashboard/`), which issues a **Client ID** and **Client Secret** instead of a token you copy once.

Access tokens are obtained programmatically via the **client credentials grant**:

- `POST https://{store}.myshopify.com/admin/oauth/access_token`
- Body: `grant_type=client_credentials&client_id={client_id}&client_secret={client_secret}`
- Response: `access_token`, `scope`, `expires_in` (≈ 86399 seconds, i.e. ~24 hours)

Key difference from the legacy flow: the old `shpat_...` static token never expired. This client-credentials token does — it must be refreshed programmatically before/on expiry, similar in spirit to Talabat's token-cache-with-expiry-buffer pattern (`TalabatClient`), not a one-time setup value.

Apps created before Jan 1 2026 under the old flow keep their static token working, but any new custom app (this one) must use the client-credentials flow.

## API surface: GraphQL, not REST

Shopify marked the REST Admin API as legacy in Oct 2024. Since April 2025, new apps must use the **GraphQL Admin API** exclusively. Any Shopify client built here should be a GraphQL client, not a REST client — this is a structural difference from `TalabatClient`, which is REST-only.

## GraphQL Admin API (for #102)

- **Endpoint**: `https://{shop_domain}/admin/api/2026-10/graphql.json` — `POST` only.
- **Pinned API version**: `2026-10` (stable from Oct 1 2026; supported until ~Oct 2027). Re-check `docs/api/usage/versioning` before pinning a new version later — don't assume this stays current.
- **Auth header**: `X-Shopify-Access-Token: {access_token}` (from `ShopifyClient.get_access_token()`), plus `Content-Type: application/json`.
- **Request body**: `{"query": "...", "variables": {...}}`.
- **Response body**: `{"data": {...}, "extensions": {"cost": {...}}}`.
- **Errors return HTTP 200.** The failure signal is a non-empty top-level `errors[]` array, not the status code — a 200 with data present and `errors` empty/absent is the only success shape.
- **Throttle shape**: `errors: [{"message": "Throttled", "extensions": {"code": "THROTTLED", "retryAfter": <seconds>}}]`. Use `extensions.retryAfter` directly for backoff — don't track bucket capacity/restore-rate ourselves, that varies by Shopify plan tier and isn't needed if we just honor `retryAfter`.
- **Per-mutation `userErrors`** are a separate concept from the top-level `errors[]` — they live inside the mutation's own payload (e.g. `webhookSubscriptionCreate.userErrors`) and must be surfaced to the caller, never treated as a transport failure.

Source: [GraphQL Admin API reference](https://shopify.dev/docs/api/admin-graphql), [Shopify API rate limits](https://shopify.dev/docs/api/usage/rate-limits), [GraphQL Admin API — example Throttled response](https://community.shopify.com/t/graphql-admin-api-example-throttled-requests-response/8456).

## Webhooks (#104, implemented)

- Custom apps (client-credentials, no Shopify CLI/`shopify.app.toml`) register webhook subscriptions via the GraphQL Admin API's `webhookSubscriptionCreate` mutation — pointing at any HTTPS URL, including a Frappe whitelisted endpoint. No Partner-app tooling or declarative config file needed. `Shopify Connection`'s "Sync Webhook Subscriptions" button (`integrations/shopify/webhooks.py`'s `sync_webhook_subscriptions()`) is the explicit, user-triggered mutation that registers/repairs subscriptions for every topic in `SHOPIFY_WEBHOOK_TOPICS` at the site's own callback URL, deleting any stale subscription left at an old URL first.
- **HMAC verification needs no separate hosted app.** Shopify signs each delivery with `HMAC-SHA256(raw_request_body, client_secret)`, base64-encoded, in the `X-Shopify-Hmac-Sha256` header. `api/shopify_webhooks.py::webhook_event()` verifies it (`verify_shopify_hmac()`) against the RAW request body before any JSON parsing, using the `client_secret` already stored on the resolved `Shopify Connection`.
- Decision made and implemented: **no separate Node/Remix bridge app** for this (a scaffold exploring that shape exists at `github.com/MohamedAmirr/erpnext-shopify-integration` but is not the chosen path — see #104). ERPNext registers its own webhook subscription and verifies HMAC itself, mirroring `api/talabat_webhooks.py`'s pattern but with HMAC instead of Bearer-token auth.
- Client secret rotation is handled: Shopify signs webhooks with the app's *oldest unrevoked* client secret, so `verify_shopify_hmac()` checks the connection's current `client_secret` first and, if that fails, its `previous_client_secret` — accepting either until the old secret is revoked and the field cleared.
- Every subscribed topic shares one endpoint (`webhook_event()`); `X-Shopify-Topic` (delivery header form, e.g. `orders/create`) is mapped to the GraphQL enum form (e.g. `ORDERS_CREATE`, via `SHOPIFY_WEBHOOK_TOPIC_HEADER_TO_ENUM`) to route to `process_shopify_webhook()`. Deduplication is by `X-Shopify-Webhook-Id`, enforced with a DB-level unique index on `Shopify Webhook Delivery.webhook_id`, not a check-then-insert read.
- The webhook request itself only authenticates, minimally validates shape, and enqueues — order topics retain only an order GID and the worker refetches canonical state for #109; the webhook payload is never treated as financial evidence and no ERPNext document is created. `APP_UNINSTALLED` disables the `Shopify Connection`; `APP_SCOPES_UPDATE` remains an acknowledged no-op.
- **Concurrent events for one order.** Shopify sends `ORDERS_CREATE`, `ORDERS_UPDATED` and `ORDERS_PAID` for a new order within milliseconds, so several worker jobs import the same order at once. The loser of the insert race sees the winner's committed row through the locking lookup in `upsert_marketplace_order()` (a current read) but not through a plain `get_doc` (a consistent read in the job's older read view), which used to fail with "Marketplace Order MKTORD-... not found" (Error Log "Shopify webhook processing failed", delivery in Error). The service now loads the order with `frappe.get_doc(..., for_update=True)` whenever it locks (Shopify passes `is_stale`): Frappe's `load_from_db` then reads the parent and every child table with `SELECT ... FOR UPDATE`, so the document and its items match the locked row. The same applies to the reload after a `UniqueValidationError` on insert. No commit is needed, so the delivery row and the sweep's savepoints are untouched.
- Because `webhook_event()` responds 200 as soon as processing is enqueued (correct: "respond promptly"), Shopify never retries a delivery whose async processing later fails. A scheduled hourly sweep (`retry_errored_webhook_deliveries()`, registered in `hooks.py`'s `scheduler_events`) reprocesses any `Shopify Webhook Delivery` still at `status="Error"`, bounded by a simple `attempt_count` cutoff (`MAX_WEBHOOK_DELIVERY_ATTEMPTS`) so a permanently-failing delivery isn't retried forever.

Source: [Manage your app credentials](https://shopify.dev/docs/apps/build/authentication-authorization/client-secrets), [webhookSubscriptionCreate mutation](https://shopify.dev/docs/api/admin-graphql/latest/mutations/webhookSubscriptionCreate).

## Products and variants (for #105)

- Catalog discovery uses a **flat `productVariants` root query** (single cursor), not nested `products { variants }` - simpler single-cursor pagination, matching `ShopifyClient.execute()`'s existing one-call-site pattern.
- `productVariants(first: Int, after: String, query: String)` returns a `ProductVariantConnection`: `pageInfo { hasNextPage endCursor }` plus `nodes`.
- `ProductVariant` fields selected: `id (ID!)`, `sku (String)`, `barcode (String)`, `product { id title }`. No variant-level `title` is selected - only the parent product's.
- Deleted-mapping detection uses the generic `nodes(ids: [ID!]!): [Node]!` root field (`... on ProductVariant { ... }`), the first batched/multi-id lookup in this codebase. Each response node is matched back to its saved mapping row by its own `id` field, never by list position - Shopify doesn't guarantee response order matches the requested id order. A deleted variant is one whose id is either missing from the response entirely or present with a `null` node.
- Source: [ProductVariant object](https://shopify.dev/docs/api/admin-graphql/latest/objects/ProductVariant), [productVariants query](https://shopify.dev/docs/api/admin-graphql/latest/queries/productVariants), [nodes query](https://shopify.dev/docs/api/admin-graphql/latest/queries/nodes) - all verified against shopify.dev on 2026-09-19 (external source, approved by the user for reliance).

## Publishing prices (#106)

- Price-only, update-only: the only mutation used by the price push is `productVariantsBulkUpdate(productId: ID!, variants: [ProductVariantsBulkInput!]!, allowPartialUpdates: Boolean = false)` - never `productCreate`/`productUpdate`/`productSet`. Product creation exists separately in `integrations/shopify/product_create.py` (#494, see "Creating products from ERPNext"); the price push itself stays update-only. `ProductVariantsBulkInput` carries only `id` and `price` here; `inventoryQuantities`/`quantityAdjustments` are out of scope (future inventory work, not #106). `allowPartialUpdates: true` persists valid variant changes even when a sibling in the same call fails.
- Every product/variant mutation requires the `write_products` access scope - the first feature in this app needing a write scope (everything through #105 only ever needed read scopes). Confirm it is actually granted on the custom app before relying on this in production.
- The exact response payload shape used by this feature (`product { id }`, `productVariants { id }`, `userErrors { field message }`) follows Shopify's well-established Bulk-mutation payload convention (the same shape `productVariantsBulkCreate` uses) but was **not independently re-verified against a live call or a fresh shopify.dev page** during #106's implementation - only `productId`/`variants`/`allowPartialUpdates` and `ProductVariantsBulkInput.id`/`.price` were checked against shopify.dev on 2026-09-22. Worth confirming the response shape against a real/test store before depending on it further.
- Result attribution deliberately avoids parsing `userErrors[].field` to identify which variant a given error belongs to (that path/shape was never verified). Instead, a variant is only ever confirmed successful if its `id` appears in the mutation response's own `productVariants` list; anything requested but missing from that list is treated as failed, with `userErrors[].message` used only to build a nicer error string, never to attribute a specific error to a specific variant.
- No general idempotency-key mechanism exists for Admin GraphQL mutations (checked - absence of evidence, not proof it's impossible). Not needed here regardless: every push is an update keyed on an existing variant GID (from #105's discovery), never a create call, so it is inherently replay-safe by construction.

Source: [productVariantsBulkUpdate mutation](https://shopify.dev/docs/api/admin-graphql/latest/mutations/productVariantsBulkUpdate), [ProductVariantsBulkInput](https://shopify.dev/docs/api/admin-graphql/latest/input-objects/ProductVariantsBulkInput) - verified against shopify.dev on 2026-09-22 (external source, approved by the user for reliance) for the arguments/input fields only, per the caveat above.

## Creating products from ERPNext (#494)

Code: `integrations/shopify/product_create.py`, `api/shopify_products.py`; UI: "Create on Shopify" on the Item form (#495).

- **Fields sent**: `title` = `item_name`, `status` = `DRAFT` (via `productCreate`); then `SKU` = `item_code` on the default variant (via `productVariantsBulkUpdate`, `inventoryItem.sku`). Nothing else: no description, images, vendor, tags, options, publishing, price or stock (price and stock follow from #106 and #107 once mapped).
- **Mapping**: after both mutations succeed, `products.upsert_mapping(account, variant_gid, item, external_product_id=product_gid, external_sku=item_code)` writes one enabled Marketplace Product Mapping.
- **Flow**: Desk queue does local checks only (no Shopify call); the worker re-checks, creates, sets the SKU, maps. Any `userErrors` or top-level error stops the job with Shopify's message and leaves no mapping.
- **No idempotency key** for `productCreate`, and **no automatic retry**. A retry after an unknown outcome can create a duplicate product.
- **Orphan recovery**: if Shopify created the product but the SKU update or mapping write failed (error names the product/variant GIDs), or the create outcome is unknown (error names the title), check Shopify for a product titled with the Item's `item_name` before retrying. Delete or reuse the orphan first; an Error Log entry "Shopify product create failed" holds the details.
- **UNVERIFIED until a live dev-store check (one Item)**: the mutation names and input shapes (`productCreate(product: ProductCreateInput!)` with `title`/`status`; `productVariantsBulkUpdate` with `inventoryItem: { sku }`), and the response shape (`productCreate.product { id variants(first: 1) { nodes { id } } }`, `productVariantsBulkUpdate.productVariants { id }`, `userErrors { field message }`) were written from memory/convention, not checked against shopify.dev or a live call. The `write_products` scope is also required.

## Inventory (#107)

- Behavior: `integrations/shopify/inventory_sync.py` pushes ERPNext stock to Shopify **`available`** (changed from `on_hand`) for the Marketplace Account's bound Location, from `floor(max(Bin.actual_qty - Bin.reserved_qty, 0))` in the Item's **stock UOM** (`sales_uom` ignored). `reserved_qty` is the Sales Order reservation (not `reserved_stock` from Stock Reservation Entries); Product Bundle components use the same `actual_qty - reserved_qty` read. Only the Shopify sync passes `subtract_reserved=True` to `resolve_stock_quantities()`; Talabat/Noon/delivery-note callers keep the plain `actual_qty` read. A Sales Order submit/cancel/delivery that changes `reserved_qty` bumps `Bin.modified` (ERPNext 16.51.1: `update_bin_qty` sets `bin.modified = now()` and `db_update()`; `update_qty` uses `update_modified=True`), so the changed-Bin sweep catches it. Two trigger paths exist: **manual** (mapping form / list bulk action "Sync Shopify Inventory", account form "Reconcile Shopify Inventory" - PR1) and **automatic** (PR2, below). Nothing in the app ever creates a Stock Entry / Stock Reconciliation / Stock Ledger Entry from Shopify data and no inventory webhook topic is subscribed - both trigger paths only ever call `enqueue_account_sync()`.
- **Pause switch (#285):** the Marketplace Account check field `shopify_inventory_push_enabled` ("Push Inventory to Shopify", default on, shown for Shopify accounts) stops every inventory write for that account while orders keep importing. Off: the 2-minute sweep and the daily reconcile skip the account without enqueueing (and without an "excluded account" Error Log line); the manual "Sync Shopify Inventory" / "Reconcile Shopify Inventory" actions are NOT affected: the switch governs only automatic triggers, so a click runs once (`manual=True` is passed to `enqueue_account_sync()` and the worker, which skips every switch check, including the per-chunk one); `enqueue_account_sync()` raises "Inventory push is paused for this account." only for automatic callers; an automatic job queued before the switch was turned off returns at the start of `sync_account_inventory()` with no Shopify call (job status `failed` with the message, no Error Log, mapping statuses untouched). A job already running re-reads the switch (fresh DB read) before every chunk and stops before its next Shopify write when it was turned off: the result carries `paused: true`, status `failed` with the same message, chunks already applied stay recorded and the mappings of the chunks not yet pushed are left untouched (a chunk already in flight, including its stale-retry/per-item fallback calls, finishes first). A sweep/reconcile that races the switch is a quiet skip, not an Error Log entry. The only Shopify writes outside the inventory sync are the price update (`catalog_push.py`) and webhook create/delete (`webhooks.py`); both are reachable only from manual, user-triggered whitelisted methods (`api/shopify_catalog_push.py`, Shopify Connection's "Sync Webhook Subscriptions"), never from `scheduler_events` or `doc_events`. Turning it back on does not push anything by itself: the next sweep/reconcile or a manual action does. Existing accounts read as on after migrate (the column default is 1). Order import, webhooks, order reconcile, Sales Order sync and price/product publishing are unchanged.
- **Automatic triggers (PR2):** `hooks.py`'s `scheduler_events` registers two jobs, both in `integrations/shopify/inventory_sync.py`:
  - **Changed-Bin sweep**, every 2 minutes (`SHOPIFY_INVENTORY_SWEEP_CRON`, cron syntax since Frappe has no built-in "every N minutes" bucket): for every enabled Shopify Marketplace Account, `sweep_changed_bins()` finds Bins in that account's Warehouse whose `modified` is newer than a per-account watermark (held in `frappe.cache()`, no TTL) minus a **10-minute overlap window** (`SHOPIFY_INVENTORY_SWEEP_OVERLAP_MINUTES`), maps them to enabled mappings, and enqueues one deduplicated job per account scoped to just those mappings. A **missing watermark** (first-ever tick for that account, or a lost/evicted cache entry) falls back to "look back 10 minutes from now", not "skip" or "do a full sync". The overlap window means one real stock change is typically re-covered by ~5 consecutive ticks before it ages out (2-minute interval / 10-minute overlap) - each of those re-syncs is a no-op write once Shopify already matches, so this is a deliberate read-cost tradeoff, not a bug.
  - **Daily full reconciliation** (`reconcile_all_accounts()`): enqueues one full (no mapping filter) inventory sync for every enabled Shopify Marketplace Account. Recovers anything the sweep could miss - a lost/evicted watermark, a change whose Bin write fell outside the overlap window, or a mapping created/enabled after its Item's Bin last changed.
  - **Dedup-rejection behavior:** both jobs share the same per-account RQ dedup job id the manual actions use, so a tick/reconciliation for an account whose previous job is still running is rejected (`enqueue_account_sync()` returns `(False, None)`), not queued twice. The sweep does **not** advance that account's watermark on a rejection - the next tick's overlap window naturally re-covers the same span once the busy job finishes, instead of the change going stale until the next daily reconciliation. The daily reconciliation has no watermark to hold back, so a rejection there is written to the Error Log (`"Shopify daily inventory reconciliation skipped"`, with the account name and reason) rather than silently dropped or retried.
  - **Scheduler account filter:** the account list feeding both jobs mirrors the worker's own validation (`validate_account_warehouse()` - Warehouse must exist, be a leaf, not be disabled, and match the account's Company when one is set), not just "Warehouse is set". A misconfigured account is silently excluded from scheduling rather than being enqueued every tick and failing in the worker every time.
  - **Deploy note - this is the step that makes live Shopify writes happen automatically:** the two Scheduled Job Type records these `scheduler_events` entries describe are only created/updated by `bench migrate` (Frappe's own scheduled-job sync from `hooks.py`) - a code deploy alone does not register them. And even once registered, nothing runs unless the site's scheduler is enabled (`bench --site <site> scheduler enable` / `resume`, or Desk's System Settings). Confirm both after any deploy that touches this feature, not just after the first one.
- Per chunk (`SHOPIFY_INVENTORY_SYNC_CHUNK_SIZE`): one `nodes(ids:)` read (`ProductVariant.inventoryItem { id tracked inventoryLevel(locationId:) { quantities(names: ["available"]) { name quantity } } }`), skip items already equal, `inventoryItemUpdate(id, input: {tracked: true})` for untracked items, `inventoryActivate(inventoryItemId, locationId)` for items with no level at the Location (both deliberate, user-approved changes to Shopify configuration - run the first live sync on ONE test variant), then one `inventorySetQuantities` with `changeFromQuantity`. `CHANGE_FROM_QUANTITY_STALE` (the real stale-compare userError code) re-reads and resends the whole chunk (max `SHOPIFY_INVENTORY_MAX_STALE_RETRIES` retries); any other userError falls back to one item per call.
- Every inventory mutation except `inventoryItemUpdate` carries `@idempotent(key: $idempotencyKey)` with a fresh `uuid4` per logical mutation (required as of API version 2026-04 per shopify.dev, verified 2026-09-24, approved by the user).
- Required scopes: `write_inventory` (and `read_inventory`) - `write_products` from #106 does not cover them. Confirm they are granted on the custom app before the first live run.
- **Operating note (`available` pushed):** the pushed value already has ERPNext's Sales Order reservations (`Bin.reserved_qty`) subtracted, so marking an order fulfilled in Shopify no longer double-subtracts it (the old `on_hand` push required that). What still holds: the ERPNext-side stock-out (a posted Delivery Note, or a Sales Invoice with `update_stock`) must eventually happen so `actual_qty` drops and the reservation clears; a Sales Order alone only reserves. Between a Shopify order and its Sales Order being submitted in ERPNext the pushed value is not yet reduced; the next push after the reservation converges both sides. An order that stays `Syncing` with no Sales Order for more than 20 minutes (`SYNC_PENDING_ALERT_MINUTES`, and not still inside its `sync_debounce_until` window) shows in Marketplace Needs Attention as "Sync Pending Too Long" (next action Retry), so that window cannot go unnoticed; a failed sync shows as Sync Error instead. `reserved_stock` (Stock Reservation Entry) is deliberately not subtracted a second time: stock reserved by a Sales Order's Stock Reservation Entry is already inside `Bin.reserved_qty`, because ERPNext counts every open Sales Order's undelivered qty there.
- **Unverified for `available`:** that `available` works as the `inventorySetQuantities` `name` together with `changeFromQuantity`, and that `quantities(names: ["available"])` returns it. The name itself is documented as valid (`available` or `on_hand`, see below), but nothing was run against a live store; test on ONE variant first.
- **Non-stock and template Items are skipped:** a mapping whose Item has `is_stock_item = 0` (service, Product Bundle parent) is reported as `skipped` ("Item is not a stock Item.") in explicit syncs and full reconciliation alike. Separately, a mapping whose Item has `has_variants = 1` (a template Item) is also skipped ("Item is a template (has variants).") - ERPNext defaults `is_stock_item` to 1 even for a template and refuses to post stock directly against it, so it has no Bin either. Neither skip mutates anything or changes the store, so a deliberately untracked variant is never set to 0 or switched to tracked. A Product Bundle parent wrongly flagged `is_stock_item = 1` is NOT detected (no bundle logic).
- Errors that happen after Shopify was already changed (tracking enabled / item activated) say so in the mapping's `inventory_last_error`. Error Log entries are capped per job (`MAX_ERROR_LOG_ENTRIES_PER_JOB`) with one summary entry; selected mappings deleted or moved after queueing get an Error row so totals reconcile.
- Status is written to the mapping's own `inventory_sync_status` / `inventory_last_synced_on` / `inventory_last_error`, never to the shared `sync_status` fields used by #106's price push.
- **Verified on shopify.dev 2026-09-24** (`mutations/inventorySetQuantities`, `objects/InventoryQuantity`): `@idempotent(key: $idempotencyKey)` with `$idempotencyKey: String!`; `reason: "correction"` (documented example; the full value list is not stated); `referenceDocumentUri` is optional in the 2026-07 input (read before the 2026-10 pin; a GID format is preferred; our `logistics://` style is accepted); `referenceDocumentUri` documented example style `logistics://some.warehouse/take/<timestamp>` (no format rules stated - the URI used matches that style); `InventoryQuantity` fields `id, name, quantity, updatedAt`.

The 2026-07 input has only `changeFromQuantity` (no `compareQuantity`). **Not verified against 2026-10:** the pinned API is now 2026-10, but the inventory, catalog, order-import and webhook queries and mutations other than the order-cancellation calls and `displayFulfillmentStatus` (checked against 2026-10 below) were checked only against earlier versions (2026-07 and before); nobody has re-read them for 2026-10. Re-check them before relying on any detail in this section.

## Orders, refunds, and reconciliation (#109)

- Canonical order state is fetched through the Admin GraphQL `order(id:)` query by Shopify GID; webhook payloads provide only the GID and are never treated as financial evidence.
- The query requests customer identity/contact and billing/shipping address fields. Protected customer-data access was live-verified on 2026-09-28; nullable customer, phone, and address values are handled as absent evidence rather than errors.
- Current Shopify MoneyBag totals are persisted as evidence (`subtotal`, discount, tax, shipping, duties, and total); line `net_amount` is `priceAfterAllDiscountsBeforeTaxesSet` (the same value as `transaction_amount`). It is display-only. It used to be original unit price × current quantity minus discount allocations, but per shopify.dev (internet, LineItem docs) `discountAllocations` still include discounts allocated to refunded/removed quantities, which understated it after a partial refund.
- Duplicate and out-of-order fetches converge through an opt-in `updatedAt` stale-write guard in the shared order upsert. Shopify GID is the identity, not the display order name.
- Webhook order topics reuse the existing asynchronous delivery worker. Manual import, per-order refresh, and scheduled incremental reconciliation are intended to reuse the same `import_order()` funnel; refunds never create accounting or stock documents.
- `lineItems` and `refundLineItems` are real GraphQL Connections with `pageInfo`/`hasNextPage`: the current implementation rejects an order when either reports another page beyond its configured page size, and pagination support is intentionally deferred for this grocery/small-retail scope. `Order.transactions` and `Order.refunds`, by contrast, are plain Shopify list fields (`[OrderTransaction!]!`/`[Refund!]!`) with no `pageInfo` at all — they are capped at `first: 50` in the query, but Shopify silently truncates past that with no detectable signal, so an order with more than 50 transactions or refunds would lose evidence with no error and no way to flag it today.
- **Fulfillment evidence (#178 part 2):** the line-item selection also requests `unfulfilledQuantity` (units not yet fulfilled) and `nonFulfillableQuantity` (units that cannot be fulfilled, e.g. refunded or tip-like), stored on `Marketplace Order Item` with a `fulfillment_quantities_known` flag (rows imported earlier read as unknown). A line has started fulfillment when `currentQuantity - unfulfilledQuantity > 0`. `displayFinancialStatus` values per shopify.dev: AUTHORIZED, EXPIRED, PAID, PARTIALLY_PAID, PENDING, VOIDED, REFUNDED, PARTIALLY_REFUNDED; a REFUNDED/PARTIALLY_REFUNDED order that is already linked to a non-Draft Sales Order is planned (refund evidence) instead of raising a sync error. **Unverified:** these field and status facts come from shopify.dev (internet), not this repo's docs, and were not checked against API 2026-07 or a live store; the access scope for these fields is expected to need only `read_orders`, which the custom app has been granted (Shopify does not document it explicitly for these `LineItem` fields; confirm on the first live query). The granted list is: read_customers, write_customers, write_draft_orders, read_draft_orders, write_inventory, read_inventory, write_locations, read_locations, read_markets_home, write_markets_home, write_order_edits, read_order_edits, read_orders, write_orders, read_product_feeds, write_product_feeds, read_product_listings, write_product_listings, read_products, write_products, read_payment_terms, read_shopify_payments_accounts, customer_read_orders, customer_write_orders, unauthenticated_read_product_inventory. No fulfillment-order scope (`read_assigned_fulfillment_orders` / `read_merchant_managed_fulfillment_orders`) is granted, so `FulfillmentOrder` queries are out of scope; whether `unfulfilledQuantity` includes `nonFulfillableQuantity` units is not documented.
- **Full refund before fulfillment:** Shopify can fully refund an order without cancelling it (`cancelledAt` empty, financial status `REFUNDED`, fulfillment status `UNFULFILLED` on API 2026-07, `FULFILLMENT_NOT_REQUIRED` from API 2026-10 on, which is the pinned version now), after which its current quantities, shipping and totals are all zero. The Shopify evidence builder then reports `cancellation: "full"` (so the stored baseline decides and a shipping charge on the Sales Order no longer blocks as a shipping diff) only when ALL hold: `cancelled_at` is empty; `external_financial_status == "REFUNDED"`; the order has lines and every `current_quantity` is 0; `order_total`, `shipping_total`, `total_taxes` and `duties_total` are all 0; and `external_fulfillment_status` (the stored raw `displayFulfillmentStatus` enum) is `UNFULFILLED` or `FULFILLMENT_NOT_REQUIRED`; and no refund line has `restockType` `RETURN`, and the refunds JSON is readable (see below). External information (shopify.dev, internet, checked 2026-10-11, not this repo's docs): on API 2026-07 (the version pinned before the 2026-10 bump) such an order reports `UNFULFILLED`; `FULFILLMENT_NOT_REQUIRED` ("The order has no items to be fulfilled") is only returned from API 2026-10 on (https://shopify.dev/changelog/posts/orderdisplayfulfillmentstatus-now-returns-fulfillmentnotrequired.md: "Earlier versions are unchanged and still return UNFULFILLED for these orders"; https://shopify.dev/docs/api/admin-graphql/2026-10/enums/OrderDisplayFulfillmentStatus). Both stay in the allowlist so the rule is right now and after a version bump. Every other value, e.g. `PARTIALLY_FULFILLED`, `FULFILLED`, `IN_PROGRESS`, `ON_HOLD`, `SCHEDULED`, keeps the conservative behavior. The usual cancellation rules then apply: delivered -> compensating transaction, billed or advance payment -> Needs Attention, otherwise the Sales Order is cancelled (a Closed one is reopened first); no replacement Sales Order is created and the refunds JSON is untouched. **Return guard:** if any `refundLineItems` node across the order's refunds has `restockType` `RETURN`, the order is never auto-cancelled (evidence stays as before). External information (shopify.dev, internet, checked 2026-10-11, https://shopify.dev/docs/api/admin-graphql/2026-07/enums/RefundLineItemRestockType): `RETURN` = the line was returned (restocking items that were fulfilled), `CANCEL` = canceled (restocking unfulfilled items), `NO_RESTOCK` = not restocked, `LEGACY_RESTOCK` deprecated. `CANCEL`, `NO_RESTOCK`, refunds without line items (money-only, shipping-only), lines without a restock type and legacy rows allow the auto-cancel; a refunds value that is present but unreadable (corrupt JSON, not a list) counts as not eligible. The blocked set is the module constant `_BLOCKING_RESTOCK_TYPES`, so a stricter CANCEL-only rule is a one-line change. **Residual risk:** Shopify documents these statuses as "fully refunded before any items shipped" but never documents the opposite case, so an order whose fulfillment was cancelled in Shopify and then refunded while the goods are physically out could still pass; the safeguards are the `RETURN` guard and, on the ERPNext side, delivered -> compensating transaction, billed or advance payment -> Needs Attention. A never-synced fully refunded order (same test) is the terminal skip described below; if the test fails (e.g. `PARTIALLY_REFUNDED`, a `RETURN` line) it still blocks with "not financially eligible". **Policy summary (auto-cancel on a full refund):** it runs only when the order is fully refunded including shipping and taxes, nothing was fulfilled, ERPNext has no submitted OR draft Delivery Note, Sales Invoice or Payment Entry for the Sales Order, and no advance payment exists; a `RETURN` refund line means manual review; `NO_RESTOCK` is never treated as evidence of delivery; anything uncertain is Needs Attention. **Draft documents hold the cancel:** ERPNext would cancel a Sales Order that still has a draft Delivery Note or Payment Entry (leaving the draft pointing at a cancelled order) and rejects one with a draft Sales Invoice with a generic error, so a `CANCEL_ORDER` plan (full refund, or any other marketplace cancellation) that finds such drafts is not executed: the order shows Modified After Sync with "The marketplace cancelled or refunded this order, but ERPNext has draft documents for it (Delivery Note X; Payment Entry Y). The Sales Order was not cancelled. Submit, cancel or delete those documents, then run the update again." (up to 3 names per type, then "and more"). Once the drafts are gone (deleted or cancelled), the next sync cancels the order; a submitted one follows the delivered/billed rules. Close-remainder and update plans are not affected.

Source: [Order object](https://shopify.dev/docs/api/admin-graphql/latest/objects/Order), [LineItem object](https://shopify.dev/docs/api/admin-graphql/latest/objects/LineItem) - verified against shopify.dev on 2026-09-27 (external source, approved for #109's locked plan).

### Customer and address evidence (#126)

**Buyer name from the addresses:** the order query also requests `firstName` and `lastName` on `shippingAddress` and `billingAddress` (`MailingAddress` fields confirmed on shopify.dev by the user; `name` was not confirmed and is not requested). The mapper fills a BLANK `customer_first_name` / `customer_last_name` from the shipping address, then the billing address; a non-blank value from `customer` always wins. Phone-only buyers and draft orders often have no customer name while the address carries one. Whether protected-customer-data access (verified 2026-09-28 for the other customer and address fields) also covers these two address fields is unconfirmed; if Shopify rejects them, `orders.py::_execute_order_query()` retries the same query ONCE without those two address fields (`_ORDER_QUERY_WITHOUT_ADDRESS_NAMES`, derived from the one query text; the customer block keeps its names) when the GraphQL error mentions `firstName` or `lastName`, and writes one Error Log "Shopify order query retried without address names" (no personal data). The decision is not cached: every import tries the full query first. Every re-pulled order is saved once, because `latest_payload`, `shipping_address` and `billing_address` now carry `firstName`/`lastName` (and a blank buyer name may be filled); harmless: none of it is in the Sales Order snapshot or hash and no sync is triggered.

Order imports request the Shopify customer identity, name, default email and phone, plus billing and shipping addresses. The mapper stores both raw address objects and derives the customer address fields (city/latitude/longitude/formatted) from shipping when present, otherwise billing; absent customer/address/contact data remains blank. `customer_phone_number` has its own, independent fallback: `customer.defaultPhoneNumber.phoneNumber`, then `shippingAddress.phone`, then `billingAddress.phone` (first non-blank, whitespace-stripped, value wins) - this matters because a guest checkout (or an account order) commonly leaves the customer's own phone null while the address still carries one, and because it can pick a different address than the one `_resolve_shopify_address()` selects for the Shopify Address record (see below).

For Shopify Sales Orders (#110), a nonblank buyer email resolves or creates an Individual ERPNext Customer by `email_id`, using the buyer's name and phone when available. Orders with blank email use the generic Marketplace Account Customer. Talabat continues to use that generic Customer and does not create Shopify-derived Address records.

For a Shopify buyer with a nonblank email, Sales Order sync creates or updates one dedicated ERPNext Address PER ORDER, titled `Shopify Marketplace Address-<hash>` (a stable hash of the Customer and the Marketplace Order, used to find-or-update that order's Address without repurposing any other Address), linked to that Customer. Two orders of one buyer therefore have two Addresses, and a correction of one never changes the other order or its Delivery Note. An order already linked to a Sales Order is frozen on the Address that Sales Order points to (orders synced before this change keep their old customer-wide Address). It uses the order's shipping address, falling back to billing only when shipping is null; existing unrelated Customer-linked Addresses are never repurposed. The Address is marked primary only when the Customer has no primary Address yet, and its type is Shipping or Billing according to the selected source. Shopify country values are assigned as-is when an exact `Country` record exists; otherwise `Address.country` (a mandatory ERPNext field) defaults to `"Egypt"` with a concise PII-free warning logged, rather than being left blank. Missing usable address data leaves the Sales Order address fields to ERPNext's defaults. Address lookup/write failures do not block Customer or Sales Order sync (a transient deadlock or lock wait is re-raised for the sync retry); an Error Log "Shopify buyer Address could not be saved" (no personal data) is written. KNOWN RISK, accepted by the user: when the order's own Address cannot be saved, ERPNext's `get_party_shipping_address` may fill the Sales Order with ANOTHER Address of the same Customer (the buyer's only Shipping Address), so a repeat buyer's order can carry an older address. Spot it by comparing the Sales Order address with the Marketplace Order `shipping_address`. On a new order `customer_address` is ERPNext's default (the buyer's first/primary Address), so print layouts show it; Bosta does not read it. When an Address is created, its `email_id` is the order's `customer_email` and its `phone` is the cleaned `customer_phone_number` (`clean_phone_number`). A frozen order's Address is NOT updated by a later Shopify change (after submit, correct it in ERPNext); Bosta then combines the frozen street with the live province code from the Marketplace Order JSON, with no warning (known limit). Open unshipped Delivery Notes and Sales Orders of repeat email buyers created before the per-order change still point to the old shared Address (the last pre-deploy order's address): check them before sending.

Buyer phone on the Sales Order (#277): Sales Order sync copies `Marketplace Order.customer_phone_number` into the Shopify Sales Order's `contact_mobile` (Mobile No), but only while that field is empty, so a number staff typed is never overwritten by a later sync. The phone is not part of the snapshot, so it does not feed the hash and never causes "Modified After Sync". `Sales Order.contact_mobile` is read-only and not allowed on submit in ERPNext; two Property Setters in `fixtures/property_setter.json` make it editable on drafts and submitted orders. ERPNext does not overwrite it on save: it has no `fetch_from`, and its server-side party defaults only fill it when it is missing; the standard form only clears it in the browser when the Customer is changed. The patch `backfill_shopify_sales_order_contact_mobile` fills existing Shopify-linked Sales Orders whose `contact_mobile` is empty (it also touches submitted orders, via `db.set_value`, without changing `modified`). The Bosta Create dialog prefills the receiver phone from `contact_mobile`/`contact_phone`, falling back to the Marketplace Order buyer phone.

Shipping data for carrier integrations (#156): the Address `state` now takes the Shopify `province` (the city stays in `city`). The order query also requests `provinceCode`, `countryCodeV2` and `phone` on `shippingAddress`/`billingAddress` (stored in the raw address JSON; `phone` also feeds `customer_phone_number` when the customer's own `defaultPhoneNumber` is blank - shipping checked before billing, independently of which address `_resolve_shopify_address()` picks for the Address record itself), plus `requiresShipping`, `retailLocation { id name }` and `shippingLines(first: 10)` (`title code source carrierIdentifier deliveryCategory phone originalPriceSet`). `ShippingLine` is a connection, so it needs a page size: `SHOPIFY_ORDER_SHIPPING_LINES_PAGE_SIZE = 10` (an order has about one shipping line, rarely one per fulfilment origin), with the same rule as the other connections (more than one page marks the order Error). The mapper stores `{requiresShipping, retailLocation, shippingLines}` in the read-only JSON field `Marketplace Order.shipping_lines`; it stays empty when the order has no shipping lines, does not require shipping and has no retail location, and for orders stored before this change until they are re-imported. No delivery/pickup classification is done. Field names were checked on shopify.dev on 2026-10-16, not against a live store: copy a real payload from a store with a shipping app before relying on `carrierIdentifier`/`deliveryCategory`. Neither the Address nor the new fields enter the Sales Order snapshot or the evidence fingerprint, so existing orders do not become Modified After Sync.

## Outbound order cancellation (#182)

`services/marketplace_outbound.py::request_platform_cancel()` dispatches Shopify orders to `integrations/shopify/orders.py::cancel_order()`. The merchant selects one of Shopify's six `OrderCancelReason` values (`CUSTOMER`, `DECLINED`, `FRAUD`, `INVENTORY`, `OTHER`, `STAFF`). Local eligibility blocks an order already marked cancelled, an evident authorization hold, any line whose fulfillment has started, and any line whose fulfillment state is unknown. Shopify remains responsible for rejecting an active return or its own fulfillment restriction through mutation user errors.

The adapter calls `orderCancel` through `ShopifyClient.execute()`, explicitly sends `restock: false` and `notifyCustomer: false`, and omits `refundMethod` (ERPNext does not issue an automatic refund; the merchant handles any refund in Shopify). Shopify also accepts optional `refundMethod` and `staffNote` (up to 255 characters); this flow does not send either. `OrderCancelPayload` has no returned order: after accepting the mutation the service persists its echo marker, then follows the JobResult behavior below before refreshing the Marketplace Order by GID with `orders.import_order()`. A returned mutation error or missing JobResult is logged as an `Order Action` Error before the error reaches the caller. The scheduled reconciliation sweep skips a marked Shopify order only after its `cancelled_at` echo is stored; a marked order that still appears active reaches the existing Modified After Sync path.

The API 2026-10 adapter requests `jobResult { id }`, then polls that ID through `node(id:)` with an inline fragment on `OrderCancelJobResult` (`done`, `status`, and `errors { field message code }`). It makes at most three polls, two seconds apart. `SUCCEEDED` proceeds to the normal order refresh; a confirmed `FAILED` clears the marker using `clear_outbound_cancelled_marker()` and records an `Order Action` Error; a still-started/unknown result or polling query failure keeps the marker and does not refresh, preventing an unsafe duplicate request. Mutation-level `orderCancelUserErrors`, including missing-scope errors, are treated as pre-acceptance failures and leave the marker unset. Top-level GraphQL errors are raised by `ShopifyClient.execute()` and handled by the caller.

**Pending verification before production use:** re-confirm that the installed custom app's live scopes include `write_orders` (or an equivalent marketplace-order write scope); the local granted-scope record is not proof of the live scope. Also unverified from shopify.dev: the effect of omitting `refundMethod` on captured payments, whether an API cancellation emits `orders/cancelled`, and the exact stock effect of `restock: false`. Shopify's orderCancel documentation says authorized payments are voided even without a refund; verify that behavior on the dev store before relying on it operationally.

Source: [orderCancel mutation](https://shopify.dev/docs/api/admin-graphql/2026-10/mutations/orderCancel), [OrderCancelJobResult](https://shopify.dev/docs/api/admin-graphql/2026-10/objects/OrderCancelJobResult), [OrderCancelReason enum](https://shopify.dev/docs/api/admin-graphql/2026-10/enums/OrderCancelReason), [OrderCancelRefundMethodInput](https://shopify.dev/docs/api/admin-graphql/2026-10/input-objects/OrderCancelRefundMethodInput) — first checked 2026-10-08 and rechecked 2026-10-24 (external Shopify documentation, approved by the user for reliance). The `OrderCancelJobResult` type was added 2026-10-01; whether the mutation emits an `orders/cancelled` webhook and the listed refund/stock effects remain unverified.


## Item edits from ERPNext (#356)

`services/marketplace_outbound.py::send_shopify_order_edit()` calls `integrations/shopify/order_edit.py::commit_order_edit()`, which runs one synchronous order-edit session through `ShopifyClient.execute()`: `orderEditBegin`, then `orderEditSetQuantity` (with `restock: false`; quantity 0 removes a line) and `orderEditAddVariant` per change, then `orderEditCommit` with `notifyCustomer: false` and a staff note naming the Sales Order. Any `userErrors` aborts the sequence; an uncommitted session changes nothing on Shopify. If the commit call itself fails without a definitive answer the outcome is treated as unknown: the order's edit marker stays `in_flight`, no further edit is accepted, and the order shows Modified After Sync ("outcome unknown, check Shopify") until a System Manager has checked Shopify and cleared the marker with "Clear edit marker" on the Marketplace Order (see `docs/marketplace-integrations/architecture.md`). Orders whose lines carry discount allocations (`discountAllocations`) are not editable from ERPNext, because Shopify recalculates discounts when items change; edit them in Shopify.

**Edit Order (#500 part 2, epic #502).** For a submitted Shopify Sales Order the "Update Items" button is replaced by "Edit Order" (`services/order_edit.py`, `api/marketplace_outbound.py::{get_order_edit_preview,edit_order}`). The order is no longer edited first and sent after: the proposed quantities are checked (stage lock, the checks above on the proposed rows, a reservation dry run), sent through this same `send_shopify_order_edit` (marker, `commit_order_edit`, re-baseline), and ERPNext is changed in one transaction only after Shopify accepted. Quantity changes, removals and added items (priced from the account's Selling Price List, corrected to Shopify's price after the commit); rate edits of existing rows are not offered. Shopify rejecting the edit changes nothing in ERPNext (the marker is cleared as in #356). If the local transaction fails after Shopify committed, the marker stays `completed`, ERPNext is rolled back to its old state and the order is re-imported without re-baselining, so the reconciliation planner applies Shopify's quantities (Retry Sync does it at once). The old "Send item changes to Shopify" button and its endpoints were removed: the server refuses every item edit of a Shopify order that is not Edit Order or Shopify's own, so ERPNext's Update Items called directly is refused. Edit Order and a Shopify-originated change are also refused / held when the order has two draft Delivery Notes or a draft that does not ship the whole order. After pickup edits are refused, and a Shopify-originated change then goes to Needs Attention (`ORDER_LOCKED_BY_SHIPMENT`). Details: `docs/marketplace-integrations/delivery-note-first.md`.

`orderEditBegin` is asked for `calculatedOrder { id lineItems(first: 250) { nodes { id quantity variant { id } } pageInfo { hasNextPage } } }` (250 is the connection page maximum; an order with more lines fails closed). The app stores only original `LineItem` GIDs, but the edit mutations take `CalculatedLineItem` IDs, which belong to the session. The code rewrites the type segment (`.../LineItem/N` to `.../CalculatedLineItem/N`) and, before any mutation, requires the rewritten ID to be present in the session with `quantity` equal to the baseline quantity; otherwise it fails closed.

**To be verified on the dev store:** that a `CalculatedLineItem` ID has the same numeric part as the original `LineItem` ID. The first #356 implementation recorded this as observed in a development-store response (not re-checked here), but Shopify's documentation describes `CalculatedLineItem` IDs only as session IDs and does not promise it. The pre-mutation check above is the safety net, not proof. Also to confirm there: the app's live scopes include the order-edit write scope, and whether Shopify emits an `orders/edited` webhook for an API commit (the app does not rely on one; it re-imports the order right after the commit).

Sources (not re-read for this change): shopify.dev `orderEditBegin`, `orderEditSetQuantity`, `orderEditAddVariant`, `orderEditCommit`, `CalculatedLineItem`.

## Controlled Sales Order handoff (#110)

- Only Shopify orders with no `cancelled_at` and financial status `PAID` or `PARTIALLY_PAID` are eligible, plus (#216) a `PENDING` order paid by a manual method (COD, bank deposit, custom): at least one transaction with `status` `PENDING` and `manualPaymentGateway: true` (Admin API 2025-01+; the gateway name is never matched because merchants can rename it). Other `PENDING` orders (an online payment still processing) and `AUTHORIZED`, `VOIDED`, `EXPIRED` stay blocked, and the blocker message lists each transaction's `kind/status/gateway/manual`. When the merchant later marks a COD order paid, the Sales Order is unchanged (only line amounts are compared). **Unverified on this store:** whether its COD orders carry the flag; shopify.dev documents the field and a Shopify staff community answer says COD returns `true`, and a COD app with its own gateway may not set it. Sales Orders are created automatically from webhooks (#133) and manually from the form ("Send to ERPNext"); a fresh Sales Order is submitted immediately (#131), not left as a Draft.
- **Staff-created PENDING orders:** an order staff record in the Shopify admin (a draft order completed with payment due later) has `transactions: []`. It is eligible when it is `PENDING`, has no transactions and Shopify sent `paymentTerms` with a `paymentTermsType` (e.g. `RECEIPT`, "Due on receipt"); online payments still processing never carry payment terms, so they stay blocked. Without payment terms it is blocked with "No payment transactions were received." Production evidence (#24684 / MKTORD-00095, recorded by warehouse sales staff in the Shopify admin, refreshed 2026-10-19): `sourceName` `shopify_draft_order`, `app.name` `Draft Orders`, `paymentTerms` `RECEIPT` / "Due on receipt", `paymentGatewayNames` `[]`, `transactions` `[]`. `paymentTerms` is read from `latest_payload`, so an order imported before the field was queried needs "Refresh from Shopify" first, and a change to the terms alone does not trigger an automatic re-sync (use "Send to ERPNext"). Checkout COD orders are not affected. To find a signal for these orders, the order query also requests `sourceName`, `app { name }`, `paymentTerms { paymentTermsType paymentTermsName dueInDays }` and `paymentGatewayNames`. `paymentTerms` needs the `read_payment_terms` access scope (a live query without it returned "Access denied for paymentTerms field" and fails the whole order query), so it was added to the custom app on 2026-10-18; every store's app must grant it before this query is deployed there; they are kept only in `latest_payload` and do not change the snapshot or the evidence fingerprint; only `paymentTerms` affects eligibility (above). Field names come from shopify.dev (internet, `Order` object, API 2026-07, checked 2026-10-18; only `read_orders` is documented at object level). Shopify has no dedicated draft/staff-created flag on `Order`, and the values a mobile-app order carries are not documented: compare a re-fetched staff-created order with a checkout COD order before choosing the eligibility rule. Live check on the dev store (2026-10-18, not the production store): checkout COD orders return `sourceName` `web`, `app.name` `Online Store`, `paymentGatewayNames` `["Cash on Delivery (COD)"]` and a `SALE`/`PENDING` transaction with `manualPaymentGateway: true`; a draft order returned `sourceName` `shopify_draft_order`, `app.name` `Draft Orders`, `paymentGatewayNames` `["manual"]`. Whether a production order created from Shopify Mobile carries the same draft-order values is not confirmed yet.
- **Cancelled before a Sales Order exists:** a Shopify order with `cancelled_at`, or one that passes the full-refund test above, and no linked Sales Order is a terminal, successful skip, not a sync error: no Sales Order is created, `ERPNext Sync Status` stays `Not Synced` with the error cleared (so an earlier blocker, e.g. an unpaid COD order, no longer sticks), and one Success row is added to the Marketplace Sync Log (earlier rows are kept). Nothing retries it on a schedule. The patch `clear_cancelled_shopify_sync_errors` clears the obsolete Sync Error on orders already stuck this way. Cancelled with a linked submitted Sales Order follows the reconciliation planner (cancel if nothing delivered or billed, Needs Attention if delivered or billed); with a linked Draft Sales Order the order is blocked with a message naming the Draft to delete or cancel by hand. The blocker for a PENDING order shows `manual=unknown` when the stored transactions predate the manual-payment fields: use "Refresh from Shopify" once.
- Each line resolves only through the exact `(Marketplace Account, external_variant_id)` mapping. A missing mapping, null variant, missing transaction amount, or fully refunded line blocks the whole order; no partial Sales Order is created.
- The line rate is `priceAfterAllDiscountsBeforeTaxesSet.shopMoney.amount / currentQuantity`, rounded to the existing six-decimal effective-rate precision. The stored `transaction_amount` equals `net_amount`.
- The existing snapshot/hash/idempotency flow is reused. Later Item Price changes do not change an already synchronized Shopify-derived rate; reprocessing updates the same Sales Order rather than creating a duplicate.
- The handoff creates a Sales Order that is submitted when created (#131); a still-Draft one left from before is updated in place. Taxes, duties, refunds, payouts, invoices, payments, GL entries, Delivery Notes, and Stock Entries remain outside this issue.
- **Shopify payment mirroring (#230, #231):** every Sales Order sync attempt for a Shopify order with a linked submitted Sales Order automatically attempts one submitted Receive Payment Entry per transaction of kind `SALE` or `CAPTURE` with status `SUCCESS` (it does not touch AUTHORIZATION, PENDING, FAILURE, VOID or REFUND). Payment work uses independent per-transaction savepoints and `Payment` Sync Log rows; a payment failure does not change the Sales Order sync result or status. If the user running the sync lacks Payment Entry Create or Submit permission, each eligible transaction is logged Invalid and appears as Payment Error in Marketplace Needs Attention. A change to a successful transaction's gateway, amount, currency or date changes the import debounce fingerprint, but does not change the Sales Order snapshot hash. The `ORDERS_PAID` webhook already imports and debounces the order; no new webhook topic was added. ERPNext's financial state is visible through Payment Entries, including any unallocated excess.
  - **Gateway mapping:** Marketplace Account (Shopify) has a table **Shopify Payment Gateways** (child doctype `Shopify Payment Gateway Mapping`): the exact `gateway` string Shopify sends (trimmed on save; one row per trimmed value), the Mode of Payment, and the Clearing Account. The match is exact on the trimmed string; a renamed gateway is unmapped and blocks with a message naming it. The Clearing Account must exist, belong to the Company, be a leaf, enabled, in the Company currency and of account type Bank or Cash (the types ERPNext offers for `paid_to` on a Receive entry, checked on Frappe/ERPNext 16.51/16.50; ERPNext enforces this only in the Desk picker, so `clearing_account_problem()` enforces it on save and again when the payment is mirrored).
  - **Amount and date:** the transaction's `amountSet.shopMoney.amount` (never `order_total`), whose currency must equal the Company currency. `posting_date` and `reference_date` are the `processedAt` date in site time, falling back to `createdAt`; `reference_no` is the transaction id.
  - **Allocation:** to the order's one submitted, non-return Sales Invoice if there is one (more than one blocks), otherwise to the Sales Order as an advance. The allocated amount is the lower of the payment and the outstanding; anything beyond that stays on the same entry as an unallocated amount and is named (with the amount) in the Success log row. The receivable account (or the invoice's debit-to) and the Clearing Account must be in the Company currency, otherwise the transaction blocks.
  - **Rounding:** the Sales Order outstanding ERPNext accepts is `rounded_total` (else `grand_total`) minus `advance_paid`, not `grand_total`: with rounded totals on (Global Defaults "Disable Rounded Total" off, the default) a Shopify total of 494.21 gives a rounded total of 494. ERPNext rejects an allocation above that, so the `grand_total - rounded_total` difference (at most) is written off with a Payment Entry deduction row to the Company's **Round Off Account** (and Round Off Cost Center), and the entry still has no unallocated amount for pure rounding. It works both ways: a 494.60 total rounded up to 495 gets a +0.40 deduction so the Sales Order is fully paid. Verified on ERPNext 16.50: the entry submits, `difference_amount` is 0 and the GL balances. If the Company has no Round Off Account the transaction blocks, naming the missing setting; the write-off applies only to a Sales Order target (an invoice's outstanding is already rounded) and only while the order still has an outstanding.
  - **Idempotency:** the Payment Entry custom fields `custom_marketplace_order` and `custom_marketplace_transaction_id` (unique, `no_copy`, read-only; fixtures) identify the mirrored entry. A transaction id that already has an entry in any docstatus is skipped, so a cancelled entry is never re-created. Frappe's Desk Amend ignores `no_copy` (it copies every field), so an amended draft of a mirrored entry carries the same id and cannot be saved while the cancelled one exists: **mirrored Payment Entries cannot be amended in Desk** (cancel and, if needed, record the payment by hand).
  - **Duplicate guard (#425):** before creating an entry, `manual_payment_totals()` sums the submitted Receive Payment Entries allocated to the same Sales Order or to its submitted Sales Invoices. Entries that carry a `custom_marketplace_transaction_id` (mirrored ones) are not counted, so the separate transactions of a split payment never block each other; an entry's allocations to the order and to its invoices are added up. The total must be positive and at least the transaction amount minus the Sales Order's rounded-down difference (`grand_total - rounded_total` when positive: Shopify 494.21 against a rounded total of 494 needs 494, since no manual entry can allocate more than the rounded total). Then no second entry is created and an Invalid log row ("A submitted Payment Entry already covers ...") makes the order show in Needs Attention; the row also records the Sales Order and the required amount, and Needs Attention lists it only while a manual entry still covers that amount (it disappears once the entry is cancelled or no longer covers it). Any repeated Invalid result (not only this one) adds no second log row while it is identical to the latest one. One manual entry covering several transactions blocks each of them. Refunds stay manual: there is no refund or cancel guard.
  - **Retry (#425):** a payment that ended Error with a transient failure (`is_transient_failure()`: deadlock, lock wait, timeout, HTTP 5xx or 429; the Error row records `transient: true`) is retried by the minute sweep `sweep_due_sales_order_syncs` (`_enqueue_payment_retries`), one attempt per sweep run. Retries are counted as the trailing run of consecutive Error rows for the order and transaction, with no time limit, ending at the first non-Error row; at most 3 retries (`PAYMENT_RETRY_ATTEMPTS`) follow the original failure, then the last Error row stays for a person. The 60-minute window (`PAYMENT_RETRY_WINDOW_MINUTES`) only requires the first Error of that run to be recent. A non-transient failure (a generic bug) gets one Error row and is never retried; Invalid rows are not retried, with one exception: a duplicate-guard Invalid row (the one recording `guard_sales_order` and `guard_required`) that is still the latest Payment row of its transaction is retried, with no time limit, once the guard no longer blocks (the covering manual entry was cancelled or no longer covers; the same coverage rule as Needs Attention) and the transaction is still a pending successful SALE/CAPTURE without a Payment Entry. The re-run writes a Success row or a new row, which ends the candidate state, so it cannot loop; if it is blocked again with the same message no row is added, but then the guard blocks and the row is no longer a candidate. A candidate whose Marketplace Order has no submitted Sales Order is skipped, so no useless job is queued. A retry runs only the payment step for the failing transaction ids, so the Sales Order sync status, debounce and retry counter are untouched and the order's other pending transactions are not re-attempted.
  - **Logging:** one `Marketplace Sync Log` row (sync type `Payment`) per attempted transaction: Success, Invalid (a blocker such as an unmapped gateway, currency mismatch, closed or cancelled Sales Order, several invoices, an existing covering Payment Entry, or a `PermissionError` raised while creating the entry, which is logged before it is re-raised) or Error. The transaction id is in `request_data`. An order with no Sales Order yet returns with no log row.
  - **Needs Attention (#231):** Payment Error rows remain until a later Payment Success for the same order and transaction; Payment Excess is live while a submitted mirrored entry has an unallocated amount; every cancelled mirrored Payment Entry stays visible until a submitted amendment of it exists (`amended_from`) or (#425) another submitted manual Payment Entry (same helper as the duplicate guard) covers the same Sales Order or invoice for at least the amount the cancelled entry allocated (`total_allocated_amount`, which already contains its rounding write-off; `paid_amount` only when it allocated nothing), which clears the row. When an order has several cancelled entries, the manual total must cover the sum of their amounts (without those already amended), so a manual entry for only part of a split payment clears none of the rows. That sum is read without permission scoping (only sums and ids are used; the rows listed stay the ones the user may read), so whether a row clears does not depend on who is looking. A duplicate-guard Payment Error row is listed only while the guard would still block (see above). Open point: Desk's Amend copies the unique `custom_marketplace_transaction_id` onto the amended draft, so that draft cannot be saved while the cancelled entry exists (see `docs/frappe-conventions.md`, Tests); how staff are meant to amend such an entry is not settled. If payment still needs recording, record it manually in ERPNext. A marketplace quantity/price reduction that would put the Sales Order total below `advance_paid` is held for manual reallocation or cancellation of the advance.
- **Gateway discovery (#347):** the Marketplace Account's Shopify Payment Gateways section has a manual "Load Shopify Payment Gateways" button. It reads at most the 500 newest local Shopify orders for that account, then lists distinct exact `gateway` names from successful SALE/CAPTURE transactions, their order count, and whether each is already mapped. It only fills `shopify_gateway` for selected unmapped rows; users still enter Mode of Payment and Clearing Account and save the account themselves. Values can also be typed. Shopify's `formattedGateway` is stored on future refreshes but is not used for matching or shown in the picker. The action requires Marketplace Account write and Marketplace Order read permission; a failed request displays a scoped message and can be retried.
- **Retrying a failed sync:** a blocker (status `Invalid` in the Marketplace Sync Log: missing or disabled mapping, unusable Selling Price List, taxes or duties, total mismatch) is retried from the order form's `Send to ERPNext` / `Update ERPNext Order` button after the cause is fixed. The Sync Log list's `Retry Selected Errors` button retries only `Error` rows (unexpected exceptions) that have a Marketplace Order, and reports how many recovered and how many are still blocked. An unexpected exception during Sales Order creation rolls the half-created Draft back, so a retry never leaves a second Sales Order.
- **Order retrieval date range:** the Shopify order retrieval dialog sends the start date as `T00:00:00Z` and the end date as `T23:59:59Z`. The 60-day limit is measured between those two instants (whole days, rounded down), so the dialog accepts up to 61 inclusive calendar days (for example 2026-01-01 to 2026-03-02) and rejects 62.
- **Shipping charge:** `currentShippingPriceSet` (Marketplace Order `shipping_total`, already after shipping discounts and refunds; per shopify.dev (internet, https://shopify.dev/docs/api/admin-graphql/2026-07/objects/Order) it includes tax when `taxesIncluded` is true, which does not matter today because the sync blocks on any non-zero tax) becomes one `Sales Taxes and Charges` row on the Sales Order: charge type `Actual`, description `Shipping`, amount `shipping_total`, account head from the new Marketplace Account field **ERPNext Shipping Income Account** (`erpnext_shipping_account`, Shopify only; no cost center set, ERPNext defaults apply). The account must belong to the account's company, be a leaf, enabled, and have root type Income or account type Tax/Chargeable; there is no fallback to the Company default income account. It is only required when an order has shipping above zero; without it the order blocks with a message naming the Marketplace Account. The snapshot carries the amount under a top-level `shipping` key, omitted when zero (so Talabat, Noon and free-shipping snapshots and hashes are unchanged); the account is read at apply time and is not part of the snapshot. ERPNext spreads an `Actual` charge over the items by value, so an order whose items are all free with shipping above zero blocks instead.
- **Taxes and duties block:** an order with `total_taxes` or `duties_total` other than zero is blocked ("Taxes and duties are not synced to ERPNext yet"); handle it in ERPNext by hand. This includes tax-inclusive stores whose prices already contain tax. The block applies only while a Sales Order is being created or a Draft one updated. An order already linked to a SUBMITTED Sales Order (including legacy orders synced before this block existed) is not blocked and does not flip to Modified After Sync because of tax; the reconciliation planner decides as for any other order.
- **Total check:** before saving, the Sales Order `grand_total` (not `rounded_total`) must equal Shopify's `order_total` (`currentTotalPriceSet`) within one currency-precision unit, otherwise the order blocks with "Shopify total X does not match the Sales Order total Y (items A + shipping B)". Nothing is forced to match with adjustment rows. The check is skipped only for a free order (`order_total` 0, no shipping, every item free). If `order_total` is missing/0 but the items or shipping are not, the order blocks with "Shopify's order total was not recorded" (rows imported before totals were stored): use Refresh from Shopify, then sync again. COD behavior is unchanged: a PENDING manual-payment order still syncs, with no Payment Entry or Sales Invoice.
- **Sales Invoice for paid orders (bulk Delivery Note action, `services/bulk_delivery_notes.py`):** the sync itself never creates invoices. When staff ship a Shopify Sales Order from the list with Actions > Delivery Note, an order that is fully paid by ERPNext's own measure (nothing outstanding on `rounded_total`, else `grand_total`, minus `advance_paid`; ERPNext caps the recorded payment at the rounded total, so 494 paid on a 494.21 order is fully paid) first gets a Sales Invoice made with ERPNext's `make_sales_invoice` (`update_stock` 0, `allocate_advances_automatically` and `only_include_allocated_payments` turned on: the mapper only fetches advances when the first is on, and the second keeps an unrelated payment of the same Customer out), submitted, and checked after submit and reload to end with outstanding 0 (the totals right after `insert` are not trusted: ERPNext totals the invoice before it allocates the advances); the mirrored Payment Entries move from the order to the invoice natively. A manual payment of exactly `grand_total` on an order whose `rounded_total` is higher leaves only a rounding difference outstanding; such an order is refused with a reason (nothing is shipped) until the difference is settled. The amount to collect from the customer stays based on `grand_total`. An invoice that already exists is reused, never duplicated, only if it covers the whole order and has no credit note. The Bosta COD is then 0; an unpaid order ships with COD = `grand_total`, and a partly paid one (a rule decided by the user) with `grand_total` minus the paid amount and no invoice. See `docs/marketplace-integrations/delivery-note-first.md`, "Bulk path". Later Shopify payments are allocated to that invoice by the existing allocation rule above.
- **Orders already synced without shipping:** the new `shipping` key makes the reconciliation planner report a submitted order whose stored baseline lacks it as Needs Attention ("The shipping charge differs from the submitted Sales Order ... cancel and amend it"); nothing is changed automatically. A shipping refund or change after submit follows the same path. **Known limit:** the advised remedy, cancelling and amending the Sales Order in ERPNext, does not clear the status today: the Marketplace Order keeps its link to the cancelled order, so it then shows "The linked ERPNext Sales Order is no longer an active submitted document." and the amended document is never adopted (no relink exists; follow-up). A Draft Sales Order is updated in place on the next sync.

## Known limits

- **Unlinked-order recovery (#354).** A new Shopify order whose webhook never arrives, or whose first Sales Order sync fails transiently, is retried only by the nightly 23:59 catch-up (once per night per order, see "Order cancellation and nightly catch-up"), a new webhook for it, or the "Send to ERPNext" button. The hourly sweeps still do not schedule it. The nightly catch-up has no age or date cutoff yet (open decision): every unlinked, non-`Cancelled` order of the account is scheduled again each night. Needs Attention lists such orders as Sync Error with Retry. The reconciliation sweeps only look at orders that already have a linked Sales Order.
- **HTTP 429/5xx are not retried.** `ShopifyClient.execute()` retries a GraphQL `THROTTLED` response (HTTP 200 with `errors[]`, bounded by `MAX_THROTTLE_ATTEMPTS`) but any non-2xx response other than a single 401 token refresh raises immediately ("Shopify GraphQL request failed"), including HTTP 429 and 5xx. Hardening gap, not changed. Webhook deliveries are covered by the hourly errored-delivery sweep; inventory chunks are re-covered by the next sweep tick.
- **Unused webhook headers.** `X-Shopify-Event-Id` and `X-Shopify-Triggered-At` are sent by Shopify but not used; deduplication is by `X-Shopify-Webhook-Id` only, and ordering by the order's `updatedAt` from the refetch.

## Open questions

`Shopify Connection` + `ShopifyClient` are now built (#101), and the Admin GraphQL `execute()` layer on top of it is now built (#102). What those issues settled and what's still open:

Settled by #101:

- Token refresh trigger: **proactive refresh before expiry**, mirroring `TalabatClient`'s safety-buffer pattern (`ttl = expires_in - EXPIRY_BUFFER_SECONDS`, cached per connection). The shared token-fetch/expiry-buffer math itself lives in `integrations/http.py`'s `fetch_client_credentials_token()`, used by both `ShopifyClient` and `TalabatClient`.
- `shop_domain` validation: `Shopify Connection.validate()` requires a bare hostname — only `[A-Za-z0-9.-]`, not starting/ending with a dot, no scheme/path/whitespace/port/userinfo/query/fragment. This is stricter than an earlier version that only blocked `://` and `/`, which still let an `@` through and made `get_store_base_url()` (a plain `https://` string prefix) vulnerable to userinfo/host confusion (e.g. `shop.myshopify.com@attacker.example` resolving to `attacker.example`, silently sending the client secret there). Deliberately does **not** hardcode a `.myshopify.com` suffix — see the still-open domain-format question below.

Settled by #102:

- Reactive token refresh: `ShopifyClient.execute()` retries exactly once on a 401 (`invalidate_access_token()` then re-fetch), mirroring `TalabatClient.request()`'s contract. A second 401 raises.
- `enabled` flag enforcement: `execute()` — the first real caller of `ShopifyClient` — now checks `Shopify Connection.enabled` and throws if disabled, closing the gap #101 deliberately left open.
- Throttle handling: bounded backoff honoring `errors[0].extensions.retryAfter`, capped at `MAX_THROTTLE_ATTEMPTS = 3` attempts — no bucket-capacity tracking.
- Error shape handling: a non-empty top-level `errors[]` (non-throttle) raises; per-mutation `userErrors` are returned to the caller inside `data`, never inspected or swallowed.

Settled by #104:

- Webhook transport/auth: a single whitelisted, guest-accessible endpoint (`api/shopify_webhooks.py::webhook_event()`) handles every subscribed topic, authenticated by `X-Shopify-Hmac-Sha256` over the raw body (never the reparsed/reserialized body).
- Dual-secret rotation handling: `verify_shopify_hmac()` accepts either the connection's current `client_secret` or its `previous_client_secret`, matching Shopify's "signs with the oldest unrevoked secret" behavior during a rotation window — this was an open question above and is now implemented, not just documented.
- Subscription management is a mutation, so it stays behind an explicit user-triggered action (`sync_webhook_subscriptions()`, the Shopify Connection "Sync Webhook Subscriptions" button) — never run automatically on save, unlike #103's read-only live checks.
- Deduplication: `Shopify Webhook Delivery.webhook_id` carries a DB-level `unique: 1` index (checked via `UniqueValidationError` on insert, not a check-then-insert read) — Shopify's at-least-once delivery guarantee means the same `webhook_id` can arrive more than once.
- Retry-ability of a failed delivery: neither a Shopify redelivery nor the "responds 200 immediately" requirement give up on a delivery whose async processing later failed — a non-`Processed` row is reprocessed in place (by a Shopify redelivery hitting the same `webhook_id`, or by the scheduled `retry_errored_webhook_deliveries()` sweep when no redelivery is coming), bounded by a simple `attempt_count` cutoff rather than retried forever.

Still open:

- Exact scopes needed — depends on which resources later catalog/order work will touch (not decided yet). Recommended set: `read_locations` (required by #103's Location-loading query — confirmed via a live "Access denied for name field" error, not something we predicted), `read_products`/`write_products`, `read_inventory`/`write_inventory`, `read_orders` (not `read_all_orders`, per #99's locked decisions).
- Whether the store domain format needed is `{store}.myshopify.com` or a custom domain — confirm against the specific store's Shopify admin before hardcoding validation. `shop_domain` currently accepts either shape.

Settled (research only, not yet acted on in #100):

- **App install flow**: in Dev Dashboard, open the app → Installs → Install app → pick the store (if the org has more than one) → Install. No OAuth approval screen.
- **Org-access caveat**: a custom app can only be installed on stores in the *same Shopify organization* as the Dev Dashboard account creating it. A known limitation: collaborator-level "Develop apps" access doesn't work with the new Dev Dashboard flow — installing needs org-level access, not just store-collaborator access. Confirm this before #100 hits a wall partway through.

Source: [Installing and setting up apps](https://help.shopify.com/en/manual/apps/install-setup-apps), [Collaborator "Develop apps" permission issue](https://community.shopify.dev/t/collaborator-develop-apps-permission-is-useless-with-new-dev-dashboard-jan-2026-cant-install-custom-app-on-clients-store/29171).

# Order cancellation and nightly catch-up

An unlinked Shopify order canceled before a Sales Order exists is marked
`Cancelled` when it is unpaid or fully refunded. If it was paid or only
partially refunded, it stays `Sync Error` with an instruction to finish the
refund in Shopify. Later Shopify imports preserve the terminal `Cancelled`
state for unlinked canceled orders. Linked orders continue through the normal
Sales Order reconciliation path.

Shopify order reconciliation runs once a night per account (#478): a nightly
coordinator queues one deduplicated long job (3600 s) per enabled
Shopify or Noon account at `23:59` site time. There is no separate `daily`
scheduler entry for it any more (it used to overlap this job on the default
queue with a 300 s timeout). The nightly Shopify job reconciles
linked-order changes, schedules the first sync of every order it inserts
(cancelled or not) and opts into unlinked-order catch-up. A lock wait timeout
(1205) on one order is retried up to 3 times in the same run, 2 s apart, before
the order is logged as a failure; an RQ job timeout is never caught per order
or per account, so it fails the job visibly. Shopify reuses its persisted watermark
and overlap; Noon reuses its seven-day import window. Imports update
Marketplace Orders and schedule the existing debounce sync; they do not create
Sales Orders inline. Every order an import creates is scheduled for its first
sync, even when it is already cancelled, voided or fully refunded (the sync then
settles it as `Cancelled` or `Needs Action`); an existing order is scheduled
again only when it is unlinked, still `Syncing` and has no pending window. The
hourly stuck sweep also picks up a cancelled order left `Syncing` without a
window. Each account's run writes one `Marketplace Sync Log` row
(sync type Order Import, trigger source Scheduled Reconciliation) whose response
holds the orders imported, first syncs scheduled (including those the import
itself scheduled for newly inserted orders, cancelled ones too) and failures; an account that
raised records an Error row with the traceback. The Noon catch-up job has its
own job id, so the hourly Noon poll never runs it and is not deduplicated
against it. See `docs/user-actions.md` for scheduler restart and the
production timezone check.
