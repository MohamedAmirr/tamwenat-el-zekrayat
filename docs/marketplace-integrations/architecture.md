# marketplace_integrations: target architecture

This document is the high-level source of truth for the marketplace integration architecture chosen for Tamwenat El Zekrayat.

It describes the target model and the boundaries already agreed for the new `marketplace_integrations` app. It is intentionally not a platform API specification. Platform-specific endpoint/auth/payload behavior must come from that platform's checked-in documentation before implementation.

## Status and app lifecycle

- `apps/marketplace_integrations/` is the target shared marketplace app (tracked by #33). It is created/migrated incrementally; do not assume a file exists until its issue is implemented.
- `apps/talabat_integration/` was the legacy Talabat implementation. It has been fully migrated and removed from this repository under #8, after verifying equivalent behavior/data in the new app (patches ran, no live cross-references remained, and legacy data was stale). `docs/talabat-integration/architecture.md` remains as a frozen historical reference only.
- All new functionality, including Talabat-specific work, belongs in `marketplace_integrations`.
- Talabat API truth remains `docs/talabat-integration/openapi.json` plus its README. The shared architecture does not replace the platform contract.
- **Connection design decision:** each platform gets its own typed Connection DocType (`Talabat Connection`, `Shopify Connection`, and `Noon Connection`), not one shared generic Connection DocType. `Marketplace Account.connection_doctype` (Dynamic Link) is already the adapter point — it doesn't care which DocType a connection lives in, so a generic connection table adds nothing there and only risks cramming unrelated platforms' fields into one form (wrong-section visibility, cross-platform validation gaps, fields guessed ahead of a platform's real API docs). Build each platform's Connection DocType only when that platform's real API contract is scoped, following `Talabat Connection`'s shape.

- **`Marketplace Account`** (`marketplace_integrations/marketplace_integrations/doctype/marketplace_account/`) — one document per external seller/store/vendor account and its ERPNext inventory partition, the generalized replacement for legacy `Talabat Vendor`. Fields: `account_name`, `platform` (Select, `Talabat`/`Shopify` as of #103), `external_account_id` (`ignore_xss_filter: 1` — opaque, byte-preserving; for Shopify, the shop GID; `mandatory_depends_on: eval:doc.platform != "Shopify"`, not a plain `reqd: 1` — Shopify fills it in itself during `validate()` and the field is read-only on the form for Shopify accounts, so a plain `reqd: 1` would make Desk's client-side mandatory check block Save on a new Shopify account with no way to satisfy it), `connection_doctype` (Link → DocType, required, hidden/read-only — set programmatically by platform-specific code, not via the form) + `connection` (Dynamic Link, `options: connection_doctype`), `warehouse` (Link → Warehouse, optional — no stock fallback), `shopify_location_gid` (Data, `ignore_xss_filter: 1`, optional — same "no fallback" philosophy as Warehouse) + `shopify_location_name` (Data, read-only, display-only, always re-derived from the live lookup below, never trusted as a typed value), `erpnext_company` (Link → Company, optional until Sales Order sync), `erpnext_selling_price_list` (Link → Price List, optional until Sales Order or Talabat catalog sync), `erpnext_customer` (Link → Customer, read-only after the sync service creates its one generic Customer for this account), `enabled`. The shared Selling Price List is shown under ERPNext Integration Settings: Sales Order synchronization requires it together with a Company, while Talabat catalog sync requires it together with a Warehouse; neither flow falls back to user or site defaults. Naming is expression-based and independent of identity (`autoname: "MKTACC-.#####"`), not a `field:`/custom-string autoname — the whole point is avoiding the identity-drift bug class `Talabat Product Mapping` had before its own #19 fix. Secondary (platform, external_account_id) uniqueness is a hidden `account_identity_key` field — a fixed-length SHA-256 hash of the pair (`compute_account_identity_key()`, mirroring `Talabat Product Mapping`'s `compute_item_vendor_key()` pattern), computed in `before_save()`, with a DB-level unique index plus a `validate()`-time friendly precheck (this same generic mechanism is what enforces "one enabled Shopify Marketplace Account per shop in v1" below — no separate Shopify-specific uniqueness code exists). `validate()` also requires a `connection` and rejects one that doesn't exist as a document of `connection_doctype` (defense-in-depth alongside Frappe's own built-in Dynamic Link existence check). `set_connection_doctype()` (#103) fills `connection_doctype` from `platform` (`Talabat` → `Talabat Connection`, `Shopify` → `Shopify Connection`) whenever it's still blank — a pure default, not a forced override, so a caller (a future migration patch, or a test building a deliberately mismatched fixture) that already set a different value is left untouched. No generic platform registry/adapter framework exists yet — this one small mapping is the only per-platform logic on `connection_doctype` itself.
- **`Marketplace Product Mapping`** (`marketplace_integrations/marketplace_integrations/doctype/marketplace_product_mapping/`) — one document per external marketplace listing mapped to one ERPNext Item, the generalized replacement for legacy `Talabat Product Mapping`. Fields: `marketplace_account` (Link → Marketplace Account, required), `item` (Link → Item, required), `external_reference` (Data, required, `ignore_xss_filter: 1` — the platform adapter's opaque canonical runtime lookup value; core mapping code never infers whether it's a SKU/barcode/product ID/variant ID), `external_product_id`/`external_sku`/`external_barcode`/`external_variant_id` (Data, optional, same `ignore_xss_filter: 1` opaque treatment), `sales_uom` (Link → UOM, optional), `enabled`, plus generic sync metadata (`sync_status` Select `Not Synced/Queued/Synced/Error`, `last_sync_reference` Data opaque read-only, `last_synced_on` Datetime read-only, `last_error` Small Text read-only — no sync logic itself lives here, just the fields the existing Talabat async catalog flow already needs). Same identity pattern as `Marketplace Account`: expression-based naming (`autoname: "MPM-.#####"`, `naming_rule: Expression`) fully decoupled from any external identifier, with a hidden `mapping_identity_key` field — a SHA-256 hash of `(marketplace_account, external_reference)` (`compute_mapping_identity_key()`), computed in `before_save()`, backed by a DB-level unique index plus a `validate()`-time friendly precheck. `before_save()` also writes the stripped `external_reference` back onto the field itself, not just into the hash, so the stored value and the key stay in sync. `marketplace_account` and `item` both set `search_index: 1` (high-cardinality lookup fields — thousands of rows per account expected); `title_field: "external_reference"` and `search_fields` covering `marketplace_account`/`item`/`external_reference` give Desk breadcrumbs/global search/Link fields something human-readable instead of the opaque `MPM-#####` name. Deliberately **not** unique on `(marketplace_account, item)` — the business model allows multiple listings in the same account to map to the same Item (e.g. a bundle vs. a single-unit listing). `services/mappings.py`'s `resolve_item(marketplace_account, external_reference)` is the one runtime entry point platform adapters call for exact mapping resolution — returns the mapped Item's name only when **both** the mapping and its `Marketplace Account` are enabled (a disabled account fails closed even if the mapping itself is still enabled); returns `None` if no such mapping exists or if a blank/missing `marketplace_account`/`external_reference` is passed (never raises). No fuzzy/fallback matching against `external_sku`/`external_barcode`/`external_variant_id` is ever attempted. `resolve_mapping()` (returns the mapping document name instead of the Item) and `resolve_mapping_and_item()` (returns both in one query, for a caller that needs both facts for the same external reference - see #84 below) share the exact same resolution semantics via one private `_resolve()` helper, so there is exactly one query implementation behind all three.
- **`Talabat Connection`** (`marketplace_integrations/marketplace_integrations/doctype/talabat_connection/`) — the first concrete Platform-specific Connection doctype, holding one Talabat Partner API credential/config set. A **non-Single** DocType (multiple real rows — a per-account connection inherently needs several, which a Single can't represent; see the resolved risk note below). Fields: `connection_name` (Data, `reqd`, title field), `client_id`/`client_secret`/`chain_id` (`reqd`, `ignore_xss_filter: 1` — opaque, byte-preserving; `client_secret` is a Password field, so it also never round-trips its plaintext through the ordinary document representation, only via `get_password()`), `environment` (Select `Sandbox`/`Production`, default `Sandbox`), `enabled` (Check, default checked), and the hidden/read-only `legacy_migration_source` marker used only by the one-time legacy backfill. Naming is expression-based (`autoname: "TALCONN-.#####"`, `naming_rule: Expression`), decoupled from every field — same rationale as `Marketplace Account`/`Marketplace Product Mapping`: none of `connection_name`/`client_id`/`chain_id` is guaranteed stable, and none should silently become part of `name`. No composite-uniqueness key field exists here (unlike those two doctypes) — there's no external-identifier pair this doctype needs to guard against duplicating; that's a deliberate scope call, not an oversight, and can be revisited if a real duplicate-connection problem shows up. Controller (`talabat_connection.py`) is intentionally thin: `get_base_url()` (environment → Talabat Partner API base URL) plus token-cache invalidation on update — no HTTP calls live on the DocType controller.
- **`integrations/http.py`** — the platform-neutral HTTP/token-cache helper module shared by every marketplace client (`TalabatClient`, `ShopifyClient`), extracted out of what was originally a Talabat-only module once `ShopifyClient` needed the identical logic. `http_request(method, url, *, service_name="the remote service", **kwargs)` is the one shared bounded-timeout/network-error `requests` wrapper (public — also reused by `integrations/talabat/catalog_feedback.py`'s feedback CSV download, a plain unauthenticated call outside any platform client entirely); `service_name` is folded into the thrown message so a network failure is attributed to the right platform instead of every integration's errors reading "Failed to reach Talabat" regardless of which platform actually failed. `error_message_from_response(response)` extracts a non-2xx response's `error`/`error_description` (or a **length-bounded** raw-body fallback, `ERROR_BODY_MAX_LENGTH = 200` chars) — bounded specifically so an unrelated host's full response body (e.g. a WAF/captive-portal HTML page, possible if a connection's configured domain resolves somewhere unexpected) never gets fully echoed into an operator-facing error/Error Log entry. `fetch_client_credentials_token(url, client_id, client_secret, *, service_name, default_expires_in, expiry_buffer_seconds)` is the shared OAuth2 client-credentials token fetch: POSTs the standard `grant_type=client_credentials` body, raises on a non-2xx response, and on a malformed body catches `(ValueError, KeyError, TypeError)` — the `TypeError` catch specifically covers a non-integer/null/string `expires_in`, which would otherwise raise an uncaught `TypeError` from the `expires_in - expiry_buffer_seconds` subtraction — returning `{"access_token", "ttl", "expires_at"}` ready for `frappe.cache().set_value()`.
- **`integrations/talabat/client.py`**'s `TalabatClient` — the Talabat Partner API client, one instance per `Talabat Connection` (`TalabatClient(connection.name)`). A faithful port of the proven `talabat_integration` app's `api/auth.py` + `api/client.py` (token caching with an expiry safety buffer, exactly one retry on a 401 after invalidating the cached token, raw non-401 responses returned to the caller — callers check `response.ok`/status themselves), now built on top of `integrations/http.py`'s shared `http_request()`/`fetch_client_credentials_token()` rather than its own copies. `get_access_token()`/`invalidate_access_token()`/`request(method, path, **kwargs)` are the same three operations the legacy module exposed, now as methods scoped to one connection instead of free functions scoped to the single global `Talabat Settings` Single. The one deliberate behavior change: the access-token cache key is `f"marketplace_integrations:talabat:access_token:{connection_name}"` — keyed **per Talabat Connection document**, not globally per environment like the legacy app (which only ever had one credential set per site) — so two connections in the same environment (e.g. two Talabat vendors both on Production) get independent tokens and one invalidating/refreshing its token never disturbs the other's. Saving **or deleting** a connection clears its own cache (`on_update()`/`on_trash()`), so rotated credentials, a changed environment, or a document name later reused cannot reuse the old token.
- **`Shopify Connection`** (`marketplace_integrations/marketplace_integrations/doctype/shopify_connection/`, #101) — the first concrete Shopify-specific Connection doctype, holding one Shopify custom-app client-credentials credential set for the single Tamwenat store (custom app, not a multi-merchant public app - see `docs/shopify/README.md`). A **non-Single** DocType, same rationale as `Talabat Connection`. Fields: `connection_name` (Data, `reqd`, title field), `shop_domain` (Data, `reqd`, `ignore_xss_filter: 1`), `client_id` (Data, `reqd`, `ignore_xss_filter: 1`), `client_secret` (Password, `reqd`, `ignore_xss_filter: 1` - never round-trips its plaintext through the ordinary document representation, only via `get_password()`), `enabled` (Check, default checked). Naming is expression-based (`autoname: "SHOPCONN-.#####"`, `naming_rule: Expression`), decoupled from every field, same rationale as `Talabat Connection`. Deliberately **no** `access_token`/`expires_in`/`token_expires_on` field - unlike a static legacy Talabat-style credential, the client-credentials access token is purely runtime cache state, never persisted configuration. `validate()` requires `shop_domain` to be a bare hostname — only `[A-Za-z0-9.-]`, not starting/ending with a dot, no scheme/path/whitespace/port/userinfo/query/fragment — since `get_store_base_url()` builds the full URL by simply string-prefixing `"https://"`; a looser check that only blocked `://` and `/` would let an `@` through and expose userinfo/host confusion (e.g. `shop.myshopify.com@attacker.example` resolving to `attacker.example`, silently sending the client secret there). It deliberately does **not** hardcode a `.myshopify.com` suffix check; whether the real store domain is `{store}.myshopify.com` or a custom domain remains open, per `docs/shopify/README.md`. Controller (`shopify_connection.py`) is intentionally thin, mirroring `talabat_connection.py`: `get_store_base_url()` (URL construction only) plus `on_update()`/`on_trash()`'s token-cache invalidation - no HTTP calls live on the DocType controller. **`integrations/shopify/client.py`**'s `ShopifyClient` is the Shopify token client, one instance per `Shopify Connection` (`ShopifyClient(connection.name)`). `get_access_token()`/`invalidate_access_token()` (#101) own the token lifecycle: POSTs form-encoded `grant_type=client_credentials&client_id=...&client_secret=...` to `{store_base_url}/admin/oauth/access_token` (`integrations/shopify/constants.py`'s `SHOPIFY_TOKEN_PATH`), reading the secret via `get_password("client_secret")`, and caches the result at `f"marketplace_integrations:shopify:access_token:{connection_name}"` with `ttl = expires_in - EXPIRY_BUFFER_SECONDS` (same per-connection keying and expiry-buffer pattern as `TalabatClient`, so two connections never share a token and a rotated credential/changed domain can't reuse a stale one after `on_update()`/`on_trash()` clears it). It delegates its token fetch entirely to `integrations/http.py`'s shared `fetch_client_credentials_token()` rather than its own copy, so the same bounded-timeout/network-error handling and malformed-response handling (including a non-integer/null `expires_in`) applies. A non-2xx token response or a malformed success body raises a `frappe.ValidationError` built only from the response's own `error`/`error_description`/length-bounded-text fields, never echoing back `client_secret` or an issued access token.
- **`ShopifyClient.execute()`** (`integrations/shopify/client.py`, #102) — the single choke point for every Admin GraphQL call against a `Shopify Connection`. POSTs `{"query": ..., "variables": ...}` with an `X-Shopify-Access-Token` header to `{store_base_url}{SHOPIFY_GRAPHQL_PATH}`, where `SHOPIFY_GRAPHQL_PATH = f"/admin/api/{SHOPIFY_API_VERSION}/graphql.json"` and `SHOPIFY_API_VERSION = "2026-10"` (both module constants in `integrations/shopify/constants.py`, sourced from `docs/shopify/README.md`'s "GraphQL Admin API (for #102)" section — no prior value in this repo was doc-backed before #102, and re-checking Shopify's versioning docs before bumping this later is a real prerequisite, not a formality). `execute()` is also the first real caller of the client, so it is the point that now enforces `Shopify Connection.enabled` (throws if disabled) — closing the gap #101 had deliberately left open. Reactive 401 handling mirrors `TalabatClient.request()`: on a 401 it calls `invalidate_access_token()` and retries exactly once with a freshly-fetched token; a second 401 raises — and this one-refresh budget (`token_refresh_state`) is tracked once for the whole `execute()` call, shared across every throttle-retry attempt inside it rather than reset per attempt, so a call that hits both throttling and an expired token can never spend more than one refresh (see `docs/frappe-conventions.md`'s note on scoping a retry budget to the outer caller, not an inner retry loop). A HTTP 200 response is first parsed defensively: a non-JSON body or a JSON body that isn't a top-level object (list, `null`, ...) raises a clean error instead of an uncaught `JSONDecodeError`/`AttributeError`, and a well-formed object carrying neither a non-null `data` nor `errors` also raises rather than silently returning `None` (this also catches a `{"data": null}` body, not just a missing `data` key). The top-level `errors` field is normalized before use — a non-list `errors` (e.g. a single dict, or a bare string) is wrapped into a one-item list rather than indexed/discarded as-is, so a malformed shape can neither crash the throttle check nor silently drop the error message. A non-empty top-level `errors[]` is treated as a failure and raises (message built from each entry's own `message` field when it's a dict, or the entry itself when it's a string, tolerating any other shape) — except when `errors[0].extensions.code == "THROTTLED"`, in which case it reads `errors[0].extensions.retryAfter`, coerces it to a validated number capped at `MAX_THROTTLE_BACKOFF_SECONDS = 10` (falling back to `DEFAULT_THROTTLE_BACKOFF_SECONDS` when it's missing, non-numeric, or a bool; floored at 0 when negative — a THROTTLED response missing `retryAfter` is still retried using that default rather than falling through to the generic error path), and backs off that long before retrying, bounded by `MAX_THROTTLE_ATTEMPTS = 3` (a fixed cap, not bucket-capacity tracking, per Shopify's own guidance to just honor `retryAfter`); exceeding the cap raises. The 10s backoff cap (lowered from an initial 30s) reflects that real Shopify `retryAfter` values are sub-second to a few seconds, so it never truncates a legitimate wait while keeping `execute()`'s worst-case synchronous blocking time (cap × `MAX_THROTTLE_ATTEMPTS`) inside a normal web-request budget. Per-mutation `userErrors` (nested inside a mutation's own payload, not the top-level `errors[]`) are returned to the caller as-is inside `data`, never inspected or swallowed by `execute()`. All three failure shapes (transport non-2xx, top-level `errors[]`, throttled-and-exhausted) reuse `integrations/http.py`'s `http_request()`/`error_message_from_response()` rather than a new `requests` call site — `execute()` remains the only place in the app that opens an HTTP request against Shopify's GraphQL endpoint. Deliberately out of scope here (see #102/#103/#104/#105): a cursor pagination helper (#105, no caller yet), a connection-test method/button (validated instead via #103's Location loading), an `environment` Select field, a scopes field, `Marketplace Account.platform`/`connection_doctype` wiring, and webhook registration/verification fields.
- **Shopify Marketplace Account / Location binding** (`marketplace_account.py`'s `validate_shopify_account()`, `integrations/shopify/locations.py`, `api/shopify_locations.py`, the `Marketplace Account` form script, #103, updated by its own review pass) — a Shopify-platform account's `external_account_id` (shop GID) and, if set, `shopify_location_gid` are cross-checked against the real store via one combined live Admin GraphQL call (`fetch_shop_and_active_locations()`: `shop { id }` plus a single page — `LOCATIONS_PAGE_SIZE = 250`, no cursor pagination — of `locations { id name isActive }`, filtered to `isActive` results client-side regardless of what the query itself defaults to). This is deliberately allowed to run automatically (unlike any future Shopify *mutation*, e.g. #104's webhook registration, which must stay behind an explicit user-triggered action) because both `shop` and `locations` are read-only queries — the project's read-vs-write rule, not a per-issue exception. (#107's automatic inventory sync — the scheduled changed-Bin sweep and daily reconciliation — IS such a mutation with no explicit user action; that is a deliberate, user-approved exception to this rule, not a contradiction of it — see #107.) The live call is skipped (`_shopify_live_check_required()`) for a save on an *existing* document unless `connection`, `external_account_id`, or `shopify_location_gid` actually changed — a save that only touches Warehouse/Price List/Customer/enabled on an already-verified account never re-triggers it; a brand-new document always runs it. This is also why `services/sales_order_sync.py`'s `_get_or_create_customer()` calling `account.save()` after only setting `erpnext_customer` does not re-trigger a live Shopify call in the common case. `external_account_id` is no longer manually typed for a Shopify account: it's read-only on the form for `platform == "Shopify"` (toggled in `marketplace_account.js`, Talabat keeps it editable and `reqd`) and `validate_shopify_shop()` always (re-)sets it from the live-confirmed shop GID — a disagreeing stored value self-heals to the live one rather than throwing (its own earlier "does not match" error was an unrecoverable dead end once the field became read-only, e.g. when repointing an existing account at a different Connection, or converting a Talabat account to Shopify while carrying over its old vendor ID); a missing/falsy live shop id is still rejected with a clear Shopify-specific error rather than silently writing a blank `external_account_id`. `validate_shopify_location()` is a no-op when `shopify_location_gid` is blank (same optional/no-fallback stance as `warehouse`); when set, it throws unless that GID appears among the live active Locations, and always re-derives `shopify_location_name` from that live result rather than trusting any previously-stored/typed value. `validate_shopify_account()` also requires `connection_doctype == "Shopify Connection"` exactly, independent of whether `set_connection_doctype()`'s default ever ran. `set_connection_doctype()` remains a blank-only default; a separate `update_connection_doctype_on_platform_change()` (called from `validate()`, plus its own form-script equivalent) explicitly re-derives `connection_doctype` when `platform` *changes* on an existing document, so switching an existing account's platform (e.g. Talabat → Shopify) doesn't strand it on the old, hidden/read-only `connection_doctype`. `validate()` also calls `set_connection_doctype()` again at its own start as a belt-and-suspenders fallback for construction paths where `__init__` alone isn't enough (see `Marketplace Account`'s own class docstring, and `docs/frappe-conventions.md`'s `_validate_links()`-ordering bullet) — `frappe.new_doc()` followed by plain attribute assignment is a known residual gap that still needs the caller to set `connection_doctype` explicitly. `before_save()` writes the stripped `external_account_id` back onto the field itself (mirroring `Marketplace Product Mapping`'s `external_reference` handling), not just into the identity-key hash. None of this touches a non-Shopify account — an existing Talabat account's `validate()` never calls Shopify at all. `api/shopify_locations.py`'s `list_active_locations(connection)` is a thin, permission-checked (doctype-level `write` on `Marketplace Account` — matching the Talabat outlet-status precedent, since Marketplace Account is the document the action is actually performed for, not `Shopify Connection`), POST-only re-export of the same live active-Location list, scoped to the Connection rather than a specific Account so the Desk form's "Load Shopify Locations" button/picker (`marketplace_account.js`) works even on a new, unsaved Marketplace Account — it only fills the form's `shopify_location_gid`/`shopify_location_name` fields client-side; the account's own `validate()` re-verifies both independently on save, so the picker is a convenience, never a trust boundary. It also checks the `connection` document actually exists before calling into `ShopifyClient`, so a bad/nonexistent Connection name surfaces a clean `ValidationError` here instead of an unhandled `DoesNotExistError`. The form script toggles the "Shopify Inventory Location" section/fields and the "Marketplace Availability" (Talabat outlet) section/fields off of `platform` so neither platform's controls are ever shown on the other's form, removes the stale Talabat outlet buttons (Refresh Status/Open Outlet/Close Today/Close Until) when `platform` is switched away from Talabat and the stale "Load Shopify Locations" button both when `platform` is switched away from Shopify and when `connection` is cleared to blank while `platform` stays Shopify — none of these survive without a page refresh. A real `platform` change on an existing document (either direction, both server-side in `update_connection_doctype_on_platform_change()` and its form-script mirror) also clears `connection` (so the user must explicitly pick a new one scoped to the new `connection_doctype`, rather than surfacing a confusing generic core link error) and clears the fields specific to the platform being left (Shopify Location fields when leaving Shopify, Talabat outlet-status fields when leaving Talabat). `ShopifyClient.execute()`'s worst-case synchronous blocking time (throttle backoff cap × max attempts, documented on `execute()` itself) is therefore also the worst case for a Shopify `Marketplace Account` save that does trigger the live check — no queuing/enqueue infrastructure exists for this and none is planned; it's a documented tradeoff, not a gap. The live check only re-verifies on a `connection`/`external_account_id`/`shopify_location_gid` change, not on every save (see above) — a Shopify Location deactivated upstream on Shopify's own side won't be caught by ERPNext until something explicitly changes one of those three fields again; future consumers of `shopify_location_gid` (inventory/sync work, #105+) must not assume save-time validation guarantees current validity and should re-check at use time if staleness matters for that operation.
- **Talabat outlet availability** (`integrations/talabat/outlet.py`, `api/talabat_outlet.py`, and the `Marketplace Account` form script, #72/#73) — per-account, synchronous status retrieval and update through `GET`/`PUT /v2/chains/{chain_id}/vendors/{vendor_id}/status`. The service reuses the enabled Talabat `Marketplace Account` + enabled linked `Talabat Connection` resolution used for operational orders, and always instantiates `TalabatClient` from that linked connection; it never falls back to legacy settings. `Marketplace Account` stores a generic, read-only cache of Talabat's **last confirmed** external status, close reason, close-until instant (converted from Talabat UTC to the Frappe system timezone), time checked, sanitized error, and full response JSON. Successful GET/PUT responses replace that cache and clear the error. A request or response failure preserves the last confirmed fields and records only the generic error, never the remote error body or an attempted state. - **Talabat catalog feedback webhook** (`api/talabat_webhooks.py`, `integrations/talabat/catalog_feedback.py`, `Talabat Connection`, #26) — trigger-source agnostic finalization of whatever mapping currently has `last_sync_reference` equal to the reporting job id, regardless of whether that job came from #6/#89/#91's manual push or a future reconciliation job. `catalog_update_feedback()` is the POST-only, guest-accessible transport boundary: it requires all four documented fields (`job_id`, `status`, `platform_vendor_id`, `download_url`), resolves exactly one enabled Talabat account/connection by `platform_vendor_id == Marketplace Account.external_account_id` (a single field, unlike the order webhook's `client.id`/`client.store_id` pair), and authenticates with constant-time comparison against that connection's own separate `catalog_webhook_secret` - distinct from `order_webhook_secret`, so neither secret can authenticate the other's callback. Only the documented `vendorId`, `sku`, `feedback`, `details` CSV columns are consumed. Correlation is exact and stale-safe: a row's `vendorId` must match the callback's `platform_vendor_id`, the mapping is resolved by `marketplace_account` plus its *effective outbound sku* - `external_sku` when non-blank, else `external_reference`, the exact same precedence `catalog_sync.py`'s `build_catalog_product` uses to build what Talabat actually received (shared via `catalog_sync.effective_outbound_sku()`, not a separately-maintained copy) - evaluated per-candidate rather than as a broad `external_sku == sku OR external_reference == sku` filter, so a mapping with a non-blank `external_sku` can never be pulled in by a coincidentally-equal `external_reference` it never actually sent. This candidate resolution is built from exactly one upfront `frappe.get_all()` of the account's mappings, not a query per CSV row. That mapping's current `last_sync_reference` must still equal the callback's `job_id`, checked and finalized with a single atomic conditional `UPDATE` (`WHERE name = ... AND last_sync_reference = ...`, rows-affected checked) rather than a separate read-then-write, so a concurrent re-push (e.g. #91's bulk push) between the two can never have its fresher `Queued`/new-job-id state overwritten by this stale job's feedback. Any mismatch is skipped rather than overwritten, and logged as one of two distinct ops signals - a CSV row whose sku matches no mapping at all (or ambiguously matches more than one) versus a row that matches a real mapping currently on a different/newer job - alongside the count and names of this job's mappings that never appeared in the CSV at all and so remain unfinalized (typically still `Queued`). Because Talabat documents no formal `feedback` enum, only the exact example success string `Product Assignment Successful` is ever treated as success (`sync_status = "Synced"`, clearing `last_error`); every other non-blank value and blank feedback alike become `sync_status = "Error"` with a bounded, plain-text `last_error` combining `feedback` and `details` - this fail-closed rule is intentional and must not be loosened without its own issue/architecture change. This module never calls Talabat's Beta job-status endpoint. `Talabat Connection` persists its own read-only `catalog_webhook_url`/`catalog_webhook_secret` pair, generated/refreshed and copied through the same before_insert/refresh/copy shape #58 established for the order webhook, entirely separate fields from `order_webhook_url`/`order_webhook_secret`; a one-time idempotent patch (`patches/v0_0/backfill_talabat_catalog_webhook_urls.py`) backfills both fields together for any Talabat Connection that existed before this feature (`before_insert` alone cannot reach it), so pre-existing connections don't keep a permanently blank secret.

- **Sales Order transaction pricing correction** (`services/sales_order_sync.py`, `fixtures/property_setter.json`, `hooks.py`, #85) — corrects #61's original pricing behavior, which let ERPNext's current Item Price/Pricing Rules compute each Sales Order line's commercial value (so an Item Price change made after the customer ordered could silently reprice an already-fulfilled historical order). The Sales Order line now preserves the finalized Talabat merchandise transaction instead: for each final (`IN_CART`/`ADDITION`) mapped `UNIT` line, `effective_rate = fulfilled_total_price / fulfilled_quantity` (rounded to a fixed `EFFECTIVE_RATE_PRECISION` of 6 decimal places, deliberately NOT the resulting Sales Order Item's own currency precision - rounding the division down to the same 2dp precision `amount` itself uses, before multiplying back by `qty`, is a double-rounding bug: e.g. `9.99 / 2 = 4.995` rounds to `5.00` at 2dp, and `5.00 * 2 = 10.00 != 9.99`, incorrectly blocking a routine non-evenly-divisible discounted line. A higher-precision Python-side rounding alone is not sufficient, though: ERPNext's own `calculate_taxes_and_totals()` unconditionally re-rounds `Sales Order Item.rate`/`price_list_rate` back down to their own field precision on every call - including the one `AccountsController.validate()` reruns on every `.insert()`/`.save()` - since neither field has an explicit `precision` in ERPNext's own doctype JSON and both otherwise default to the site's `currency_precision`, identical to `amount`'s. `fixtures/property_setter.json` therefore ships two Property Setters raising `Sales Order Item.rate` and `.price_list_rate`'s own field precision to 6 (never a doctype JSON edit inside `erpnext`/`frappe` itself), so ERPNext's internal rounding no longer clips the higher-precision value below what this module computed - verified directly against the installed ERPNext 16.33.0 source and a live bench console reproduction, not assumed; `amount` itself keeps the site's normal `currency_precision`. Because this Property Setter is global to the doctype/field, it is a site-wide change - every Sales Order's `rate`/`price_list_rate` columns can now display trailing digits beyond 2dp, not just marketplace-synced ones; see `docs/frappe-conventions.md`.) and `fulfilled_total_price` itself (zero and negative are handled distinctly: zero is a valid, final amount; negative blocks the line same as a missing quantity). A zero `fulfilled_total_price` paired with a nonzero `fulfilled_unit_price` on the same line is treated as likely-missing pricing data, not an honest free item, and blocks the line the same way; both genuinely `0` still passes through as a legitimate free item. A null `fulfilled_total_price` also blocks the line, but that distinction cannot be read off the stored Float field itself - a Frappe Float column is `NOT NULL` and silently coerces `None` to `0.0` - so `integrations/talabat/order_mapper.py` captures "Talabat's raw `pricing.total_price` was absent" as a separate `Marketplace Order Item.fulfilled_total_price_missing` flag at parse time, before that coercion happens, and `_build_sales_order_lines()` checks that flag *in addition to* the direct `fulfilled_total_price is None` check (kept as defence-in-depth for an in-memory caller that hasn't gone through a DB save/reload yet, where the coercion hasn't happened and the flag may not be set either) - never one instead of the other. Pre-existing orders are backfilled by `patches/v0_0/backfill_marketplace_order_fulfilled_total_price_missing.py`, which processes each order in its own try/except (a malformed `latest_payload` is logged and skipped rather than aborting the whole site migration) and writes the flag with a direct `frappe.db.set_value()` per child row rather than loading/validating/saving the parent Marketplace Order (which would otherwise re-run full account/price-list/warehouse/mapping validation via its own `before_save()` for every changed order, for no reason, mid-migration). `Marketplace Account.warehouse` is mandatory sync configuration, validated through the shared `services/account_warehouse.py::validate_account_warehouse()` helper (also used by #6 catalog sync, so the two can't drift on wording or coverage): must be set, a leaf (non-group) Warehouse, not disabled, and - when the account has an `erpnext_company` configured - belonging to that same Company; it is set on every Sales Order Item's `warehouse`. Because #61 never required a Warehouse for Sales Order sync, this is a new mandatory prerequisite: any Marketplace Account previously used for Sales Order sync without one configured will fail this check with a `SyncBlocker` on its next sync attempt after this change deploys - an expected one-time operational consequence of deploying #85, not a regression, and mirrors the same Warehouse requirement #6's catalog sync already enforces. That helper raises via `frappe.throw()`, which appends its message to `frappe.local.message_log` before raising; `sales_order_sync.py` catches it and calls `frappe.clear_messages()` before re-raising as a `SyncBlocker`, so only the `SyncBlocker`'s own (client-side `escape_html`'d) message reaches the user rather than both. `Marketplace Account`'s own `validate_warehouse()` keeps a separate, deliberately lighter save-time check (leaf-vs-group only, no Company/disabled check) - the two are not folded together, since a Company mismatch or disabled state isn't necessarily wrong outside the context of one specific sync operation. The account's Selling Price List currency, and the account's generic Customer's own `default_currency` (when either is set), are both also required to equal the Company's default currency before sync (V1 assumes single-currency operation - Talabat fulfilled amounts are bare numbers with no currency of their own on Marketplace Order, so a currency mismatch would otherwise copy a Talabat amount as a raw rate into the wrong currency unconverted; the Customer check exists because ERPNext resolves a Sales Order's real currency from its Customer *first*, so a Customer-level currency override would otherwise slip past a Price-List-only guard entirely while `rate * qty == fulfilled_total_price` still holds numerically, silently mis-denominating the whole document). ERPNext's own `set_missing_values()` still runs exactly once, but purely for structural defaults (Item/UOM/conversion, accounts, party/company details, currency) with `ignore_pricing_rule = 1` already set - never to price a line: whatever current Item Price it fetches into `rate`/`price_list_rate` as a side effect is immediately discarded by an explicit per-line override (`rate`, `price_list_rate` both set to `effective_rate`; `discount_percentage`/`discount_amount` forced to `0`; `is_free_item = 1` only when `effective_rate == 0`), and `calculate_taxes_and_totals()` is then called to recompute net/grand totals from that overridden rate. This survives ERPNext's own subsequent `validate()`-time re-run of `set_missing_item_details()` on `.save()`/`.insert()` because `rate`/`price_list_rate` are not in that method's `force_item_fields` override list and are already non-`None` by the time it runs - confirmed directly against the installed `erpnext/controllers/accounts_controller.py`, not assumed (also recorded as a general gotcha in `docs/frappe-conventions.md`). Every re-sync of an existing Draft also explicitly resets `apply_discount_on`/`additional_discount_percentage`/`discount_amount`/`taxes_and_charges`/`taxes`/`shipping_rule` before recalculating totals, so a header-level discount or tax/shipping configuration added by hand to the Draft between syncs cannot survive a re-sync and silently cut the merchandise total. After totals are recalculated, each Sales Order Item's `amount` must equal Talabat's `fulfilled_total_price` at that same currency precision; a mismatch (e.g. a fulfilled amount that doesn't divide evenly by fulfilled quantity at ERPNext's configured precision) blocks the whole sync with an actionable error instead of silently posting a drifted amount - this hard block is deliberate and permanent (no auto-rounding/reconciliation), matching #85's literal wording. Nothing else changes: `delivery_fee`/`service_fee`/`container_charge`/`difference_to_minimum`/`additional_fees`/`collect_at_pickup`/`payment.discount`/marketplace settlement or commission still never enter the Sales Order, and `grand_total` is still never forced to equal Talabat's `order_total` - V1 remains final-merchandise-lines-only. The deterministic snapshot used for the `Needs Action` hash now carries company, generic customer, Selling Price List identity, `transaction_date` (`date(order.received_on)`, newly added to the Sales Order header alongside the existing `delivery_date = date(order.promised_for)`), each final line's `external_item_id`, mapped Item, UOM, qty, Warehouse, and the transaction `effective_rate`/`fulfilled_total_price` - deliberately never a current Item Price amount, so an Item Price change alone still does not dirty a synced Marketplace Order, while a fulfilled quantity/amount change still does. The unhandled generic-exception path in `sync_sales_order()` logs via `frappe.log_error(title=...)` with no `message=` kwarg, so `frappe.get_traceback()` still populates the Error Log entry - passing a static `message=` there (as an earlier revision of this fix did) replaces the real traceback with that string, per `frappe/utils/error.py`. Client-side, the "ERPNext Sync Blocked" `frappe.msgprint()` in `marketplace_order.js` escapes the returned error string with `frappe.utils.escape_html()` before interpolating it, since `msgprint`'s `message` renders as HTML and the error text can embed `ignore_xss_filter` Talabat values (`external_item_id`/`external_sku`), matching #84's established pattern for external strings reaching an HTML sink. Customer policy, KG blocking, and the submitted-Sales-Order block-only policy are all unchanged from #61. **Deploying this change re-flags every previously-synced Marketplace Order as `Needs Action`**, because the snapshot shape itself changed (new `transaction_date`/`warehouse`/`effective_rate`/`fulfilled_total_price` hash inputs) - each order computes a different hash and flips status the next time `get_current_sync_status()`/`set_sync_status_from_current_snapshot()` runs on its next form load (an existing, generic mechanism that already writes status changes to the record on view, not new code - just newly triggered at scale by this diff). This is expected, not a bug, and no migration patch re-stamps `last_synced_hash` to suppress it. For an order whose linked Sales Order is already Submitted, this is permanent under the existing block-only policy: there is no auto Update Items/cancel/amend/duplicate path, so resolving it (if desired) is a manual/human decision made outside this sync path, the same as any other Submitted-Sales-Order case.
- **Shopify order webhook registration, verification, and monitoring** (`marketplace_integrations/doctype/shopify_webhook_delivery/`, `integrations/shopify/webhooks.py`, `api/shopify_webhooks.py`, `Shopify Connection`, #104) — registers, inspects, and repairs webhook subscriptions for `ORDERS_CREATE`/`ORDERS_UPDATED`/`ORDERS_CANCELLED`/`ORDERS_PAID`/`REFUNDS_CREATE`/`APP_UNINSTALLED`/`APP_SCOPES_UPDATE` (`SHOPIFY_WEBHOOK_TOPICS`, `integrations/shopify/constants.py`) — deliberately not inventory/fulfillment/tracking topics. `Shopify Connection.sync_webhook_subscriptions()` (a mutating, explicit user-triggered Desk button — unlike #103's automatic read-only live checks, and gated behind a `frappe.confirm()` on the client script that names what the delete side can affect, see below) inspects current subscriptions for `SHOPIFY_WEBHOOK_TOPICS` at ANY uri via a single bounded `webhookSubscriptions` query (filtered by topic only, not by uri — that's how stale-uri detection below works at all), then creates only whatever of those topics are still missing at this connection's own current callback URL via `webhookSubscriptionCreate` — idempotent by construction, since existing subscriptions are always read first, so calling it twice only ever creates topics still missing after the first call. It persists a small live health snapshot on `Shopify Connection` itself (`webhook_registration_status`, `webhook_missing_topics`, `webhook_last_checked_on`, plus `last_webhook_delivery_at`/`last_webhook_delivery_topic`/`last_webhook_processed_at`/`last_webhook_error`) rather than a separate config doctype, since webhook subscriptions are store-wide, one set per `Shopify Connection`, not per `Marketplace Account`. **Verified**: the `webhookSubscriptions`/`webhookSubscriptionCreate` GraphQL field/argument names used here were checked against https://shopify.dev/docs/api/admin-graphql/latest (input-objects/WebhookSubscriptionInput, enums/WebhookSubscriptionTopic) on 2026-09-19 — not from `docs/shopify/README.md` (which only names the mutation, not its full shape). `sync_webhook_subscriptions()` also repairs stale subscriptions: a subscription for one of `SHOPIFY_WEBHOOK_TOPICS` registered at a different uri than the current callback URL (e.g. after a dev tunnel URL or site `host_name` changed) is deleted via `webhookSubscriptionDelete` before the missing-topic pass runs, so only the current-uri subscription remains per topic. `webhookSubscriptionDelete`'s shape (`id: ID!` argument, `deletedWebhookSubscriptionId`/`userErrors` on the payload) was likewise verified against https://shopify.dev/docs/api/admin-graphql/latest/mutations/webhookSubscriptionDelete on 2026-09-19. Per-topic Shopify `userErrors` (both from create and delete calls) are persisted to `Shopify Connection.last_webhook_error` — on the exception path and on a success-with-errors path alike — and surfaced verbatim (HTML-escaped) by the "Sync Webhook Subscriptions" button's client script, not just a generic "incomplete" message. **`webhook_registration_status` is `"Error"` whenever `errors` is non-empty, full stop — a second review pass (2026-09-19) fixed an earlier version of this logic that only consulted `errors` when a topic was still `missing`, which let a failed delete-side `webhookSubscriptionDelete` (stale-subscription cleanup) go unreported as `"Complete"` whenever that same topic's create-pass still succeeded, silently leaving a stale subscription live and double-delivering behind a green status.** `Shopify Connection.shop_domain` carries a DB-level `unique: 1` constraint, since `api/shopify_webhooks.py`'s `_resolve_connection()` depends on resolving exactly one connection per shop domain. `api/shopify_webhooks.py`'s `webhook_event()` is the single public POST transport boundary for every subscribed topic (Shopify's `X-Shopify-Topic` header routes within it, rather than one endpoint per topic): it verifies `X-Shopify-Hmac-Sha256` (`HMAC-SHA256(raw_request_body, client_secret)`, base64, constant-time-compared) against the RAW body *before* any JSON parsing, resolves exactly one `Shopify Connection` by `X-Shopify-Shop-Domain` (deliberately not gated on `enabled`, since an `APP_UNINSTALLED` delivery must still authenticate and be processed for an already-disabled or about-to-be-disabled connection), and rejects before enqueue on any missing header, an unresolvable/ambiguous shop domain, or a bad signature. A valid delivery for a topic outside `SHOPIFY_WEBHOOK_TOPICS` is acknowledged (200, so Shopify stops retrying) but never enqueued. `integrations/shopify/webhooks.py`'s `process_shopify_webhook()` is the enqueued worker: it switches to Frappe's system user (the public request was received as Guest, mirroring Talabat's order webhook), then inserts one `Shopify Webhook Delivery` row keyed by Shopify's own `X-Shopify-Webhook-Id` (`webhook_id`, DB-level `unique: 1`) — deduplication is enforced by that unique index, not a check-then-insert read (`docs/frappe-conventions.md`'s concurrency guidance), so a duplicate delivery (Shopify's documented at-least-once guarantee) raises `UniqueValidationError` on insert (the unique *field* constraint on `webhook_id`, not `DuplicateEntryError`, which is for a duplicate document *name*). **A duplicate is only a harmless no-op when the existing row for that `webhook_id` already reached `status = "Processed"`** — a second review pass (2026-09-19) fixed an earlier version that treated every duplicate as a no-op unconditionally, which meant a delivery whose first attempt ended in `"Error"` (or was interrupted before reaching `"Processed"`) could never be reprocessed by any of Shopify's own retries of that same `webhook_id`, ever. `process_shopify_webhook()` now looks up the existing row on `UniqueValidationError` and, when its status is not yet `"Processed"`, reprocesses `_handle_topic()` against that same row (never inserting a second one — the unique index still guarantees only one row per `webhook_id`). The `frappe.clear_messages()` call right after catching `UniqueValidationError` mirrors #85's established pattern for a `frappe.throw()`-caused `msgprint()` inside a background worker (see #85's bullet above) — without it, `show_unique_validation_message()`'s own `msgprint()` would leave a stray message in `frappe.local.message_log`. Canonical order retrieval and ERPNext Sales Order/document creation from webhook payloads are explicitly out of scope for #104 (and so is storing the payload itself on `Shopify Webhook Delivery`): every topic other than `APP_UNINSTALLED` is acknowledged and recorded (`status = Processed`) with no further side effect. `APP_UNINSTALLED` safely disables the connection (`enabled = 0`, saved through the normal document API so `Shopify Connection.on_update()`'s existing token-cache invalidation still runs) — idempotent, since a second uninstall delivery (or one arriving after an admin already disabled the connection manually) is a no-op. A processing failure marks that delivery `Error` with a length-bounded sanitized message (`integrations/http.py`'s shared `truncate_response_text()`, reused rather than a second bound) and mirrors it onto `Shopify Connection.last_webhook_error`, alongside a full traceback in the Error Log for operator diagnosis. Secret-rotation dual-secret acceptance is covered: `Shopify Connection` has an optional `previous_client_secret` field (same `Password`/`ignore_xss_filter: 1` shape as `client_secret`), populated by an admin during a rotation window and cleared once rotation completes. `verify_shopify_hmac()` checks the delivery's HMAC against `client_secret` first and, only if that fails and `previous_client_secret` is set, also checks it against `previous_client_secret` — accepting the delivery if either matches, since `docs/shopify/README.md` notes Shopify signs with the app's oldest unrevoked secret during a rotation window, not necessarily the current one. **A third review pass (2026-09-19) closed a remaining reprocessing gap**: `webhook_event()` correctly responds 200 as soon as processing is enqueued, so Shopify never retries a delivery whose ASYNC processing later fails (e.g. `APP_UNINSTALLED` failing inside `_disable_connection()`'s `save()` on a lock timeout) — nothing was left to give such a delivery a path back to `"Processed"`. The processing logic previously inlined at the end of `process_shopify_webhook()` is now its own shared `_process_delivery(delivery, connection)`, called both from `process_shopify_webhook()`'s existing duplicate-`webhook_id` reprocess path and from a new scheduled sweep, `retry_errored_webhook_deliveries()` (registered hourly in `hooks.py`'s `scheduler_events`), which reprocesses every `Shopify Webhook Delivery` still at `status = "Error"`, plus (added in a later review pass on PR #117) any row stuck at `status = "Received"` older than `STUCK_RECEIVED_THRESHOLD_MINUTES` (a worker crash between `delivery.insert()` and its first status write — the one failure mode with no other recovery path) — one implementation of "(re)run a delivery", not a second copy. `Shopify Connection.last_webhook_delivery_at`/`last_webhook_delivery_topic` are stamped only from the delivery's own `received_at`/`topic` on its ORIGINAL processing attempt (`attempt_count == 0` going in) — never re-stamped with the current time on a reprocess/retry, since those fields mean "has Shopify stopped delivering to us" and a stale retry falsely making them look fresh would defeat that (an earlier version of this logic re-stamped `last_webhook_delivery_at` with `now_datetime()` on every attempt including retries; a review pass on PR #117 reverted that). `last_webhook_processed_at`/`last_webhook_error` still update on every attempt, original or retried, since those track "last processing attempt/outcome" rather than "last delivery received". Both reprocess paths are bounded by a `Shopify Webhook Delivery.attempt_count` field (`Int`, `read_only: 1` — a visible operator-facing diagnostic on the form, not hidden) and a module constant `MAX_WEBHOOK_DELIVERY_ATTEMPTS = 5`: a delivery that has already reached the cap is left untouched at `"Error"` rather than retried forever, by either a Shopify redelivery or the sweep. The cap check and the increment are one atomic `UPDATE ... WHERE attempt_count < %s` (`docs/frappe-conventions.md`'s concurrency guidance), not a separate read-then-write, so two concurrent callers hitting the same row (e.g. the sweep and a simultaneous Shopify redelivery) can't double-count or exceed the cap. The sweep's own query is a single parameterized raw SQL `SELECT` (the OR-of-two-status-branches-with-one-branch-only-age-filtered shape isn't expressible as plain ANDed `frappe.get_all()` filters), read oldest-first (`ORDER BY creation ASC`) and bounded to `SWEEP_BATCH_LIMIT` rows per run so one run is never unbounded against a large backlog. Each row is processed under its own DB savepoint (`frappe.db.savepoint()`/`rollback(save_point=...)`/`release_savepoint()`, same pattern as `api/talabat_orders.py`'s vendor-order import) and committed per-row on success, so one bad row can't roll back every row already successfully processed earlier in the same sweep run.

Post-#106 review-fix details worth knowing before touching this feature again: `validate_push_account()` is split into `_validate_push_account_local()` (platform/Connection/Price List config, account enabled — no network call) plus its own `_validate_shop_currency()` call (the live `shop { currencyCode }` GraphQL read). `queue_catalog_push()` (the synchronous Desk request) calls only the local half — the currency check, and the actual price push, both happen exclusively inside the background worker (`push_catalog()`, via the full `validate_push_account()`), so a throttled Shopify shop can never block the Desk request itself. `queue_catalog_push()` also never `frappe.throw()`s mid-loop on an RQ dedup rejection OR a per-account misconfiguration — it returns `{"jobs": [...], "skipped_accounts": [...]}`, collecting every account's outcome (queued job id, or a skip reason distinguishing "already running" from "misconfigured") together, so a rejection or misconfiguration for one account can't hide the job ids of other accounts already enqueued/validated in the same request; a misconfigured account (missing/disabled Price List, disabled Connection, ...) no longer blocks every other valid account in the same request from being queued. Both client surfaces render each `skipped_accounts` entry's own server-provided `reason` verbatim, HTML-escaped (form: `show_alert` with the single reason; list: `msgprint` of "account: reason" lines) — never an assumed "already running" message, since a reason may equally be a config error; `reason` is the only discriminator, no separate field — and only open the job-status dialog when `jobs` is non-empty; `skipped_mappings` (a separate field, inside `_push_result_payload()`'s per-job `result`) counts MAPPINGS excluded as disabled within an already-queued job, not accounts skipped at queue time — the two are deliberately named differently to stay textually distinct. `push_catalog()` excludes a mapping from the push entirely — no network call, no local build, no sync_status write — when the mapping is disabled or its linked Item is disabled (`_split_active_mappings()`, matching Talabat's own `bool(mapping.enabled) and not bool(item.disabled)` semantics in `build_catalog_product()`); such a mapping is reported as `skipped: true` in the result, distinguishable from an actual `Error`. A successful push no longer writes `last_sync_reference` (`_mark_synced()` leaves it untouched) — the product GID it would have stored already lives on `external_product_id`, so writing it again was pure duplication; this differs from Talabat's `_mark_queued()`, which genuinely needs `last_sync_reference` to hold a new remote job id. `_push_product_group()` chunks a group's variants into `constants.py`'s `SHOPIFY_CATALOG_PUSH_VARIANT_CHUNK_SIZE`-sized batches (one `productVariantsBulkUpdate` call per chunk, still inside the same per-group savepoint/commit) so a Shopify product with unusually many mapped variants doesn't fail as one oversized mutation call. `push_catalog()`'s document loading is O(1) queries, not O(mappings): `_mappings_for_push()` and `_fetch_items()` each issue one bulk `frappe.get_all()` (only the fields the push path actually reads) instead of a `frappe.get_doc()` per mapping/per Item, before the per-group processing loop runs; `services/mapping_push.py`'s `group_mappings_by_account()` deliberately did NOT get the same treatment: it keeps Talabat's original per-mapping `frappe.get_doc()` + `check_permission("write")` flow (same error text, per-mapping check order, deterministic account order), since #106 requires no user-visible Talabat behavior change (pinned by `test_queue_mappings_pins_original_per_mapping_error_order_and_text`). `shopify_catalog_push_status.js` stops each job's own polling loop as soon as that job is completed/failed, independent of other jobs.

  **Concurrency hardening (decision 10, user-confirmed real race; round-3 review findings #1/#3):** `Document.save()` → `update_children()` re-syncs every `Table` field on a parent doc on every save, deleting any child-table row absent from the in-memory copy being saved - a Noon poll that read an order's row before a concurrent fulfillment write committed could silently delete that write's just-committed shipment/unit/AWB row. The fix: `integrations/noon/orders.py::import_order()` takes a `FOR UPDATE` lock on the order row as the very FIRST database statement it issues - before `normalize_order()` (whose `resolve_mapping_and_item()` calls issue their own plain consistent reads against `Marketplace Product Mapping`), before the customer-data/stale-status-group reads, and before `upsert_marketplace_order()`'s own `frappe.get_doc()`. Ordering this way matters, not just locking at all: under MariaDB's `innodb_snapshot_isolation=ON`, ANY earlier consistent read in the same transaction (on any table) establishes that transaction's read view, and a later locking read that then hits a row committed after that read view was created raises error 1020 (`frappe.QueryDeadlockError`) - which MariaDB handles by rolling back the whole transaction, destroying the caller's open savepoint and aborting its `release_savepoint()` call with "SAVEPOINT does not exist" (a real bug an earlier version of this fix had, caught in round-3 review: it retried once on 1020 instead of reordering, which still left the caller's savepoint gone). `api/noon_fulfillment.py::_get_noon_order()` has the identical ordering fix for the same reason: it locks the order row before its own `frappe.get_doc()`, ahead of calling into whichever `integrations/noon/fulfillment.py` function re-locks the same row. `integrations/noon/orders.py` also commits after each order's own savepoint (not once per whole run), releasing this lock promptly.

  **Round-5 fix (review finding #1):** being first-in-FUNCTION, or committing once right after a caller's own setup reads (the round-4 fix), both turned out to still be insufficient - MariaDB's read view is scoped to the whole transaction, and `NoonClient.request()`'s own connection/auth read on every single Noon API call (pagination, a single-order `GetFbpiOrder`, etc.) can re-establish a stale-ahead-of-the-lock read view just as easily as any other plain read. The fix: every lock acquisition now commits immediately before the lock itself, with nothing else in between - `fulfillment.py::_lock_and_load_order()` does this as its own first statement (covering every lock acquisition in that module uniformly), and `orders.py::_import_order_isolated()`/`refresh_order()` each commit immediately before their own savepoint/lock, placed AFTER whatever HTTP call most recently ran, not before it. See `docs/frappe-conventions.md`'s general rule for this.

  A worker chaining several Noon HTTP calls (`run_create_shipment()`, `run_mark_out_of_stock()`, `run_add_awb()`, `run_upload_invoice()`) does NOT hold this lock across any of those calls (round-3 review finding #3) - each releases it (`frappe.db.commit()`) immediately before every Noon call and re-acquires it immediately after, re-checking the shipment's status against the status read before that call (any change aborts the worker, since only a concurrent committed write - e.g. a cancel - could have changed it while the lock was released). Holding the lock across a ~4-call sequence would otherwise risk `QueryTimeoutError` against the 50s `innodb_lock_wait_timeout` and block the hourly poll/Desk saves/other fulfillment actions on the same order for the whole sequence's duration. `run_cancel_shipment()` makes only one Noon call, so it keeps the lock held across it (nothing to release/re-acquire for). `run_mark_out_of_stock()` makes two Noon-related calls in sequence (`UpdateOrder`, then a post-success `GetFbpiOrder` refresh) - round-3 review already described both as lock-released, but only the first actually was; the second one ran with the lock from the first call's re-acquisition still held until round-5 fixed it (review finding #5) to release-then-reacquire around the refresh too, same as every other multi-call worker. `import_order()`'s own lock is a deliberate exception left as-is: it's still held across its internal `_maybe_fetch_customer_data()` HTTP call (worst case ~30s, under the 50s timeout) rather than given the same release/reacquire treatment, since that's a one-off backfill call not worth the extra complexity. Covered by `integrations/noon/test_orders.py`'s `IntegrationTestNoonOrderImportConcurrency`, which uses two real OS threads with independent site connections (the only way to exercise real InnoDB row locking) to prove a shipment row committed mid-poll survives that poll's own save, and `IntegrationTestNoonOrderImportBatchIsolation`'s deadlock-simulation test, which proves a `QueryDeadlockError` from the locking read is isolated to its own order like any other per-order failure rather than aborting the run.

  **#146 round-5 review hardening:** `run_create_shipment()` re-verifies the shipment's status immediately before the actual `CreateShipment` call (not just after it returns) - a concurrent `discard_shipment()` landing in the gap after the lock was released for that call would otherwise let `CreateShipment` still reach Noon and create an orphaned shipment with no local record claiming it (finding #2). `run_mark_out_of_stock()` still writes a `Marketplace Sync Log` row recording the actual `UpdateOrder` outcome even when a concurrent `release_stuck_oos_reservation()` cleared the local reservation while that call was in flight, instead of returning silently and losing the only evidence that Noon may have already applied the change (finding #3). `upload_invoice()` clears `invoice_last_error` when writing a fresh `Pending` upload attempt, so a new attempt doesn't still show a previous attempt's stale error (finding #7).

### Carrier fulfillment integrations

A carrier answers: **How do we hand an ERPNext delivery to a shipping
provider and receive its carrier lifecycle?** It is distinct from a
marketplace/storefront integration: it does not represent a seller account,
does not own a stock partition, and is not modeled through `Marketplace
Account` or `Marketplace Order`.

The Bosta MVP starts with one site-wide, carrier-specific `Bosta Settings`
Single containing the raw API key, one Bosta business-location ID, enabled
flag, and generated webhook URL/secret. `integrations/bosta/client.py` owns
the raw-API-key authenticated Bosta transport and the Create Delivery and A4
Arabic AWB endpoints. It deliberately receives an opaque delivery payload: the
Sales Order workflow owns the Bosta-required payload mapping, rather than the
settings/client foundation.

**Picking the business location (#276).** `Business Location ID` is read-only on
the form; the **Fetch Locations** button on `Bosta Settings` calls
`api.bosta_settings.get_pickup_locations` (System Manager only), which uses the
*saved* API key (no key: rejected before any request; unsaved edits: the form asks
to save first) and returns `[{id, name, address, city, is_default}]` via
`integrations/bosta/locations.get_pickup_locations()` ->
`BostaClient.get_pickup_locations()` (`GET /pickup-locations`, every page, capped at
20). It works while Bosta is still disabled (`BostaClient(allow_disabled=True)`,
since enabling requires the location); every other client call still requires
enabled. Nothing is cached or stored. A dialog Select (labels escaped, value =
Bosta `_id`) sets the field; the default location is preselected only when no ID is
set yet; a Bosta error shows escaped with Retry, and an error or empty list never
changes the saved ID. Field shapes come from the docs.yaml example; `data.list[]`
`_id`, `locationName`, `address.firstLine`, `address.city.name`, `isDefault` and
`pages`/`page`/`limit`/`total` were seen in a live response on 2026-10-16. The `page`
query parameter is honored and the default page size is 200 (verified live
2026-10-16). An empty page ends the walk, and a location repeated across pages is
returned once.

The `Bosta Shipment` operational record links an ERPNext Sales Order and
Delivery Note; it is not a marketplace shipment or a generic carrier
framework.

`Bosta Shipment` has one `Bosta Shipment Item` row per reserved Sales Order
item row. Each row stores the exact `so_detail`, item, transaction UOM and
conversion factor, warehouse, stock-UOM quantity, fulfilled quantity, and the
linked Delivery Note Item when one is submitted. Before contacting Bosta, the
service locks the Sales Order and reserves all currently available stock
quantity by row: ordered stock quantity minus stock quantity on submitted
outbound Delivery Notes minus other active Bosta reservations. The Sales Order
lock serializes reservation attempts. This issue has no per-line quantity
chooser, so true partial shipments and concurrent split shipments are deferred.
Creating or checking the carrier shipment does not post stock. The reservation
remains held until Bosta reports `SEND` state 21 (picked up from the business),
or an authorized user records physical handover. That trigger creates and
submits one Delivery Note limited to the stored reservation. Delivery Note
creation failure keeps the reservation and is retried only through an explicit
handover/check action. An explicit Bosta rejection releases it; a timeout or
malformed acceptance keeps it until Check Bosta resolves whether the remote
delivery exists. Handover and stock posting have independent states. System
Manager and Stock Manager may confirm physical handover before `SEND`/21.
`Bosta Shipment.bosta_delivery_type` stores the documented type received from a
carrier status event or poll; the type requested during creation is not treated
as evidence of the carrier's actual delivery type. Automatic state-21 posting
and Check Bosta require persisted evidence equal to `SEND`. Historic rows
without reliable type evidence remain Review Required.
Carrier cancellation never automatically cancels an already-submitted Delivery
Note or reverses its stock posting. Historic rows whose handover cannot be
established are marked Review Required; migration does not change stock.
The standard Sales Order form's Bosta tab uses the permission-aware summary API
to show current and historical shipments, their saved allocations and independent
handover/stock states. It reuses the existing create, track, label and retry APIs;
authorized System Managers and Stock Managers confirm physical handover there.
The standard Sales Order list exposes the existing Marketplace Platform and the
linked Marketplace Order's External Order ID; shipping status stays in the form tab.

Each shipment receives a generated immutable `fulfillment_key`. A hidden unique
identity key enforces uniqueness for a non-empty Bosta delivery ID. The former
`active_sales_order` column remains only as legacy historical data and no longer
has a unique index. The migration backfills fulfillment keys, non-conflicting
external IDs, and allocation rows only from an unambiguous linked Delivery Note;
duplicate external IDs or ambiguous links are left unchanged for manual review.

**Creating.** Only **Sales Manager**, **Stock User** and **System Manager** may
create or check a shipment (Sales User is read-only; Stock User can read but not
submit a Sales Order, so the Sales Order check is `read`). The order must be
submitted, not Closed or On Hold, and have available deliverable quantity; this
is checked before any row is inserted or Bosta is called. The flow is: commit,
lock the Sales Order as the first statement of the transaction, compute and
persist the per-row reservation in a `Pending Bosta` row, commit, call Bosta,
persist the result and commit, then re-lock the Sales Order and create/submit
the standard Delivery Note for that reservation inside a savepoint (rolled
back on failure, with the reservation retained). COD is the **outstanding** amount:
`rounded_total` (else `grand_total`) minus `advance_paid`, never below 0, and
rejected locally above Bosta's documented 30,000 EGP limit. The payload sends
the same value as `businessReference` and `uniqueBusinessReference`. The OpenAPI
says COD must be positive for type 10, so a fully paid order (COD 0) may be
rejected by Bosta; that is unverified, the escaped Bosta message is shown and the
shipment ends `Bosta Failed` (retryable). COD is computed only from the Sales Order total minus
`advance_paid`: it does not see payments made against a Sales Invoice, and a
partly delivered order still uses the whole-order outstanding amount (proportional
COD is undecided). Orders in a currency other than the company currency are
rejected, and the amount the dialog showed is sent back as `expected_cod`; if the
recomputed amount differs, creation is refused until the dialog is reopened. A
configuration problem (Bosta disabled, no API key) is rejected before anything is
persisted. A network exception also ends
`Bosta Failed` with an "outcome unknown" message rather than staying Pending.

**City picker, address prefill (#245, #318).** The create dialog picks the city from
Bosta's list instead of typing IDs; there is no district. `integrations/bosta/locations.py`
fetches `GET /cities` (`data.list[]`: `_id`, `name`, `nameAr`) through `BostaClient` and caches
it for 24 hours in the Frappe cache; nothing is cached when Bosta fails or answers in an
unrecognised shape. The whitelisted POST method `api.bosta_shipments.get_cities` (`refresh=1`
refetches; a failed refresh keeps the previous list) requires a creator role. The dialog uses a
Frappe `Autocomplete` (searchable, label = escaped name plus Arabic name, value = Bosta city
ID); a load failure shows an error with Retry and disables Create. `create_shipment` takes
`city_id`. Prefill: the address first line comes from the Sales Order's shipping Address
(`address_line1`, `address_line2`), else the Marketplace Order's `customer_formatted_address`;
the city is resolved as described in the next paragraph, and when nothing resolves the operator
picks it.
**No district: Bosta resolves it (#318).** The create call is `POST /deliveries` **without**
`?apiVersion=1` (that version requires a district and rejects a create without one with
errorCode 777), and `dropOffAddress` is exactly `{city: <Bosta city code>, firstLine}`: no
`districtId`, `districtName` or `cityId`. Bosta works out the district from the city code and the
address text, so the first line should carry the area name. This call shape is not in
`docs/bosta-integration/docs.yaml` (only the `apiVersion=1` call is); it was verified live on
2026-10-22 (the create without a district, with an English and an Arabic address). `locations.get_city(city_id)` returns
`{id, name, code}`: the name `GET /cities` gives the city (stored on the shipment and shown) and
its code from `GET /cities/getAllDistricts` (`data[]`: `cityId`, `cityName`, `cityOtherName`,
`cityCode`; only these are kept, cached 24 hours, a city-list refresh drops it). It is called
before the Sales Order lock and before any row is inserted, and throws for an unknown city, a
city without a code or a blocked lookup, so a city name is never sent in place of a code. The
shipment stores `city`, `city_id` and `city_code` (read-only "Bosta City Code"); the payload
sends `city_code`. The district fields (`district_id`, `district_name`) are hidden and read-only;
only shipments created before #318 have them, and a retry of such a `Bosta Failed` row sends no
district either. Edit sends the same `{city: <code>, firstLine}` (below).
**City resolution (#305, #318).** `city_match.resolve_city(address)` returns
`{city_id, city_name, from_shopify}`: for an Egypt Shopify order, `provinceCode` from the
Marketplace Order's `shipping_address` JSON goes through `SHOPIFY_EG_PROVINCE_TO_BOSTA_CITY_CODE`
to a Bosta city code (`from_shopify` true). The 29 codes were verified against Shopify's Egypt
checkout province list on 2026-10-19 (`SU` "6th of October" and `HU` Helwan are Shopify-only and
map to Giza and Cairo). Else the shipping Address city/state text is matched against the Bosta
city name, Arabic name or code (`from_shopify` false). `get_create_defaults` adds `city_id`,
`city_name` (the `GET /cities` name, the directory's only as a fallback) and `from_shopify`.
**Fail fast:** the first failed directory fetch in a request or job blocks every further lookup of
it in that request (`locations.lookups_blocked`), and the failure is remembered for 60 seconds
so the next request does not retry at once; the affected orders simply fall back to review. A
failure shows no popup. Lookups served from the cache still work while blocked. The earlier
district matching (address text against district names, and the undocumented
`GET /cities/pinLocation`) was removed in #318.
**COD amount (#345).** The Sales Order form and reviewed bulk dialogs show the calculated outstanding COD as the initial value in an editable company-currency field. The existing creator roles may enter any amount from 0 through 30,000 EGP, independently of the outstanding balance. The API keeps `expected_cod` as the calculated default for stale-dialog detection, validates the separate entered amount, and stores only the sent amount in `Bosta Shipment.cod_amount`. Bulk orders sent without review omit the entered value and use the calculated default. Retrying a `Bosta Failed` shipment reuses its stored amount.

**Bulk create (#305).** The Sales Order list action **Create Bosta Shipments**
(`public/js/sales_order_list.js`, registered through `doctype_list_js`; creator roles only; at
most 50 orders, refused with a message naming 50) calls
`api.bosta_shipments.get_bulk_create_plan` (`integrations/bosta/bulk.py`). The plan creates nothing in Bosta;
its only Bosta calls are the cached city lookups above (directory, city names), which stop after
the first failure. An order is Skipped, with a one-line reason, when it is not submitted, Closed or
On Hold, has nothing left to deliver, is not in the company currency, has COD over 30,000, or
already has an active Bosta Shipment. Of the rest, an order whose city came from the Shopify province code
(`from_shopify`), with a receiver phone and an address first line longer than 5 characters, is
sent without review (a city read from the typed Address text may be wrong);
every other order opens the existing Create dialog (`sales_order.js`, shared through
`frappe.marketplace_integrations.open_bosta_create_dialog`) one at a time ("Order 2 of 5",
with Skip). Closing a dialog cancels the whole run and nothing is sent. The skips are listed
before anything is sent. `queue_bulk_create` enqueues one `long` job (`bulk.run_bulk_create`)
that calls `deliveries.create_bosta_shipment` per order, each in its own try/except with a
rollback, so one failure never stops the rest. Progress and results live in the cache under a
job id readable only by the requesting user (`get_bulk_create_status`), shown by
`ShopifyCatalogPushStatus` with the `BOSTA_BULK_OPTIONS` labels (Created / Failed / Skipped,
one line per order). Bosta `errorCode` 777 shows "Bosta could not find the district from this address. Add the area
name to the address and retry.";
other Bosta errors show Bosta's message; Bosta accepted but the Delivery Note failed shows
Failed with the tracking number. **Retry failed** reopens the dialog for the failed orders
with the values already used and sends them again; the existing resume path
(`_resume_existing`) searches Bosta first or creates only the Delivery Note, so a retry never
creates a second Bosta delivery.

Prefill reads Address / Marketplace Order values without permission checks, after the Sales Order read check and the creator-role check (a conscious decision; `shipping_address_name` is not validated against the order's customer).
`get_city` rejects any city id not in the cached/fetched Bosta city list.
The API key is sent to the public `/cities` endpoints too (unverified whether Bosta needs it).

**Bosta Delivery tab on the Sales Order (#246, #271).** Two fixture Custom Fields on Sales
Order (`custom_bosta_delivery_tab`, shown when `docstatus >= 1`, and the HTML field
`custom_bosta_delivery_html`) hold the tab; a draft does not show it.
`api.bosta_shipments.get_sales_order_shipment` (POST) returns the order's current shipment
summary: `name`, `status`, `tracking_number`, `bosta_state`, `active`, `last_update`
(`last_bosta_status_on`), `receiver_name`, `receiver_phone`, `city`, `city_id`,
`address_first_line`, `cod_amount`, `delivery_note` and `delivery_note_status` (the Delivery
Note's status only when the caller can read that Delivery Note, else empty), documented
`bosta_delivery_type`, `bosta_exception_reason`, and `delivery_note_posted` (null when its
read permission is absent). It needs read on
the Sales Order (else a permission error) and on Bosta Shipment (else it returns nothing); it
reads with the caller's permissions. The latest non-Canceled shipment is returned at the top
level; if none exists, the latest Canceled shipment is returned with `active` false. With no
shipments the response is empty.
`Bosta Shipment.cod_amount` is the COD sent when the delivery was created; it is a read-only
Currency system field.
`sales_order.js` asks on every refresh (a reply that arrives after a newer refresh is
dropped) and draws the tab: status, tracking number, Bosta state, last update, COD,
receiver, address (first line and city) and Delivery Note, all escaped. Buttons live
in the tab (delegated click handler): **Create Bosta Shipment** (creators; with no shipment, a
Canceled latest one, or a `Bosta Failed` one without a tracking number - that retry resumes the
same row: search Bosta, then send, and the receiver and address typed in the dialog replace the
row's stored values), **Print A4 Label** (active shipment with a tracking number; follows Bosta
Shipment read; the window is opened inside the click so popup blockers allow it, and if the
browser blocks it the URL is offered as a link) and **Refresh from Bosta** (creators, active
shipment with a tracking number). `Sales Order.custom_bosta_delivery_status` is a read-only,
stored, filterable list column containing the exact state name from the latest non-Canceled
shipment (falling back to the latest Canceled shipment), or the shipment status when its state
is unknown; a Canceled shipment always shows "Canceled" (`bosta_shipment.sales_order_delivery_status()`, shared by the controller and the backfill patch). The Bosta Shipment controller keeps it in sync with that selection. The backfill patch creates the Custom Field from the fixture itself, because patches run before fixtures are synced on a first migrate. It is visible
to anyone who can read the Sales Order. `Bosta Shipment.shipment_fee` is a read-only Currency
field displayed in EGP in the tab only for users who can read Bosta Shipment. It is display-only
and has no accounting effect. A Currency column stores an unset value as 0, so `Bosta Shipment.shipment_fee_received_on` records when Bosta first reported a fee: the tab shows the fee, and the Delivered poll stops asking for it, only once that is set (a real 0 is therefore shown and not re-polled). Patch `backfill_bosta_shipment_fee_received_on` stamps shipments that already store a fee above 0. The dashboard indicator
(status, tracking number, Bosta state, link to the shipment) stays. No shipment shows "No Bosta
shipment"; a failed read says
it could not load (creators still get Create); a user without Bosta Shipment read sends no
request and sees an empty tab. `Pending Bosta` (after 5 minutes), `Bosta Created` and
`Delivery Note Failed` are recovered with **Check Bosta** on the shipment form (labelled
**Retry Delivery Note** for `Delivery Note Failed`, which also shows `delivery_note_error` as a red
banner there and in the Bosta tab), reached through the indicator link. The Sales Order status
column is filterable; status bulk actions are not built.

The Sales Order tab renders normal outbound `SEND` as Created (10/20), Picked up (21), In transit
(24/30), Out for delivery (41) and Delivered (45). Bosta states 47/48/49/100/101/102/103/105
use a problem badge and the stored exception reason where present; 46/60 use a returned badge and
ask staff to create a return Delivery Note against the linked Delivery Note. Other delivery types
show their known raw state instead of outbound steps. The dashboard indicator turns red for
problem/returned states and a delivered `SEND` without a submitted Delivery Note. These are
presentation/reporting changes only; carrier state does not change stock or create/cancel a
Delivery Note.
**Refresh from Bosta (#271).** `statuses.refresh_shipment_state(shipment)` (creator roles
only; whitelisted as `api.bosta_shipments.refresh_shipment`, POST) does one
`GET /deliveries/business/{trackingNumber}` and feeds the documented `data.state` to the same
`apply_state` as the poll and the webhook (timestamp = the instant the read started), so state
`49` records carrier cancellation without automatically canceling a submitted Delivery Note,
and a stale read cannot overwrite a newer webhook. A `SEND` state 21 is the automatic physical
handover event and posts the Delivery Note once. Unlike the poll the refresh does not skip an
unchanged state, so the last-update time moves. A Bosta error (escaped), a network failure, a
body without a readable state or an unrecognised state code raises and stores nothing.
It also reads numeric, nonnegative `data.shipmentFees`; missing or invalid fee data leaves the
stored fee unchanged. The scheduled poll keeps reading state 45 only while this fee is blank;
manual Refresh always reads it. The confirmed fee currency is EGP (the response has no currency
field).
**Cancelling (#272).** `statuses.cancel_bosta_shipment` (creator roles; whitelisted as
`api.bosta_shipments.cancel_shipment`, POST; the tab's **Cancel Bosta Shipment** button asks
for confirmation first and nothing is sent before it) terminates the delivery with
`BostaClient.terminate_delivery` (`DELETE /deliveries/business/{trackingNumber}/terminate`, no
body; the documented success reply is `success: true`). It refuses locally, without calling
Bosta, only when there is no tracking number, the shipment is already `Canceled`, the stored
state is Delivered (45), or the Delivery Note is on a submitted Sales Invoice; every other
state goes to Bosta and a Bosta error is shown escaped with nothing changed. On success it
sets `Bosta Shipment.bosta_terminated_on` and marks the carrier shipment `Canceled`. It never
automatically cancels a submitted Delivery Note or reverses its stock posting. A shipment
without a posted Delivery Note releases its reservation; a posted shipment retains its
Fulfilled reservation. A network error has an
unknown outcome: nothing is changed, then `refresh_shipment_state` reads the delivery back; a
reported 48 (Terminated) or 49 finishes the local cancel, anything else (or a failed read)
tells the user to verify in Bosta. When `bosta_terminated_on` is already set or the stored
state is 48/49, a Cancel click skips the DELETE and only finishes locally. If that local finish
itself fails after Bosta accepted, the failure is rolled back and logged, `bosta_terminated_on`
and `delivery_note_error` are written best-effort so the poll retries it, and the user is told
the cancel will be retried. The client's own "Failed to reach Bosta" popup is cleared on these
recovery paths. The tab hides the button for non-creators, `Canceled`
shipments, shipments without a tracking number and state 45 (the summary carries
`bosta_state_code` for this). Not built: side effects for a webhook state 48, cancelling
Sales Invoices, bulk cancel.

**Editing (#273).** `editing.edit_bosta_shipment` (creator roles; whitelisted as
`api.bosta_shipments.edit_shipment`, POST; the tab's **Edit Bosta Shipment** dialog shares the
city picker with the create dialog and asks for confirmation before anything is
sent) calls `BostaClient.update_delivery` (`PUT /deliveries/business/{trackingNumber}`). The body is
exactly `receiver.phone` and `dropOffAddress` (`city` code, `firstLine`; no district since
#318, unverified live until the user tests it); never
COD, open-package, images or the receiver name. It refuses locally, without calling Bosta,
unless the shipment has a tracking number, is not `Canceled`, and its stored state is one of
Bosta's documented editable states `{10, 11, 20, 21, 22, 24, 30, 41, 47}` (no stored state yet:
"Refresh from Bosta first"). A Bosta refusal or a network error changes nothing locally and
tells the user to verify in Bosta (no auto-reconcile: the shape of the GET address is
unverified). On success, under the Sales Order lock, only the Bosta Shipment fields are
updated (`city`, `city_id`, `city_code`; the old district fields are cleared). The Sales Order and its address,
Addresses, any Marketplace Order and the Delivery Note are **not** changed, and nothing is pushed
to Shopify: those must be updated by hand if needed. If recording fails after Bosta accepted,
the local change is rolled back and the user is told Bosta has the change. The same message is
shown (and nothing written) when a webhook canceled the shipment while Bosta was updating.
Once a shipment has a tracking number its receiver and address fields are locked for everyone
(server `validate`, plus `read_only_depends_on` in the form) except the system write flag, so
Edit is the only path; shipments without a tracking number stay editable and retryable.

**Recovery.** A retry of a `Bosta Failed` shipment, and the **Check Bosta**
action (shipments that are Pending for more than 5 minutes, Bosta Failed, Delivery
Note Failed, or Bosta Created without a Delivery Note), first search Bosta by
`businessReference` (`POST /deliveries/search`; searching by
`uniqueBusinessReference` is not documented). Found: the delivery ID and
tracking number are linked; the check itself has no stock effect. A check observing `SEND`
state 21 can resume handover posting. Not found:
`Bosta Failed`, so a retry is allowed. An unrecognised search response is an
error, never "not found". The live search response (seen 2026-10-19) is
`data: {count, deliveries, limit, page}`; `deliveries` is read as the result list,
and a `count` larger than the returned page is treated as ambiguous.

**Shipment reservation lifecycle.** `reservation_status` is `Reserved` while a
shipment holds quantities, `Released` after a definitive Bosta failure or a
successful cancellation before stock posting, and `Fulfilled` after the linked Delivery Note submits.
An ambiguous Bosta outcome remains reserved until Check Bosta resolves it. Carrier cancellation
never changes a submitted Delivery Note. There is no
terminal Returned status: state `46` is stored only, and the "Returned to
business" return Delivery Note remains blocked.

**Delivery Note permissions.** Delivery Note posting runs from the handover
workflow with system-level document writes after the caller is authorized to
confirm handover (System Manager or Stock Manager). A posting failure keeps the
reservation and records `stock_posting_status = Failed`; an authorized handover
retry resumes posting. No session switch to Administrator is made in desk
requests (it corrupts the logged-in session).

**State application.** The state is applied by one function
(`statuses.apply_state`) for both webhooks and the 30-minute poll. It takes the
Sales Order lock then the shipment lock, ignores events not newer than the stored
`last_bosta_event_timestamp` (a poll uses the instant the read started, so a stale
poll cannot overwrite a newer webhook; this assumes Bosta's clock and ours are
roughly aligned), stores only documented fields including the delivery type.
Only a documented carrier event or poll establishes the stored delivery type;
the requested type in the create payload is not evidence of the actual type.
Historical rows without reliable type evidence stay blank.
Automatic `21` handover and `Check Bosta` posting both require `SEND`; a poll
without type information can update status but cannot establish the handover.
Carrier cancellation state `49` never cancels a submitted Delivery Note. Unknown tracking numbers, state codes and delivery
types are logged and skipped (HTTP 200); only bad authentication or a malformed
body is an error. The webhook is `allow_guest`, so its processing runs as
Administrator and restores the caller afterwards. The poll skips terminal states
(`45` Delivered, `49` Canceled), Canceled shipments and shipments older than
60 days. Bosta webhooks use the configured custom `X-Bosta-Webhook-Secret`
header. System-set fields are rejected server-side for anyone but System
Manager/Administrator, not only read-only in the form; the status snapshot JSON
is rendered escaped, and remote error text is escaped before `frappe.throw`.

**Needs Attention (#343/#344).** Bosta Shipment rows with failed Delivery Note posting
(`delivery_note_error`), an exception state (47/100/101/102/103/105, not for a Canceled shipment; 48 and 49 are not listed), a return state
(46/60), a delivered `SEND` (45) without a submitted linked Delivery Note, or a tracking number
with no Bosta update for 5 days are listed in Marketplace Needs Attention (platform `Bosta`, no
account). The stale rule uses the poll exclusions: it ignores states 45/49, Canceled shipments
and shipments older than 60 days. A return finding clears only after a submitted return Delivery
Note has `return_against` set to the shipment's linked Delivery Note. State 103 also creates a
Desk System Notification for Sales Manager, Stock User, System Manager and Bosta User. These
indicators and notifications do not change carrier state or stock.

The Bosta AWB documentation confirms that `POST /deliveries/mass-awb` returns
a base64-encoded PDF for a request of 50 or fewer AWBs. The live endpoint answers
`{"success": true, "data": "<base64 PDF>"}` (verified 2026-10-16). The MVP requests only
A4/Arabic labels, enforces that 50-label ceiling locally, decodes that JSON
shape and a bare base64 body (any other shape is rejected, not guessed), shows Bosta's
escaped error message for a non-success reply (including `success: false` on HTTP 200), and saves each requested label as a private `File`
attached to its `Bosta Shipment`; a shipment reader may request it on demand.
The different response shape above 50 labels is intentionally unsupported.
Automatic creation of a Sales Return from a carrier event remains blocked: the supplied
lifecycle does not define a standard-`SEND` return state, and neither polling nor callbacks may
infer one. Returned states only surface a Needs Attention finding; staff record the return
against the linked Delivery Note themselves.

### Order hover card on the Sales Order list (#325)

Every Sales Order list row opens a hover/focus card (customer and phone, items, platform order number, platform and payment status, Bosta status and tracking number, last sync status and error, total) built on `frappe.ui.hover_card`, plus a per-row "Details" button that shows the same content in a dialog for touch. The shared helper is `public/js/order_hover_card.js` (`frappe.marketplace_integrations.order_hover_card.create({method, arg, render})`, loaded from `sales_order_list.js`; the Marketplace Order list can reuse it with its own endpoint and renderer).

- **Anchor.** The trigger is the row's subject link (`.list-subject a[data-name]`), not the whole row, with `side: "bottom", align: "start"`. The card therefore never sits over the row checkboxes (they are before the link) and passing over the checkbox column opens nothing. Keyboard: focusing the link opens the card; arrow-key row navigation focuses the row container, which is not a trigger, so scrolling with the arrows sends no requests. Tab order is link, ..., Details button; Frappe's `tabindex="1"` rows make Tab visit all rows first, which cannot be changed from here.
- **Lifecycle.** A `MutationObserver` picks up new rows and destroys the card of every removed row (refresh and re-render remove rows without firing pointerleave/blur); the `page-change` event closes open cards. The card instance is read once from the trigger's jQuery data right after `frappe.ui.hover_card(...)` and kept in a `WeakMap` keyed by row inside `create`; cleanup and the page-change close use that handle, never `.data("es-hover-card")`, because Frappe removes rows with jQuery `.remove()` (`list_view.js` `render_list` / `remove_list_items`), which wipes jQuery data before the observer callback runs.
- **Data.** Lazy fetch, cached per document (one request per order per page load, failures are not cached), a response for a superseded card or dialog is ignored, skeleton then the card or the escaped server error. The endpoint `api/order_hover_card.py::get_sales_order_card(sales_order)` requires read on the Sales Order doctype (checked before the existence check, so a user without it gets `PermissionError` for any name) and on that document, and returns the Marketplace Order, Sync Log and Bosta parts only when the caller can read those doctypes (Bosta via `deliveries.get_sales_order_shipment`). The marketplace part (and with it the last sync status) is shown only to System Manager/Administrator or holders of the order's platform role (`Talabat User`, `Noon User`, `Shopify User`), because Marketplace Order rows are filtered by platform (#322); any other user, even with Marketplace Order read, gets `marketplace: null`. The Bosta part does not depend on a platform role. The endpoint returns only what the card renders. A missing order raises `ValidationError` (HTTP 417) so Desk shows no modal; a 404 would open one (see `docs/frappe-conventions.md`). The reference is `platform_order_reference`, falling back to `external_order_id`, never the `MKTORD-` name. The built-in link preview on Sales Order is not enabled.
- **Browser acceptance (user check).** Not covered by automated tests: on a narrow viewport, confirm the card opened from the subject link does not overlap or hide the checkbox column awkwardly (see `docs/ui-customization.md`, Browser acceptance checks); also confirm that after a list refresh with a card open, the card disappears.
- **Dependency.** Needs `frappe.ui.hover_card` (present on dev Frappe 16.51.0; prod version to check): without it the rows only get the Details button. Guarded by `test_order_hover_card_js_wiring.py`. The `__mi_list_extended` flag on `frappe.listview_settings["Sales Order"]` keeps `sales_order_list.js` from wrapping `onload` twice.

### Marketplace Account

A Marketplace Account answers: **Which seller/store/vendor account are we operating on, and which ERPNext stock partition does it use?**

Core relationship:

```text
Marketplace Account
- platform
- external_account_id
- connection (Dynamic Link to the platform-specific Connection)
- warehouse
- erpnext_company (required only for Sales Order synchronization)
- erpnext_selling_price_list (required for Sales Order synchronization and Talabat catalog sync)
- erpnext_customer (generic Customer created on the first successful Sales Order sync)
- last confirmed external outlet-status cache (status/reason/until/check time/error/full payload)
- enabled
```

Examples:

```text
Talabat Vendor A ──→ Talabat Warehouse A
Talabat Vendor B ──→ Talabat Warehouse B

Shopify Main ──────┐
                   ├──→ Shared Online Warehouse
Instashop Main ────┘

Noon Main ─────────────→ Noon Warehouse
```

For this business, channel quantities are **true inventory partitions**, not virtual selling limits. ERPNext Warehouses are therefore the stock-pool model. Never duplicate the same physical quantity across multiple Warehouses merely to represent a sales limit.

### Marketplace Product Mapping

A mapping answers: **Which ERPNext Item does this external marketplace listing represent?**

One document represents one external listing:

```text
Marketplace Product Mapping
- marketplace_account
- platform (read-only, fetched from marketplace_account.platform)
- item
- external_reference
- external_product_id (optional)
- external_sku (optional)
- external_barcode (optional)
- external_variant_id (optional)
- sales_uom (optional)
- enabled
- sync metadata
```

`external_reference` is the platform implementation's canonical runtime lookup value. Core mapping code does not guess whether the platform uses SKU, barcode, product ID, or variant ID.

Runtime resolution is exact:

```text
Marketplace Account + external_reference
        ↓
Marketplace Product Mapping
        ↓
ERPNext Item
```

No fuzzy matching or automatic SKU/barcode inference belongs in runtime order processing.

The model intentionally allows multiple external listings in the same Marketplace Account to point to the same ERPNext Item:

```text
ITEM-001
└── Talabat Account A
    ├── Listing 82191
    └── Listing 99281
```

Do not add a uniqueness rule on `(marketplace_account, item)`.

## Inventory rules

- Marketplace Account → Warehouse is the inventory partition boundary.
- Multiple Marketplace Accounts may share one Warehouse.
- A Marketplace Account may have its own Warehouse.
- Marketplace-facing stock reads must use the configured account Warehouse only; never silently sum other Warehouses or fall back to global stock.
- Missing Warehouse/configuration should fail closed according to the implementing issue, not invent a stock source.
- UOM conversion should use ERPNext's native Item/UOM model when a marketplace listing sells a pack/unit different from the Item stock UOM.

### ERPNext behavior the Sales Order sync relies on (derived from source, 2026-10-11)

- **Shipping** is an `Actual` Sales Taxes and Charges row on an Income (or Tax/Chargeable) account, the same mechanism as ERPNext's Selling Shipping Rule (`add_shipping_rule_to_tax_table`). An `Actual` charge is distributed over the items by `net_amount / net_total`, so it is lost on a zero-value order (the sync blocks that case). The Desk account picker for sales tax rows offers only Tax/Chargeable/Expense accounts; an Income account works when set by code, as the sync does.
- **Cancelling a Sales Order** is blocked by SUBMITTED linked documents and by draft Sales Invoices, not by draft Delivery Notes or Payment Entries; the sync therefore holds the marketplace-driven cancel itself while any of those drafts exist (#226).
- **Returns:** a Sales Return / Credit Note lowers `delivered_qty` / `billed_amt` through negative rows linked by `so_detail`, which is how a Needs Attention order clears. Derived from source, not verified live.
- **Cancel and amend does not clear a changed shipping charge (found 2026-10-11, from source).** The reconciliation message for a changed shipping charge says "cancel and amend it". After the submitted Sales Order is cancelled and amended in ERPNext, `Marketplace Order.erpnext_sales_order` (read-only) keeps pointing at the cancelled order: nothing in the app follows `amended_from` or relinks. On the next sync `plan()` sees `docstatus != 1`, and because the marketplace order is not cancelled it falls to "The linked ERPNext Sales Order is no longer an active submitted document." (Needs Attention, with the platform instruction appended); `_inactive_order_converged` only counts a cancelled link as converged when the marketplace order itself is cancelled or all lines are zero. The amended Sales Order is never adopted, so the status cannot clear by this remedy. Follow-up (not built): a relink to the amended Sales Order, or another way to accept a manually corrected order.

**Two forward-looking risks flagged during #31 review remain open — notes only, no code guard added yet (`Marketplace Account`'s `account_identity_key` computation is correct as-is for every write-path that exists today):**

- `account_identity_key` is only ever recomputed in `before_save()`, so it **goes stale if a future migration/patch writes `external_account_id` or `platform` via `frappe.db.set_value()` or raw SQL rather than `doc.save()`.** #38 avoids that risk by constructing and saving each `Marketplace Account` document normally. Any future bulk change must do the same, or explicitly recompute `account_identity_key` itself (via `compute_account_identity_key()`) after any bulk write.
- `Marketplace Product Mapping`'s `mapping_identity_key` has the identical exposure under direct writes. #38 likewise uses normal document writes per row. Additionally, `mapping_identity_key` embeds a Link value (`marketplace_account`, the document *name*, not a surrogate ID) — so it also goes stale if a `Marketplace Account` is ever **renamed**, since Frappe's rename machinery updates linked fields via direct `frappe.db.set_value()`-style writes, never through the linking document's own `.save()`/`before_save()`. This is currently latent (neither `Marketplace Account` nor `Marketplace Product Mapping` sets `allow_rename: 1`, so renaming isn't possible today) but worth recording now, before someone adds that flag later without realizing it would silently desync every `mapping_identity_key` referencing the renamed account.

# Shopify cancellation and nightly order reconciliation (#353/#354)

Unlinked Shopify orders with a full cancellation are terminal `Cancelled` if
unpaid or fully refunded. Paid, partially paid, or partially refunded
cancellations remain `Sync Error` with a refund instruction. Shared order
upsert preserves `Cancelled` for unlinked canceled Shopify orders; linked
orders retain the regular Sales Order reconciliation status path. `Cancelled`
is excluded from the existing unmapped and Sync Error metrics by their existing
status/cancellation filters.

At `23:59` site time, a small coordinator queues one deduplicated long job per
enabled Shopify/Noon account. Only this nightly Shopify job opts into unlinked
catch-up and canceled-paid retries; the existing daily Shopify watermark sweep
continues to reconcile linked-order changes only. Shopify uses its existing
persisted watermark and overlap. Noon uses
its existing seven-day order import window and records `Scheduled
Reconciliation` as the debounce trigger. The Noon catch-up is a flag
(`catch_up_unlinked`) passed through `enqueue_order_import` and
`run_order_import`, not keyed on the trigger source (the hourly poll uses the
same trigger source and must not run it), and it has its own RQ job id.
Imports only bump the existing Sales-Order debounce; Sales Orders are not
created inline. Per-account enqueue failures are aggregated in one Error Log
entry. `services/marketplace_order_reconciliation.py` holds the coordinator
(`enqueue_nightly_order_reconciliation`), the shared `schedule_first_syncs()`
(skip-if-already-pending through
`sales_order_sync_debounce.bump_sync_debounce_unless_pending`), the
`write_catch_up_summary()` Sync Log row per account (orders imported, first
syncs scheduled, failures; trigger source Scheduled Reconciliation) and the
cancelled-order status constants shared by `sales_order_sync` and the
`reconcile_cancelled_shopify_orders` patch. The nightly job has no age or date
cutoff (open decision). The production System Settings
timezone must be checked before deployment; dev/test scheduler evidence is
Asia/Kolkata.
