# Delivery Note-first fulfillment (decided 2026-10-29)

Status: decided. Epic #392 is superseded by epic #413 / #415: the Noon adapter behind the neutral carrier contract creates the shipment on Submit (Bosta shape), and the old flow (create, cancel, handover, discard, retry paths, `handover_state.py`, `delivery_note_drafts.py`, `delivery_note.js`, the AWB pool, the shipment child tables) is removed (#415, phase 4). Read `docs/noon-integration/README.md` and `business-spec.md`; the text below is the original direction. See also `docs/noon-integration/fulfillment-release.md`. This document records the agreed direction so the plan, the issues and the code follow it.

## Decision

Fulfillment is driven from the Delivery Note instead of from each platform's own shipment flow.

1. A person creates a draft Delivery Note from the Sales Order (ERPNext's `make_delivery_note`).
2. Creating the draft triggers a per-platform adapter that calls the platform or carrier API to create the shipment (Noon: `CreateShipment`; Bosta: create delivery).
3. The tracking number and AWB come back and are saved on the Delivery Note (or on ERPNext's native Shipment doctype if the native check below prefers it).
4. A person reviews and presses Submit. **Decision (#500, epic #502; reverses the 2026-11-02 decision, confirmed by the user)**: the submit moves from "right after Created" to "when the carrier picks the parcel up", and it depends on the carrier. **Bosta** (adapter flag `SUBMIT_AT_PICKUP`): Create Shipment / Submit starts the create job; once Bosta confirms Created the note STAYS A DRAFT in the stage Shipment Created (label job queued then, `after_created`). `request_create` records the person who asked in `custom_shipment_requested_by`. The first Bosta event or refresh that enters a pickup code (`statuses.PICKUP_CODES`) queues a short, deduplicated job after commit (`carrier_shipments.queue_submit_at_pickup` -> `run_submit_at_pickup`) that submits the draft as that person (`frappe.set_user`, no `ignore_permissions`, so the Authorization Control and credit-limit rules judge the requester, and the Version owner that `_submitter` reads is the requester). A repeated or out-of-order event queues nothing once the note is submitted or the event is older (`custom_bosta_last_event_at`). The stage then comes from the ONE mapping table `statuses.STAGE_BY_CODE` (`fix_state_after_submit` on submit, `_write_state` afterwards); a stage never moves backwards, except to Exception and to Delivered (45) from Lost / Damaged (`statuses.STAGE_RANK`, `may_move_back`); a submitted note never gets a draft-only stage (`delivery_note_workflow.state_for` gives at least Picked Up). Lost and Damaged (100/101) submit a draft like any pickup code (staff wait for Bosta to return the shipment) and, on any non-return note, show a red banner and indicator on the form beside the Carrier Exception row. A cancel code (48/49) on a draft cancels the shipment (Integration Status Cancelled), it never submits. A refresh or poll that sees 45/46/60 on a draft submits it first, then queues the draft return as for any submitted note (`after_pickup_submit`). With no requester recorded (a shipment started before #500) the note's owner is used. The job tries the submit up to 3 times (`PICKUP_SUBMIT_ATTEMPTS`): the first on the short queue, each retry a separate job on the long queue that waits 30 seconds first (`PICKUP_SUBMIT_PAUSE_SECONDS`; this Frappe has no delayed enqueue, and a short-queue worker must not sleep). If it still fails (stock, credit limit, authorization) the note stays a Created draft with `custom_last_integration_error` ("X picked the shipment up; the Delivery Note could not be confirmed: ..."), and Needs Attention shows "Picked up but not submitted" with a Retry that queues the job again (`api/carrier_shipments.retry_pickup_submit`: needs a pickup status, never changes the note; the job falls back to the note's owner when no requester is stored). **Nobody submits a Created Bosta draft by hand before the pickup (decided 2026-11-09)**: `carrier_shipments.require_shipment_created` refuses it with "The Delivery Note is submitted when Bosta picks the shipment up" unless the pickup job set `PICKUP_SUBMIT_FLAG`; the form's Submit and the Confirm Shipment workflow action are refused the same way, and the bulk path never submits. A Created draft is no longer a problem by age for Bosta. **Noon** is unchanged: its create job still submits the note as the user who pressed Submit once Created (`_submit_created`), and a Created draft older than 15 minutes is a Carrier Exception. Only `request_create` with `submit_as` (the form's Submit or Create Shipment and the bulk path) records the requester; Check, the nightly job, a retry that nobody asked for and return pickups never submit. The T9 mapping of Bosta codes to stages (which codes are Picked Up and In Transit) is PROPOSED and unconfirmed (epic #502); it lives only in `STAGE_BY_CODE`. **Pre-flight (#476):** before any carrier call, `carrier_shipments.request_create` (every carrier, form Submit and bulk alike) runs `check_deliverable`: a stock item row asking for more than the Bin `actual_qty` of its warehouse (unless negative stock is allowed), or more than the Sales Order has left to deliver (over-delivery allowance and the over-delivery role count), is refused with one message naming each item, no "Create" Integration Request row and no carrier call. A Product Bundle row is judged by its components, as ERPNext posts it (`SellingController.get_item_list`: the parent row is not a stock movement, only its `packed_items` are): each packed item's `qty` (already bundle qty times the parent's stock qty, in stock units) in `packed.warehouse or row.warehouse`, summed per (item, warehouse) with the plain rows, so one component used twice is checked together and the message names the component item code. The packed items are built by the Delivery Note's own `validate` (`make_packing_list`) when the draft is inserted or saved, so they exist on the bulk draft and on the form; they are read, not rebuilt (a rebuild without the saved copy would reset an edited packed warehouse). There is no over-delivery check for a Product Bundle row (the parent is a non-stock item and ERPNext's `fetch_items_with_pending_qty` only judges stock items). Components are judged on the packed items as last saved: ERPNext rebuilds them at submit, so a bundle edited after the draft was saved can still end as a Created draft in Needs Attention. The check is skipped when the note already stores a carrier reference (a retry after Creation Unknown must reach the lookup-first read, whatever the stock is now). Quantities in the message use the qty precision and the stock figure never shows below 0. Not judged (they still end as the Created draft below): the stock race, Stock Reservation Entries, credit limit and Authorization Control. If a submit by the Noon job fails, the note stays a Created draft with `custom_last_integration_error` ("Shipment created at X; the Delivery Note could not be confirmed: ..."), Needs Attention flags it (Carrier Exception, also any Noon Created draft older than 15 minutes), and a person submits it natively (`before_submit` still requires Created).
5. If the carrier call fails, the draft stays and the error shows in Needs Attention with a retry.
6. Cancelling the Delivery Note cancels the carrier shipment (the form's Cancel runs the carrier cancel first). **Deleting a DRAFT note with a live shipment (Created, Cancellation Pending, Cancellation Unknown) cancels the shipment first (decided 2026-11-09)**: `on_trash` runs `carrier_shipments.guard_delete`, which calls `carrier_shipments.cancel`; only a confirmed cancel lets the delete go on. If the carrier refuses (for example after pickup) or the answer is unknown or pending, the delete is BLOCKED with the carrier's reason (escaped) and a second delete asks again. Creating and Creation Unknown still block a delete; before_cancel (`guard_cancel_or_delete`) still refuses a live shipment. Deleting needs write permission on the note as well (the carrier cancel). `cancel` commits before it locks and after the carrier answered; that is safe in `on_trash` because the delete has changed nothing yet, and if the native delete then fails (a linked document) the note stays with Integration Status Cancelled, which a later delete passes without asking the carrier. The list's bulk delete calls the same hook per note (a note that is blocked is reported as undeleted, the others go on); the "Cancel Bosta Shipment" button stays as the explicit step. Cancelling a Sales Order with a live Delivery Note is blocked by ERPNext's own linked-document check, so no custom cancel-refusal rules are needed.
6a. See "One-step failure and delete" below for the note a one-step flow deletes when the shipment definitely fails.

Why: one flow for every platform (a new platform is one adapter), stock moves correctly for Shopify and Talabat (today only Bosta creates a Delivery Note, see #368), and the dependency between shipment and Delivery Note is enforced by ERPNext instead of by custom tracking code.

## Rules agreed

- One Delivery Note per shipment. For Noon, units of the same SKU are interchangeable, so the adapter picks `mp_item_nr` values by SKU and quantity from the Delivery Note rows.
- The carrier is ERPNext's native `transporter` on the Delivery Note (Supplier "Noon" for Noon), not a custom Carrier field. On the form it is labelled "Carrier", and `lr_no` "AWB / Tracking No" (Property Setters in `fixtures/property_setter.json`); both, with `lr_date`, sit under the customer on the Details tab so the AWB can be typed before the first save. Carrier Status and Carrier Error follow them (read-only, `custom_carrier_error` only when status is Error). It is locked, with the item rows and `lr_no`, once the adapter has started the shipment. Defaulting the transporter per Marketplace Account (Shopify to Bosta) is deferred to the Bosta work.
- Mark Out of Stock stays a standalone dialog calling Noon `UpdateOrder` (valid only before a shipment exists). On HTTP 200 the existing sync and reconciliation planner updates the Sales Order. It is not part of the Delivery Note.
- The Delivery Note is created by a person from the Sales Order, not automatically on Sales Order submit, because automatic shipment creation would remove the chance to mark units out of stock first.
- Noon was built first. Bosta is the second adapter (epic #413, `docs/bosta-integration/README.md`): the shipment is created when the Delivery Note is submitted (a background job started by Submit or Create Shipment that the form waits for; the note then stays a draft until Bosta's pickup event submits it, see Decision 4), through the carrier-neutral Shipping section. A next carrier plugs in with one adapter module, one row in `services/carrier_shipments.CARRIERS`, a Supplier and its carrier-specific fields. Noon will join the same Shipping section in a separate epic.
- Manual delivery: one transporter Supplier "Manual delivery" (`is_transporter` = 1, Arabic "توصيل يدوي") created by patch `create_manual_courier_suppliers`, with no adapter in `CARRIERS`. Staff say who delivered (inDrive, Uber, own driver) in the native Delivery Note Driver Name / Vehicle No fields (transport section, which opens once a Carrier is set); no field was added. The patch first created three Suppliers (inDrive, Uber, Own driver); they were replaced by this one (2026-11-04) and on sites where the old patch ran they are disabled by hand, so old notes stay valid. `adapter_for()` returns `None` for it, so a Delivery Note with this transporter behaves as a plain ERPNext Delivery Note: no API call, no job, Integration Status stays empty, no Needs Attention item, no carrier button or banner on the form. Only the Delivery Note list colors the courier pill ("Manual delivery" green; any other carrier grey). No cost, shipping status or COD for them yet. Caveat: a Delivery Note of a submitted Noon-linked Sales Order is always claimed by the Noon adapter, which forces the transporter to Noon, so Manual delivery does not apply to Noon orders. Tests: `services/test_manual_couriers.py`.
- Rely on ERPNext native features and do not re-invent until really needed. Every custom field, doctype, hook or guard in the plan must name the native option that was checked (native Delivery Note transporter and `lr_no` fields, the native Shipment doctype with `awb_number` and `tracking_url`, native linked-document cancel checks, native delivery status) and why it was rejected.
- No ERPNext or Frappe core files are edited. Everything lives in `marketplace_integrations`: Custom Fields as fixtures, `doc_events` in `hooks.py`, whitelisted methods, client scripts.

## Editing a Shopify order before pickup (#500 part 2, epic #502)

User decisions: the whitelisted **Edit Order** action REPLACES "Update Items" on a submitted Shopify Sales Order (the button is dropped, see `public/js/sales_order.js`); anyone who may edit the Sales Order may use it before pickup (the API needs write and submit on the Sales Order, because `update_child_qty_rate` checks the session user; the Marketplace Order marker is a system write, so no Marketplace Order permission); after pickup nobody may edit, no override role; rate edits are out of scope; the automatic draft note of #499 was removed, so a draft Delivery Note may or may not exist and both cases are handled. Code: `services/order_edit.py`, the shared send in `services/marketplace_outbound.py::send_shopify_order_edit(preview_fn, apply_fn)`.

- **Stage lock.** "Picked Up and later" = a SUBMITTED Delivery Note exists for the order (a Bosta note is submitted by the pickup event, a manual or plain note by the person; `delivery_note_workflow.STATE_DOCSTATUS` maps Picked Up, In Transit, Delivered and Returned / Failed to docstatus 1). Edits are refused for everyone then (decided for #501: no manager override role). While the draft note has a started carrier shipment (Integration Status not Not Created / Creation Failed: Shipment Requested or Created) edits are ALLOWED (user decision): the ERPNext note rows follow (the refresh sets `skip_carrier_shipment` for that save, which skips only the adapter's row lock). **Bosta (#501)** can only update the COD, not the items, the parcel description or the label, so an edit of an order with a Created Bosta draft runs in this order: (1) Bosta COD PUT (`bosta/editing.update_cod`, body `{"cod": n}`, `DeliveryEditBody.cod` in docs.yaml; the old value is kept so it can be put back), (2) the Shopify edit, (3) the local changes. The new COD is the COD rule (`delivery_note_shipment.cod_from_totals`, the same as the form's default and the bulk path's for a whole-order note) on the totals the order WILL have, calculated on an unsaved copy (`order_edit.cod_plan`); a note that ships only part of the order, a shipment that is Creating / Creation Unknown / being cancelled (`cod_plan` refuses an edit; a change that comes from Shopify is HELD as Needs Attention, `ORDER_LOCKED_BY_SHIPMENT`, until the result is known, `update_hold_reason`), a Bosta state that does not allow editing, a COD already different from Bosta's, or a new COD over Bosta's 30,000 limit refuses the edit before anything is sent. A shipment Bosta cancelled changes the note rows only. If Shopify rejects the edit (the Marketplace Order edit marker is clear), `_restore_bosta_cod` PUTs the old COD back; an unknown Shopify outcome (marker kept) does not revert, because Shopify may hold the edit. If Bosta's answer to a PUT is Unknown (timeout, 5xx, 429) the edit stops before Shopify and the note is listed in Needs Attention as **Bosta COD Differs** with Retry; so is a failed revert. The state is kept in the request snapshot (`custom_carrier_request_snapshot.cod` = the COD Bosta was last sent, written BEFORE the call and put back only on a definite 4xx refusal); `custom_cod_amount` is what ERPNext wants; a difference between them is the row, computed live (`marketplace_attention._collect_bosta_cod_differs`). Retry (`api.bosta_shipments.retry_cod_update` -> `editing.sync_cod`) sends `custom_cod_amount` again; a PUT of the same value is harmless, so the repeat is also the check of an unknown answer (no separate read). When a label is stored (`custom_shipping_label`), every successful COD PUT queues a short job per note AND COD (`queue_label_refresh` -> `fetch_label(replace=True)`; a second update while one runs queues its own and the older job skips itself when the note's COD has moved on) that requests a new label; if that fails the stored label is dropped (it shows a COD Bosta no longer has) and Fetch Bosta Label gets it again. Edits that come from Shopify (planner) set the started note's COD with the same rule but do not call Bosta (an offline job): the difference is the same Needs Attention row. Both note paths are covered because the refresh reads the draft note, not how it was made (the bulk path writes `custom_cod_amount` and `custom_cod_confirmed = 1`, the same fields). The Sales Order Item hooks (`before_update_after_submit`, `before_insert`, `on_trash`) enforce the pickup lock for every path, including an edit that comes from Shopify, and ALSO refuse every item, quantity or rate edit before pickup that is neither Edit Order (`apply_edit` sets `_EDIT_FLAG` around `update_child_qty_rate`) nor Shopify's own (the planner's `marketplace_syncing_orders`): ERPNext's Update Items called directly is refused, and the old "Send item changes to Shopify" button and its endpoints were removed (their flow edited the rows first). **Draft notes rule (decided 2026-11-09):** Edit Order and an edit that comes from Shopify are REFUSED / HELD, before anything is sent, when the order has more than one draft Delivery Note or a draft that does not ship the whole order (or also holds items of another order), with a message naming the note (`order_edit.draft_note_problem`; the planner path holds with `ORDER_LOCKED_BY_SHIPMENT`, no new reason code), so `refresh_draft_note` only ever runs for one whole-order draft and never overwrites a partial note. The bulk path always makes one whole-order draft.
- **Quantities, removals and added items; no rate edits.** A quantity of 0 removes the row, removing every row is refused (cancel the order). An added item (a row without `docname` in the dialog; the item of an existing row cannot be changed) gets the current Item Price of the Marketplace Account's ERPNext Selling Price List (`listing_price.resolve_listing_price`, stock UOM, account warehouse); with no price list or no price it is refused before Shopify is called. After the commit the re-baseline (`rebaseline_after_outbound_edit(correct_rates=True)`) stores a baseline holding ERPNext's own rate and amount, so the planner sees only the price difference and queues an update to Shopify's price (without it the difference would be a plain divergence). The reviewed change list is the #356 preview built on the proposed rows, with its fingerprint.
- **Sequence** (no row lock across the Shopify call): preview (no lock); for a Confirmed (fully reserved) order a reservation dry run under the Bin locks (`order_reservation.edit_shortfalls`), committed before Shopify is called, so a quantity increase without stock is refused first; Marketplace Order lock, marker `in_flight` committed, `commit_order_edit`, marker `completed` committed; then ONE transaction (`apply_edit`: Sales Order row lock, then the draft Delivery Note row lock (the pickup submit locks the note, then the order and the Bins), then the Bin locks, right after a commit; `update_child_qty_rate`, the draft note rows, `reserve_or_wait(refuse_partial=True)` for a Confirmed order, `keep_reservation=True` for a held Waiting for Stock order: a shortfall releases nothing), then the #356 re-import and re-baseline. If the transaction fails, everything of it is rolled back, the marker stays `completed`, an Order Action error row and an Error Log entry are written, the order is re-imported WITHOUT re-baselining, so the planner sees Shopify's new quantities against the old baseline and applies them (queued sync, or Retry Sync at once); the form says Shopify accepted the change but ERPNext follows.
- **Draft Delivery Note** (`order_edit.refresh_draft_note`, used by Edit Order and by an edit that comes from Shopify): rows matched by `so_detail` get the Sales Order's pending quantity, a row whose Sales Order row is gone is removed, a Sales Order row the note lacks is added through ERPNext's `make_delivery_note(kwargs={"filtered_children": ...})`, rows without `so_detail` are left alone; only for ONE draft note that shipped the whole order (see the draft notes rule above); saved with `ignore_permissions` (the person edited the order, not the note). No draft note: nothing to do, the note a person (single form) or the bulk dialog creates later reads the current Sales Order. Bulk path: it creates notes from the Sales Order under the Sales Order row lock; it reuses an unsent whole-order Bosta draft (`order_shipment.existing_draft`) and skips an order with any other live note, so it never conflicts with an edit; a bulk-made note that Bosta definitively refuses is deleted (see "One-step failure and delete"), one whose outcome is unknown or that was a reused draft stays a draft with editable rows and is refreshed like any other draft; whenever the rows (or rates) of a draft note change, its COD is recomputed at that save and `custom_cod_confirmed` stays 1 (changed 2026-11-09; the amount already sent for a started shipment is not touched). The single form's Create Shipment and the bulk path both require a confirmed COD; the bulk path re-sends only an unsent whole-order draft (it overwrites the COD with the computed amount, confirmed) and never a note whose shipment started (it skips the order: "Delivery Note ... already exists").
- **Reservation.** The Sales Order `on_update_after_submit` hook refuses an edit that would leave a Confirmed order partly reserved, judged on the final rows (`update_child_qty_rate` writes the rows first and reserves last); the real check is `apply_edit`'s, under the locks. An order in Waiting for Stock has nothing reserved to lose, so an edit is allowed and `reserve_or_wait` runs afterwards (it may confirm the order).
- **Cancel from the workflow (Status > Cancel)**: `public/js/delivery_note_bosta.js::before_workflow_action` runs the same Bosta-first cancel as the native Cancel (`before_cancel`) when the Cancel workflow action is pressed on a Bosta note with a live shipment: it asks, cancels the shipment at Bosta, and applies the workflow action only after Bosta accepted. A refusal or an unknown answer stops it with the reason shown. Frappe applies a workflow action after `before_workflow_action` whatever `frappe.validated` says, so the stop is a promise that never settles and the hook releases the frozen screen itself. The server guard (`guard_cancel_or_delete`) still refuses a cancel while the shipment is live. Before this fix a submitted note whose shipment Bosta had not picked up could not be cancelled at all from the workflow.
- **Edits coming from Shopify** (the `orders/updated` planner path): in the draft states `_execute_update` applies the change, then `order_edit.after_marketplace_update` refreshes the draft note and settles the reservation (Shopify raising a quantity (or adding a line) of a Confirmed (reserved) order, or of one already held this way, while the free stock cannot cover the extra is NOT applied: `_reconcile_submitted_order` calls `order_edit.hold_for_stock` before `update_child_qty_rate`; an order that is Waiting for Stock for another reason has nothing reserved, so Shopify's change is just applied; on a shortfall the Sales Order stage becomes Waiting for Stock with the Stock Manager ToDo, the Sales Order list shows a red "Waiting for Stock" indicator (`sales_order_list.js::stage_indicator`), and the Marketplace Order is Syncing with reason `WAITING_FOR_STOCK_EDIT`, no debounce window, NOT Needs Action, baseline untouched so Shopify's increase is not lost. The Bin sweep (`retry_waiting_orders`) bumps the Marketplace Order's debounce for such an order instead of reserving the old quantities, so the planner runs again and either holds again or applies the change and settles the reservation; the hourly stuck sweep re-checks it daily. Known limits: a stock change of an ADDED line's item alone is seen by the daily recheck only (the Bin sweep looks at the Sales Order's own rows), and if Shopify later reverts the increase the order stays Waiting for Stock until a Bin of its rows changes). A draft note with a started shipment is refreshed too (same rules as above). When the stage is locked (parcel with the carrier), the order has two draft notes or a partial draft, or the draft note's Bosta shipment is Creating / Unknown (`order_edit.update_hold_reason`), `sales_order_reconciliation.hold_update_for_shipment` turns the update plan into Needs Attention with reason code `ORDER_LOCKED_BY_SHIPMENT`; ERPNext is not changed (Retry Sync applies it once the cause is gone). Once a note is submitted the order has delivered quantity, so the planner's own `EXECUTION_BLOCKS_UPDATE` already holds the change before this hold is reached.

## Cancelling a Shopify order before pickup (#501, epic #502)

The **Cancel Order** button on a submitted Shopify Sales Order (`public/js/sales_order.js`, `api/marketplace_outbound.py::cancel_order`, `services/order_cancel.py`) runs a chain, each step committed before the next: (1) cancel the draft note's shipment at the carrier (`carrier_shipments.cancel`, for Bosta one terminate), skipped when there is no draft note or its shipment never started / is already cancelled; (2) delete the draft Delivery Note (a comment on the Sales Order keeps its name and tracking number; the native delete is allowed once the shipment is not live); (3) cancel the Sales Order; (4) `request_platform_cancel` (Shopify). A failure STOPS the chain: earlier steps stay, the answer names the failed step and the reason, and pressing Cancel Order again continues from that step (steps re-read the real documents; a finished step counts as done). Before the first step, while the Sales Order is still submitted, the chain is checked as a whole: a submitted Delivery Note (the carrier has the parcel) refuses it and points to the return flow (a Sales Return against the note), a submitted Sales Invoice or a linked Payment Entry refuses it ("Nothing was cancelled"; ERPNext would only stop the Sales Order cancel after the shipment was terminated and the note deleted), the permissions of every step are checked (cancel on the Sales Order, write and delete on each draft note), a draft note that also holds rows of another order or has a document linked to it (the native delete would refuse it) refuses the chain too, and Shopify's own eligibility (`get_platform_cancel_option`) is read so a cancel Shopify would refuse does not terminate a shipment first. A shipment in Creating / Creation Unknown stops the chain at step 1 ("check it with the carrier"). The native Sales Order Cancel now cascades (next section: invoices, then submitted notes, with the carrier shipment cancelled first) and, for a Shopify order, pushes the cancel to Shopify itself; the old "Cancel on Shopify" prompt (#183) is no longer shown for Shopify orders (the button stays as the retry). It still refuses a Sales Order whose DRAFT note has a live shipment. The Cancel Order chain above is unchanged and still refuses a submitted Delivery Note or Sales Invoice up front (it sends its own Shopify cancel in step 4). Automatic refunds are out of scope. The chain works on whichever draft note exists, from the form or from the bulk path.

## Cancelling a Sales Order cancels its documents (decided 2026-11-09)

`services/order_cancel_cascade.py`, three document hooks in `hooks.py`. Delivery Note changes cover both the form and the bulk path because the rules sit on the documents, not on a button.

- **Any Sales Order** (`before_cancel`, after the existing live-draft-shipment refusal): the submitted Sales Invoices that bill it are cancelled first, then its submitted Delivery Notes. A note with a live carrier shipment (Created, Cancellation Pending, Cancellation Unknown) first has the shipment cancelled at the carrier with the same `carrier_shipments.cancel` that Cancel Bosta Shipment and the workflow Cancel use; the note is cancelled only if the carrier confirmed, else the Sales Order cancel stops with the carrier's reason. Creating / Creation Unknown refuses ("check it on the Delivery Note"). Draft notes are not touched (the existing refusal still covers a draft with a live shipment). The Shopify "Cancel Order" chain is unchanged and runs its step 3 with the push hook switched off (it pushes in its own step 4).
- **Blocked, with nothing cancelled**: a submitted Payment Entry that references the Sales Order itself (an advance; the same rule as the Cancel Order chain, `order-lifecycle-open-decisions.md` item J); a Sales Invoice with a Payment Entry, a Journal Entry, or paid / partly paid (payments are never cancelled by this code); any return (credit note or return Delivery Note, draft or submitted; returns are left alone); a POS invoice; an invoice line that belongs to neither this order nor one of its notes, or a note that also holds another order's rows (the payment checks are the shared `carrier_shipments.invoice_blocker`); a user without cancel permission on one of the documents. Everything is checked before the first cancel. Prepaid orders (an advance Payment Entry) therefore cannot be cancelled by this cascade until item J is decided.
- **Partial result**: `carrier_shipments.cancel` commits, so if the carrier refuses (or a later cancel fails) AFTER it ran, the documents cancelled before the carrier call stay cancelled (only those are named; later ones are rolled back); the error names them and cancelling the Sales Order again carries on (a cancelled shipment is answered without calling the carrier).
- **Shopify order cancelled** (`on_cancel`): the cancel is also sent to Shopify in a queued job after the commit (`request_platform_cancel`, reason `OTHER`, nobody is asked). A Shopify order that is already cancelled / fulfilled / on a payment hold is skipped with an orange warning; one already cancelled on Shopify (the cancel came from Shopify) is skipped silently. If the push fails the Sales Order stays cancelled, the failed call wrote an Order Action Error log, and the Marketplace Order goes to Needs Action (reason `ORDER_INACTIVE`, in Needs Attention); the "Cancel on Shopify" button on the cancelled Sales Order retries it. The old after-cancel prompt is not shown for Shopify orders any more. Other channels: no push.
- **Noon** (Delivery Note `on_cancel`, decided 2026-11-09): ONLY a cancel that Noon started cancels the Sales Order. The marker is `flags.cancelled_by_carrier`, set by `carrier_shipments._auto_cancel` (the carrier-initiated automatic cancel, which never runs for this app's own Cancel), and the job also requires the stored Noon order to show no eligible unit (`order_reconciliation` evidence `cancellation == "full"`); a partly cancelled or not yet refreshed order is left to the order sync, which cancels through the cascade. The job runs after the commit in the session that cancelled the note, which in practice is always Administrator (only the system-run automatic cancel sets the marker), so there is no permission scoping. The cascade then cancels the remaining invoices and notes; a live Noon shipment on another note is cancelled at Noon through the generic carrier cancel. A merchant cancelling a note or shipment (the cancel-and-amend path for an AWB or items) never cancels the order. A block (payment, return) never undoes the note cancel: the order stays, with a comment and a Stock Manager notification. Shopify and other channels: cancelling a note leaves the order alive.
- **Picked up** (refused up front, nothing cancelled): a submitted note whose live carrier shipment the adapter reports as picked up (`picked_up(doc)`: Bosta = decided from Bosta's own state (`custom_shipping_status`, `statuses.before_pickup`): only the Shipment Created stage (Pickup requested, Waiting for route, Route Assigned, Picking up from consignee, Picking up) is NOT picked up, so a submitted note still at "Pickup requested" (prod has such notes) is cancelled at Bosta first; Picked up, In transit, Delivered, Returned/Failed states count as picked up, and an empty, unknown or unstaged state (e.g. Archived) is treated as picked up, i.e. refused (conservative); Noon = the shipment shows Shipped or Mixed; Noon's cancellable states are otherwise undocumented) blocks the Sales Order cancel, pointing to a Sales Return.
- **Cancel and amend a Shopify order (decided 2026-11-10, option A)**: the app cannot know at cancel time that an amend follows, so the Sales Order form asks. Native Cancel runs the form hook `before_cancel` (Frappe's `savecancel` first runs "Cancel All Documents", which cancels the submitted linked documents natively, then `_cancel` with its confirmation, then `before_cancel`; the promise is awaited and the cancel goes on only while `frappe.validated` stays true. So the form puts Delivery Note, Sales Invoice and Payment Entry into `frm.ignore_doctypes_on_cancel_all` (a property redefined in `setup`/`refresh`, because ERPNext's `sales_order.js` reassigns the list in `onload`): the server cascade owns those documents, with the payment and return blocks. Checked in the dev container's `form.js` and ERPNext's `sales_order.js`), which, for a submitted Shopify order that Shopify would still cancel (`get_shopify_cancel_choice` = platform option eligible, not already requested / cancelled), shows a dialog: **Cancel and push to Shopify** (the default behavior), **Cancel in ERPNext only** (`skip_shopify_cancel_push` stores a 2 minute cache key for this user and order, which `queue_shopify_cancel` reads and deletes, so it cannot affect anyone else's cancel; both endpoints need cancel permission on the Sales Order only) and **Don't cancel** (also closing the dialog). No dialog when Shopify would refuse anyway (the orange warning after the cancel stays). The cascade is the same in all choices. If the question cannot be asked the cancel goes on as before (push). List-view bulk cancel does not run the form hook and keeps the default (push). The "cancel and amend it" guidance of the shipping-charge reason and message now says to choose Cancel in ERPNext only. The inbound reconciliation cancel (`sales_order_reconciliation.execute`, CANCEL_ORDER) sets `SKIP_PUSH_FLAG`, so an inbound sync never pushes a cancel to Shopify.
- **No loop**: the cascade flags the Sales Order in `frappe.flags` while it cancels its notes, so their `on_cancel` does not queue the Noon cancel again, and the job exits when the order is no longer submitted.

## One-step failure and delete (decided 2026-11-09)

Applies ONLY to the notes the one-step flow makes: the Sales Order form's Create Shipment and the bulk path (both call `services/order_shipment.ship_order`). A Delivery Note that flow MADE is deleted (`carrier_shipments.discard_draft`) when the shipment DEFINITELY fails, and the failure reason is reported; it is KEPT when the outcome is unknown. A note made any other way (native Create > Delivery Note, Duplicate, Data Import, REST insert, Amend) is NEVER deleted by failure handling: the `after_insert` auto-request (`request_shipment_on_insert` -> `run_request_on_insert` -> `delivery_note_workflow.start_shipment`) and the Workflow's Create Shipment pass no discard flag, so those notes stay drafts with the error shown on them (decided 2026-11-09, reversing the earlier "the insert trigger deletes too").

- **Definite**: our pre-checks refuse it (`validate_ready`, `check_deliverable`, missing phone, address or city, COD limit: a deliberate `ValidationError` / `PermissionError` from `request_create`, or the city not found), or Bosta definitively refuses the create (`carrier_log.Failed` in `run_create`, Creation Failed). **Unknown** (timeout, 5xx, Creation Unknown) and unexpected errors keep the note: it may exist at Bosta and a retry looks it up first.
- **Where**: pre-check refusals are deleted in the request that made the note (`order_shipment._discarded`). A `TimestampMismatchError` (the note was changed meanwhile) is not a refusal and keeps the note. A Bosta refusal happens in the queued create job, so the job is told (`request_create(discard_on_failure=True)` puts the flag on the job kwargs; nothing is stored on the note) and `run_create` deletes the note right after writing Creation Failed. No new field, no extra job. Exactly one shipment request is made per one-step note: `ship_order` sets `SKIP_AUTO_REQUEST_FLAG` so the `after_insert` trigger leaves it alone. A REUSED draft (`existing_draft`: the person's own note) and `check`/retry paths never pass the flag, so they are never deleted.
- **Permission**: the delete runs as the system, but only if the user who triggered the flow has the Delivery Note delete permission (`has_permission(..., "delete", user=requested_by)`). Without it the note is kept and the failure reason is reported; a Creation Failed note also gets "The Delivery Note could not be removed because you do not have permission to delete it." appended to its error.
- **Reporting**: the note is gone, so the reason travels elsewhere: the failed result row has no `delivery_note` and names the reason; the waiting form (`api/order_shipment.shipment_state`, polled) and the bulk wait (`order_shipment.shipment_outcome`) read a one-hour cache entry (`carrier_shipments.discarded_notice`, answered only to the user who asked); every Sales Order of the note gets a comment. The Integration Request rows of the note stay as the audit log.
- **Deleting a draft that has a live shipment** (`carrier_shipments.guard_delete`, `on_trash`): linked documents that would block the native delete are checked FIRST (`_check_native_delete_not_blocked`, skipped for a forced delete, which it reads from the calling `delete_doc` frame because Frappe sets no flag; it uses Frappe's own `get_linked_docs`/`get_dynamic_linked_docs`, so `ignore_links_on_delete` applies, and skips Workflow Action rows, which Frappe's wildcard `on_trash` clears itself after this check ran), so the Bosta shipment is never cancelled for a delete that then fails. After a successful carrier cancel the in-memory note carries Integration Status Cancelled, so the Deleted Document snapshot and the later `on_trash` handlers see it. Known: a bulk list delete may ask the carrier twice for notes the carrier refused (each delete retries its own cancel); not fixed.
- **Not touched**: the Sales Invoice of a paid order. None is made at creation, and none is made on Delivered yet (planned in #506: a draft invoice from the Delivery Note when Bosta reports Delivered); one that exists is never deleted.
- The delete runs as the system after the caller's own permission checks and only if the note is still a draft with Integration Status Not Created / Creation Failed (re-read under the Sales Order and note locks); if the delete itself fails the note is kept.

## Shipping charge, COD and the cancel button (decided 2026-11-09)

- **Shipping charge on the note (root cause found on prod, DN-SHP-2026-00065 vs SO-SHP-2026-00984).** A Shopify Sales Order holds the shipping as one "Actual" row in `taxes` (account 4210, description "Shipping"). ERPNext's `make_delivery_note` maps the tax rows with `reset_value`, so the note DOES get the row but with `tax_amount` 0: `total_taxes_and_charges` 0, grand total 309.5 instead of 414.5, while the COD was 414.5. `delivery_note_shipment.carry_order_charges` (called from `guard_changes` for a new Bosta note, and by `order_shipment._set_draft_cod` for a reused draft) restores the amount of each Actual row whose amount is 0 from the Sales Order's row (same account head and description) when the note ships the WHOLE order (`order_edit._whole_order_note`), then recalculates the taxes and totals AND the amount in words (the controller's own `validate` ran before the hook, so `in_words` would keep the old total; `base_in_words` and the rounded total follow `calculate_taxes_and_totals`). A row is never added, a partial note is left alone (it would repeat the whole charge), the account is not touched. Noon strips its taxes on purpose (`integrations/noon/delivery_note_shipment.py`) and is untouched.
- **COD confirmed stays, default ticked.** The field is needed: it separates a deliberate amount (including 0) from an untouched Currency, and it drives the recompute for older or unticked notes. Not removed. `custom_cod_confirmed` defaults to 1. **The computed COD has one helper**, `delivery_note_shipment.computed_cod(doc)`: a whole-order note gets the order's payment position (`order_shipment.payment_plan`, the formula the Sales Order button and the bulk path use; an ambiguous position falls back to `default_cod`), any other note its own grand total minus its share of the advance (`default_cod`). The browser's live prefill (`get_default_cod`) works on an unsaved copy without order rows and calls `default_cod`, so it can differ only for an order with an existing invoice. **New note (`_apply_cod_rule`)**: an amount the person TYPED on the form is kept; the form says so with the hidden Check `custom_cod_typed` (set by `delivery_note_bosta.js` when the person edits the amount of a new note; the server always clears it). Without the marker a note from a Sales Order gets `computed_cod` (an untouched Currency reaches the server as 0, which is not a choice), and so does a note with no order and an empty or 0 amount. `ship_order`'s own note sets the marker (its amount is `payment_plan`'s, the same). **Amended note**: not asked to confirm again; it takes `computed_cod` like a new note and is confirmed. **Saved note**: a ticked box keeps the saved amount; an unticked box (an older note, or unticked by hand) recomputes on every save until it is ticked or the amount is changed. **Reused unsent draft** (single form and bulk): `order_shipment._set_draft_cod` first restores the shipping amount, then overwrites the COD with `payment_plan`'s amount and ticks the box. Because it calls `payment_plan`, an order whose payment position is ambiguous (a partial or outstanding invoice with a recorded payment, a zero total, ...) is now REFUSED for a reused draft too, instead of shipping the draft as it was. **Row changes** (`order_edit.refresh_draft_note`, Edit Order and Shopify edits): sets `RECOMPUTE_FLAG` on the editable draft, so the one validated save recomputes the COD and ticks the box (no untick-save-tick toggle, unconfirmed notes included). Form vs button: the form's first save and the button / bulk path give the same amount, because both end in `payment_plan` for a whole-order note.
- **Cancel Bosta Shipment (button on a draft note).** The button asks (only if `frappe.model.can_delete("Delivery Note")`; otherwise it says so and sends nothing), then calls `frappe.client.delete` on the draft. The native `on_trash` (`carrier_shipments.guard_delete`) cancels the shipment at Bosta first, after `_check_native_delete_not_blocked`, and lets the delete go on only when Bosta confirmed; a refusal, unknown or pending answer blocks the delete with the reason, which the form shows (press the button again to ask again). On success the Sales Order opens (the Delivery Note list when the note has no single order). The old button flow (cancel at Bosta with its Retry / Check dialogs, then a separate delete) is gone for the button; `cancel_at_bosta` stays for the native and workflow Cancel. The workflow Cancel and the submitted-note Cancel are unchanged. The bulk path has no cancel button (its failures already delete the notes they made).

## Nightly lifecycle reconciliation (#501)

`services/order_lifecycle_reconciliation.py`, cron `30 1 * * *` (`hooks.py`, one deduplicated long job), read only, no API call, no automatic fix. For every synced, open, not-refunded, not fully delivered Shopify Sales Order (a Completed or fully delivered order and an order Shopify shows REFUNDED / PARTIALLY_REFUNDED are left out: the bound of the check) it finds: a Delivery Note stage that its statuses do not lead to (a stored stage above the mapped one is not a mismatch where the live write holds it, the same rank rule as `statuses._forward_only`); Sales Order quantities that differ from Shopify's current quantities; a Sales Order total that differs from Shopify's total by more than 0.5 (items, shipping, taxes and discounts are in the row text); a draft note that ships more of an order row than is left to deliver, or a row of an order row that is gone (a partial note, or a note shared with other orders, is legitimate and not flagged; only the order's own rows are judged, so a note that ships LESS than the order is not reported). Orders in Waiting for Stock are skipped for the quantity and total checks. One Marketplace Sync Log row (sync type Lifecycle Check, status Error, keyed `kind|Sales Order|Delivery Note`) per mismatch is shown in Needs Attention as "Order Lifecycle Mismatch"; a mismatch still there keeps its row, a gone one is closed (status Success), so a second run creates nothing. The COD comparison ("Bosta COD Differs"), a picked-up draft ("Picked up but not submitted") and a Lost / Damaged parcel are live Needs Attention rows, not part of the nightly job.

## Invoice on Delivered (#506)

`integrations/bosta/auto_invoice.py::invoice_delivered_notes`, cron `*/10 * * * *` (`hooks.py`), which queues one deduplicated long job (`run_invoice_delivered_notes`). It replaces the prod Server Script "Auto Invoice - Bosta On Delivered" and keeps its behaviour. Every run it reads up to 50 submitted, non-return Delivery Notes whose Carrier is the Bosta Supplier (`delivery_note_shipment.bosta_supplier()`; no Supplier, no run), Shipping Status "Delivered", `per_billed` < 100 and a posting date in the last 60 days (oldest created first, `creation asc`). Per note: skip when a Sales Invoice Item with `docstatus` < 2 already has `delivery_note` = the note, or when every Sales Order of the note is billed 100%; otherwise `make_sales_invoice(note)`, `update_stock` 0, advances allocated automatically (only allocated payments), posting date and due dates set to the Bosta delivery date (`custom_bosta_last_event_at`, else `custom_last_sync_at`, else today, clamped between the note's posting date and today), then the invoice is inserted AND SUBMITTED (decision 2026-11-09; the draft-only wording of the issue text was superseded) and committed. Each note has its own try/except: on a failure the transaction is rolled back, an Error Log "Auto invoice failed: <note>" is written once and a High-priority ToDo (assignee constant `FAILURE_TODO_ASSIGNEE`, no site setting exists) is opened on the note until someone closes it. The ToDo text is a short translated summary starting with the stable marker `[auto-invoice]` (the one-open-ToDo check matches on it); the full error (HTML stripped) is only in the Error Log, and when the assignee user does not exist the ToDo is skipped but the Error Log is still written. It makes no Bosta call. The 50-note query excludes notes that already have a non-cancelled invoice line (NOT EXISTS on `Sales Invoice Item.delivery_note`), so a note the job would only skip never takes a slot; the in-loop checks stay as a safety net. Known limit: a note that FAILS every run (no invoice line is created) stays in the oldest-50 window, and enough of them would starve newer notes. Same as the old script: a split shipment (one order, two notes) gives two invoices, and a Shopify payment mirrored AFTER the invoice exists is not allocated automatically (manual allocation; see `services/shopify_payments.py::_allocation_target`).

## Bulk path (Sales Order list, Bosta)

On the Sales Order list, Actions > Delivery Note opens this app's dialog; it REPLACES ERPNext's own bulk Delivery Note action (decided 2026-11-05, so users see one "Delivery Note" item only; see `docs/ui-customization.md`). The list therefore no longer offers ERPNext's bulk creation (cut-off date option, non-marketplace or manual orders, users without Sales Invoice rights); a single Delivery Note per order is still created from the Sales Order form (Create > Delivery Note), or through this dialog for marketplace orders. The dialog chooses the shipping method (Bosta only; Noon and Manual delivery are not built) and queues `services/bulk_delivery_notes.py::run_bulk` (queue `long`, at most 50 orders, one run per user at a time, runs as the requesting user). The user never types the COD. Per order, one at a time, a failure never stops the others:

1. Under a Sales Order row lock: eligible only if submitted, `custom_marketplace_platform` set, not a platform that fulfils its own orders (`BOSTA_EXCLUDED_PLATFORMS`: Noon and Talabat, same text as the single form), status To Deliver or To Deliver and Bill, Supplier "Bosta" exists, and no live (draft or submitted, non-return) Delivery Note, EXCEPT one unsent whole-order Bosta draft (no shipment started, `order_shipment.existing_draft`), which is REUSED instead of making a second note (the form's Create Shipment does the same). An order with a Product Bundle item is Skipped ("packs must be normal items", the -P<N> items); the form's Submit still judges a bundle by its components (Decision 4). The live-note reason is given before the status one (a submitted note makes the order To Bill, which would hide the note). Any other live note (submitted, shipment started, another carrier, partial, or more than one draft) skips the order with the reason naming it. Otherwise the order is Skipped with the reason.
2. COD basis, for the bulk path AND the single Bosta note (`delivery_note_shipment.default_cod` / `cod_hint`, changed 2026-11-05): the Sales Order/Delivery Note `grand_total` (Shopify's total including shipping), never `rounded_total` as the amount to collect (a difference of up to 0.50). "Fully paid" is judged by ERPNext's own measure, because ERPNext caps a recorded payment at the rounded total (grand 494.21, rounded 494, 494 paid and 0.21 written off is fully paid): nothing outstanding on `(rounded_total or grand_total) - advance_paid` at 2 decimals, or for an existing invoice `outstanding_amount` 0. Not paid at all = `grand_total`; partly paid = `grand_total` minus `advance_paid`. The single Bosta note uses the same rule (`default_cod`: fully paid gives COD 0). While a Delivery Note is being created (new, unsaved) the amount is also prefilled at once in the browser (choosing Bosta, a note made from a Sales Order, changed items, taxes, shipping or discounts) by the read-only `api/bosta_shipments.get_default_cod`, which calls this same `default_cod` on a transient, never-saved copy of the form; the prefill carries no typed marker, so the server computes the amount itself (`computed_cod`, see "Shipping charge, COD and the cancel button"). A saved note is never prefilled by the browser. Fully paid ships with COD 0 and NO Sales Invoice is created in this flow (changed 2026-11-09; `order_shipment.payment_plan` never makes one). An order paid to the grand total but not to the rounded total (only a rounding difference left) is refused with a reason. Partly paid = `grand_total` minus the paid amount, never below 0. A zero-total order is refused. An existing submitted invoice (made by someone else) is only read, never duplicated or deleted, and only if it covers the whole order (same grand total, order billed 100%) and has no credit note; more than one invoice, a partial invoice, a credit note or an outstanding invoice together with a still-recorded order payment refuse the order with a reason.
3. In one transaction (committed once, after the note): the draft Delivery Note from ERPNext's `make_delivery_note` (or the reused unsent draft), transporter Bosta, `custom_cod_amount` and `custom_cod_confirmed = 1` (the adapter's `guard_changes` applies its own COD rule and limit). Then, still before the commit, the neutral pre-flight `carrier_shipments.check_deliverable` (Decision 4): an order short of stock or over the Sales Order's pending quantity is Skipped with the reason, with no new draft and no Bosta call. Any failure rolls the note back.
4. After the commit, with no lock held: `carrier_shipments.request_create(note, submit_as=user)`, the same entry point as the form's Submit (it runs the adapter's `validate_ready`, so every case the single form refuses is refused here with the same text). The bulk path never submits a Delivery Note itself: the note stays a draft after Bosta confirms Created and Bosta's pickup event submits it as the requesting user (Decision 4, #500). If `request_create` refuses (missing city, phone, address ...) or Bosta definitively refuses, the note this run made is DELETED and the row is failed with the reason (changed 2026-11-09, see "One-step failure and delete"); if Bosta does not answer (Creation Unknown), or the note was a reused draft, the draft is KEPT and the row links it. No invoice is made, and one that exists is never deleted.

Progress and summary (realtime event `bulk_delivery_note_progress` to the requesting user, one payload shape with `stage`): `creating` (documents N of M, each order waiting, creating, sent, skipped or failed), `waiting` (the job then watches the sent notes' Integration Status for up to `WAIT_SECONDS` = 120, every 3 seconds, a light read, no polling infrastructure: "Waiting for Bosta K of M accepted"; Created (the note stays a draft until pickup, #500) = accepted by Bosta; Creation Unknown = failed with Bosta's reason, the draft kept; a definite refusal = failed with the reason, the draft already deleted and no link; still Creating = "still creating, check the Delivery Note list later"), and `done` (counts: accepted, failed, skipped, still creating; each problem order with reason and the draft note and invoice that were left; a "Copy failed orders" button). The summary is also kept as a native Notification Log (`enqueue_create_notification`, the failed list in its content, linked to a Delivery Note), so it survives closing Desk. The listener is registered once at startup on every Desk page (`app_include_js`). A crash outside a single order (for example while waiting) is caught: unfinished orders are reported failed and the `done` event and the notification still go out, so the dialog never hangs on "creating". Operational notes: the job runs on the shared `long` queue and the wait holds one long-queue worker for up to 120 seconds per run, alongside Shopify, Noon and Bosta jobs (no new queue); one run per user is a check then enqueue (`deduplicate` on the job id), not atomic, which is harmless because each order is processed under its Sales Order row lock and a live Delivery Note makes the second run skip it; every progress event carries all rows, about 20 KB for 50 orders, and a run publishes about 3 events per order plus the wait updates. Caveat: a progress event published while the person has no Desk open (or is reloading) is not replayed; the dialog reopens at the next event and the Notification Log has the final summary. Tests: `services/test_bulk_delivery_notes.py`, `public/js/sales_order_bulk_delivery.test.js`.
