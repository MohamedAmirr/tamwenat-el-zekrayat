# Delivery Note-first fulfillment (decided 2026-10-29)

Status: decided. Epic #392 is superseded by epic #413 / #415: the Noon adapter behind the neutral carrier contract creates the shipment on Submit (Bosta shape), and the old flow (create, cancel, handover, discard, retry paths, `handover_state.py`, `delivery_note_drafts.py`, `delivery_note.js`, the AWB pool, the shipment child tables) is removed (#415, phase 4). Read `docs/noon-integration/README.md` and `business-spec.md`; the text below is the original direction. See also `docs/noon-integration/fulfillment-release.md`. This document records the agreed direction so the plan, the issues and the code follow it.

## Decision

Fulfillment is driven from the Delivery Note instead of from each platform's own shipment flow.

1. A person creates a draft Delivery Note from the Sales Order (ERPNext's `make_delivery_note`).
2. Creating the draft triggers a per-platform adapter that calls the platform or carrier API to create the shipment (Noon: `CreateShipment`; Bosta: create delivery).
3. The tracking number and AWB come back and are saved on the Delivery Note (or on ERPNext's native Shipment doctype if the native check below prefers it).
4. A person reviews and presses Submit. **Decision 2026-11-02 (reverses the original "The app never submits it")**: Submit starts the create job and the job itself submits the Delivery Note once the carrier confirms Created, as the user who pressed Submit (`frappe.set_user`, no `ignore_permissions`, so the Authorization Control and credit-limit rules judge the requester, and the Version owner that `_submitter` reads is the requester). The browser only waits and reloads. Only `request_shipment` for a delivery passes `submit_as`; Check, the nightly job, a retry that nobody asked for and return pickups never submit. If the job's submit fails, the note stays a Created draft with `custom_last_integration_error` ("Shipment created at X; the Delivery Note could not be submitted: ..."), Needs Attention flags it (Carrier Exception, also any Created draft older than 15 minutes), and a person submits it natively (`before_submit` still requires Created).
5. If the carrier call fails, the draft stays and the error shows in Needs Attention with a retry.
6. Deleting or cancelling the Delivery Note cancels the carrier shipment. Cancelling a Sales Order with a live Delivery Note is blocked by ERPNext's own linked-document check, so no custom cancel-refusal rules are needed.

Why: one flow for every platform (a new platform is one adapter), stock moves correctly for Shopify and Talabat (today only Bosta creates a Delivery Note, see #368), and the dependency between shipment and Delivery Note is enforced by ERPNext instead of by custom tracking code.

## Rules agreed

- One Delivery Note per shipment. For Noon, units of the same SKU are interchangeable, so the adapter picks `mp_item_nr` values by SKU and quantity from the Delivery Note rows.
- The carrier is ERPNext's native `transporter` on the Delivery Note (Supplier "Noon" for Noon), not a custom Carrier field. On the form it is labelled "Carrier", and `lr_no` "AWB / Tracking No" (Property Setters in `fixtures/property_setter.json`); both, with `lr_date`, sit under the customer on the Details tab so the AWB can be typed before the first save. Carrier Status and Carrier Error follow them (read-only, `custom_carrier_error` only when status is Error). It is locked, with the item rows and `lr_no`, once the adapter has started the shipment. Defaulting the transporter per Marketplace Account (Shopify to Bosta) is deferred to the Bosta work.
- Mark Out of Stock stays a standalone dialog calling Noon `UpdateOrder` (valid only before a shipment exists). On HTTP 200 the existing sync and reconciliation planner updates the Sales Order. It is not part of the Delivery Note.
- The Delivery Note is created by a person from the Sales Order, not automatically on Sales Order submit, because automatic shipment creation would remove the chance to mark units out of stock first.
- Noon was built first. Bosta is the second adapter (epic #413, `docs/bosta-integration/README.md`): the shipment is created when the Delivery Note is submitted (a background job started by Submit that the form waits for; the job also submits the note once Created, see Decision 4), through the carrier-neutral Shipping section. A next carrier plugs in with one adapter module, one row in `services/carrier_shipments.CARRIERS`, a Supplier and its carrier-specific fields. Noon will join the same Shipping section in a separate epic.
- Manual delivery: one transporter Supplier "Manual delivery" (`is_transporter` = 1, Arabic "توصيل يدوي") created by patch `create_manual_courier_suppliers`, with no adapter in `CARRIERS`. Staff say who delivered (inDrive, Uber, own driver) in the native Delivery Note Driver Name / Vehicle No fields (transport section, which opens once a Carrier is set); no field was added. The patch first created three Suppliers (inDrive, Uber, Own driver); they were replaced by this one (2026-11-04) and on sites where the old patch ran they are disabled by hand, so old notes stay valid. `adapter_for()` returns `None` for it, so a Delivery Note with this transporter behaves as a plain ERPNext Delivery Note: no API call, no job, Integration Status stays empty, no Needs Attention item, no carrier button or banner on the form. Only the Delivery Note list colors the courier pill ("Manual delivery" green; any other carrier grey). No cost, shipping status or COD for them yet. Caveat: a Delivery Note of a submitted Noon-linked Sales Order is always claimed by the Noon adapter, which forces the transporter to Noon, so Manual delivery does not apply to Noon orders. Tests: `services/test_manual_couriers.py`.
- Rely on ERPNext native features and do not re-invent until really needed. Every custom field, doctype, hook or guard in the plan must name the native option that was checked (native Delivery Note transporter and `lr_no` fields, the native Shipment doctype with `awb_number` and `tracking_url`, native linked-document cancel checks, native delivery status) and why it was rejected.
- No ERPNext or Frappe core files are edited. Everything lives in `marketplace_integrations`: Custom Fields as fixtures, `doc_events` in `hooks.py`, whitelisted methods, client scripts.

## Bulk path (Sales Order list, Bosta)

On the Sales Order list, Actions > Delivery Note opens this app's dialog; ERPNext's own bulk action stays, unchanged and fully working (cut-off date, non-marketplace orders, users without invoice rights), as Actions > "Delivery Note (ERPNext)" (see `docs/ui-customization.md`). The dialog chooses the shipping method (Bosta only; Noon and Manual delivery are not built) and queues `services/bulk_delivery_notes.py::run_bulk` (queue `long`, at most 50 orders, one run per user at a time, runs as the requesting user). The user never types the COD. Per order, one at a time, a failure never stops the others:

1. Under a Sales Order row lock: eligible only if submitted, `custom_marketplace_platform` set, not a platform that fulfils its own orders (`BOSTA_EXCLUDED_PLATFORMS`: Noon and Talabat, same text as the single form), status To Deliver or To Deliver and Bill, no live (draft or submitted, non-return) Delivery Note, Supplier "Bosta" exists. Otherwise the order is Skipped with the reason.
2. COD basis, for the bulk path AND the single Bosta note (`delivery_note_shipment.default_cod` / `cod_hint`, changed 2026-11-05): the Sales Order/Delivery Note `grand_total` (Shopify's total including shipping), never `rounded_total` as the amount to collect (a difference of up to 0.50). "Fully paid" is judged by ERPNext's own measure, because ERPNext caps a recorded payment at the rounded total (grand 494.21, rounded 494, 494 paid and 0.21 written off is fully paid): nothing outstanding on `(rounded_total or grand_total) - advance_paid` at 2 decimals, or for an existing invoice `outstanding_amount` 0. Not paid at all = `grand_total`; partly paid = `grand_total` minus `advance_paid`. The single Bosta note uses the same rule (`default_cod`: fully paid gives COD 0). While a Delivery Note is being created (new, unsaved) the amount is also prefilled at once in the browser (choosing Bosta, a note made from a Sales Order, changed items, taxes, shipping or discounts) by the read-only `api/bosta_shipments.get_default_cod`, which calls this same `default_cod` on a transient, never-saved copy of the form; the prefill is not confirmed. A saved note is never prefilled by the browser: the server fills or recomputes the COD at save until the person confirms it. Fully paid = a submitted Sales Invoice (`update_stock` 0, recorded Payment Entries applied as advances, `only_include_allocated_payments` so an unrelated payment of the same Customer is never pulled, trusted only after submit and reload: outstanding 0) and COD 0; a paid order never ships "COD 0 without an invoice" (an order paid to the grand total but not to the rounded total, only a rounding difference left, is refused with a reason). Partly paid = `grand_total` minus the paid amount, never below 0, no invoice (a rule the user decided). A zero-total order is refused. An existing submitted invoice is reused, never duplicated, but only if it covers the whole order (same grand total, order billed 100%) and has no credit note; more than one invoice, a partial invoice, a credit note, a draft invoice (when a new one would be needed) or an outstanding invoice together with a still-recorded order payment refuse the order with a reason.
3. In one transaction (committed once, after the note): the invoice (paid orders), then the draft Delivery Note from ERPNext's `make_delivery_note`, transporter Bosta, `custom_cod_amount` and `custom_cod_confirmed = 1` (the adapter's `guard_changes` applies its own COD rule and limit). Any failure rolls the invoice and the note back together.
4. After the commit, with no lock held: `carrier_shipments.request_create(note, submit_as=user)`, the same entry point as the form's Submit (it runs the adapter's `validate_ready`, so every case the single form refuses is refused here with the same text). The bulk path never submits a Delivery Note itself: the existing job submits it only once Bosta confirms Created. If `request_create` refuses (missing city, phone, address ...), or Bosta later refuses or does not answer, the draft note and the invoice of a paid order are KEPT (user decision) and the result names them with links and the reason, for the person to finish with the normal Submit.

Progress and summary (realtime event `bulk_delivery_note_progress` to the requesting user, one payload shape with `stage`): `creating` (documents N of M, each order waiting, creating, sent, skipped or failed), `waiting` (the job then watches the sent notes' Integration Status for up to `WAIT_SECONDS` = 120, every 3 seconds, a light read, no polling infrastructure: "Waiting for Bosta K of M accepted"; Created AND submitted (`docstatus` 1) = accepted by Bosta; Created but still a draft keeps waiting, and becomes a failure naming the draft and the stored error when the automatic submit failed (stock, credit limit, authorization) or the wait ends; Creation Failed or Creation Unknown = failed with Bosta's reason; still Creating = "still creating, check the Delivery Note list later"), and `done` (counts: accepted, failed, skipped, still creating; each problem order with reason and the draft note and invoice that were left; a "Copy failed orders" button). The summary is also kept as a native Notification Log (`enqueue_create_notification`, the failed list in its content, linked to a Delivery Note), so it survives closing Desk. The listener is registered once at startup on every Desk page (`app_include_js`). A crash outside a single order (for example while waiting) is caught: unfinished orders are reported failed and the `done` event and the notification still go out, so the dialog never hangs on "creating". Operational notes: the job runs on the shared `long` queue and the wait holds one long-queue worker for up to 120 seconds per run, alongside Shopify, Noon and Bosta jobs (no new queue); one run per user is a check then enqueue (`deduplicate` on the job id), not atomic, which is harmless because each order is processed under its Sales Order row lock and a live Delivery Note makes the second run skip it; every progress event carries all rows, about 20 KB for 50 orders, and a run publishes about 3 events per order plus the wait updates. Caveat: a progress event published while the person has no Desk open (or is reloading) is not replayed; the dialog reopens at the next event and the Notification Log has the final summary. Tests: `services/test_bulk_delivery_notes.py`, `public/js/sales_order_bulk_delivery.test.js`.

## Form layout

The Details tab of a new note and of a saved note is the same. In order: customer block (naming series, customer, customer name, Carrier, AWB / Tracking No, lr_date, Carrier Status, Carrier Error), posting and company columns, accounting dimensions (hidden on this site), currency, items, totals, taxes, discounts section (now empty, auto-hidden), tax breakup, packing list, pricing rules, then ONE collapsed **More** section (Custom Field `Delivery Note-custom_more_section`, `collapsible` = 1). Native sections cannot nest, so More holds the fields of Status, Customer PO Details, Additional Discount, Transporter Info, Print Settings and Additional Info in three columns (status/PO/discount; transport/print; additional info); the emptied native sections hide themselves. Nothing is hidden and nothing is removed. `per_installed` and `per_returned` lose ERPNext's saved-only `depends_on` (Property Setters) so nothing appears only after save. UTM Analytics, Commission, Sales Team and Auto Repeat stay on the More Info tab. Nothing in `public/js/delivery_note.js` or the Noon/Bosta services reads these fields' visibility.
