# Bosta integration (epic #413)

Status: Batch A built (#408 create on Submit, #409 status sync). Batch B partly built: #410 cancel, delete and edit (built, with open questions below), #411 returns (only the draft Sales Return of a returned shipment), #412 costs (only the cost-received stamp). The rest of #411/#412 waits for the answers under "Batch B open questions". The spec is `business-spec.md`; Bosta API facts are `docs.yaml`; the architecture summary is in `docs/marketplace-integrations/architecture.md` ("Bosta shipment of a Delivery Note").

The new design replaces the old Sales Order based flow. Nothing of the old flow is kept behind a compatibility layer.

## How it works

1. A person creates a draft Delivery Note from the Sales Order and sets the Carrier (native `transporter_name`) to the Supplier "Bosta". The Shipping section is always shown and holds the native Carrier (`transporter`), AWB / Tracking No (`lr_no`) and Transport Receipt Date (`lr_date`) first, then the carrier-neutral status and COD fields; the carrier-managed fields (COD amount, COD confirmed) show for any carrier listed in `frappe.boot.marketplace_shipping_carriers`, the Bosta city fields only for Bosta.
2. The person checks the COD, saves, and presses Submit. The Bosta city is filled by the server on Submit from the address linked to the order (`delivery_note_shipment.autofill_city`, `city_match.resolve_city`); a city already set is used as it is and never asked again. Only when it is still empty after that, Submit stops, answers `needs_city` and the form opens the city picker (**Pick Bosta City**, also a button on the draft); the person picks, saves and submits again. Bosta is sent its own city code. The COD is computed by default (the note's total minus the order's advance, proportional per note) and **recomputed on every save while the note is editable (Not Created / Creation Failed) until the person confirms it**: ticking **COD confirmed**, or changing the amount, confirms it (a typed 0 is a deliberate choice). Submit refuses a note whose COD was never confirmed. The merchant can change the COD at any time until the shipment is started (Not Created / Creation Failed), also after confirming; a confirmed amount is never recomputed, but if the items or the advance change so that it differs from the computed amount, the form shows a note with the computed amount (`delivery_note_shipment.cod_hint`). An amended note must confirm again, and so must a note amended from a Bosta note and given another carrier (its Bosta fields are cleared). Marker: Check field `custom_cod_confirmed` (a Currency cannot tell "never set" from 0).
3. The form's `before_submit` calls the neutral `api.carrier_shipments.request_shipment`; `carrier_shipments.request_create` sets Integration Status `Creating`, writes an Integration Request log row and enqueues `carrier_shipments.run_create` (job id `bosta-create|<note>`, kwarg `submit_as` = the session user; a return pickup, Check, the nightly run and any other caller pass none), which calls the Bosta adapter. The form shows "Sending to Bosta..." and polls every 2 seconds (up to 60).
4. Before any of this, `carrier_shipments.request_create` refuses a note whose stock rows ERPNext would refuse to submit (`check_deliverable`: more than the warehouse Bin quantity, more than the Sales Order has left; #476), with the same text on the form and in the bulk run, and no Bosta call. Created (decided 2026-11-02, `delivery-note-first.md`): the job itself submits the Delivery Note (`carrier_shipments._submit_created`: commit, row lock as the next statement, then if still a Created draft `frappe.set_user(submit_as)` and `doc.submit()` without `ignore_permissions`, commit, restore Administrator). The form only polls `docstatus` and reloads, and always sets `frappe.validated = false` so Frappe never saves a second, stale copy. If the job's submit fails (negative stock, credit limit, authorization), the note stays a Created draft with "Shipment created at Bosta; the Delivery Note could not be submitted: <reason>" in `custom_last_integration_error`, the form shows it, Needs Attention flags it (Carrier Exception; also any Created draft older than 15 minutes), and a person submits it natively. Failed or Unknown: Submit stops with the reason (Unknown offers **Check with Bosta** in the same dialog). **Close, keep sending** ends the wait without stopping the job. The server `before_submit` refuses a note that is not Created, whatever the client says. The label job that follows Created writes `custom_shipping_label` with `update_modified=False`, so it cannot make the native Submit fail with "modified after you opened it". Webhook and refresh writes (`statuses._write_state`) to a draft note do the same. A posted copy loaded before such a write cannot overwrite the app's fields: `guard_changes` puts the stored values of `SYSTEM_FIELDS` back on every save instead of refusing. The Sales Order summary is restored the same way (`statuses.keep_stored_summary`).
5. Webhooks and a nightly reconciliation (`59 23 * * *`) keep `custom_shipping_status` and the Sales Order counts (`custom_shipping_status_summary`) current. Bosta jobs only act on notes whose carrier is Bosta (`statuses._open_notes` filters by the Bosta Supplier; `statuses.refresh_note` and webhook matching refuse any other note, so a Noon AWB is never asked at Bosta).

Integration Status (`custom_integration_status`) options: Not Created, Creating, Creation Unknown, Created, Creation Failed, Cancellation Pending, Cancellation Unknown, Cancelled. An empty value means Not Created. The native `docstatus` is the other half of the state. "Unknown" is never "Failed": a timeout, connection error, 5xx/429 or malformed 2xx leaves it Unknown, and only a 4xx (not 408/429) is Creation Failed. Bosta has no idempotency key, so there is no automatic retry and a lookup (`POST /deliveries/search`, `businessReference` = the Delivery Note name) runs before any later attempt. "Later attempt" is decided by `custom_carrier_reference` being set on the note (written when the first attempt starts), never by counting Integration Request rows: Log Settings deletes them after 90 days. The generic retry (`carrier_shipments.retry_shipment`, Noon's Retry button endpoint, write permission only) refuses a Bosta note; only Submit (submit permission, stale-modified check) starts a create. The error text (`custom_last_integration_error`) is stored raw, because Bosta's text is untrusted, and every place that shows it escapes it once (form intro, Needs Attention).

Webhooks: an event that arrives while the note is still Creating (or before any note can claim the delivery, while a create is in flight) stays `Queued` in the Integration Request log and is applied when the shipment is Created (`statuses.replay_pending_events`), or by the nightly run; one that nobody could take for 3 days is closed as ignored. The apply compares the event time with `custom_bosta_last_event_at` inside the row lock, so a late event writes nothing. An event that contradicts the note makes a refresh from Bosta; if the refresh fails the log is `Failed`, not `Success`. The Sales Order summary counts only Bosta Delivery Notes and takes the Sales Order row lock first.

Needs Attention "Carrier Cancelled" (neutral problem type, "Bosta" in the message and platform column) clears when the Delivery Note is cancelled in ERPNext or 14 days after Bosta's cancellation, and never lists a note that has a Success "Cancel" Integration Request row (the cancel the user started here).

## Batch B: cancel, edit, returns, costs

Decided 2026-11-01: terminate 404 / 1066 / "already terminated" is settled by one GET (above); Cancellation Unknown plus a live state returns to Created; edits log operation "Edit". Still to confirm: that the 404 / 1066 answers behave as built against one real cancelled delivery.

**Cancel (#410).** Native cancel stays the only way to cancel a submitted note, native delete the only way to delete a draft; both are refused (`guard_cancel_or_delete`, `before_cancel`/`on_trash`) while the shipment is live, and allowed once Integration Status is Cancelled. `api.carrier_shipments.cancel_shipment` (cancel permission on a submitted note, write on a draft) calls the neutral `carrier_shipments.cancel`, which calls `delivery_note_shipment.cancel_remote` for the Bosta calls: Created / Cancellation Unknown -> Cancellation Pending (committed, no lock across HTTP) -> one `DELETE /deliveries/business/{tracking}/terminate` -> Cancelled (200 `success:true`), or after a 4xx refusal one GET that turns 48/49 into Cancelled, else back to Created with the raw refusal in `custom_last_integration_error`; timeout, 5xx and 429 end Cancellation Unknown. A 404, errorCode 1066 or an "already terminated" text is "unclear": one read-only `GET` of the shipment decides it (found and 48/49 = Cancelled; found and live = back to Created with the raw refusal; not found (404) or a failed read = Cancellation Unknown). A Cancelled note makes no further Bosta call, so a failed local cancel is simply retried. Pending younger than 2 minutes is refused (`STALE_CANCEL_MINUTES`). On the form: **Cancel Bosta Shipment** on a draft; on a submitted note the form's `before_cancel` asks Bosta first and stops the native cancel unless Bosta cancelled (Retry / Check with Bosta in the dialog on Unknown). A webhook or refresh showing 48/49 (or the 1066 "Delivery not found" answer for a Pending / Unknown cancel) also turns Created, Pending or Unknown into Cancelled, and then **cancels a submitted Delivery Note automatically** (decided 2026-11-01): `statuses._write_state` calls the neutral `carrier_shipments.cancel_after_carrier_cancelled`, which, only when the stored Integration Status is Cancelled and the note is submitted (never on Pending / Unknown), and only when the read itself moved the note into Cancelled from Created / Pending / Unknown, or the note is Cancelled with an error left by an earlier blocked attempt (a retry) - never when this app's own Cancel just wrote Cancelled, so a person's native cancel is not raced (`statuses._write_state`, Noon `refresh`) - enqueues the short job `carrier_shipments.run_auto_cancel` (job id `auto-cancel|<note>`, deduplicated, after commit); the job runs as Administrator (no `set_user` in the request), locks the row and runs the native `doc.cancel()` with no Bosta call, once (a cancelled note is left alone, and it never raises). A retry of a Cancelled note with a blocked-cancel error does not need a Bosta read: `statuses.refresh_note` short-circuits before any HTTP call (so the Refresh button works even when Bosta now answers 1066), and the nightly `_open_notes` includes such notes. If a linked submitted document blocks it (`_check_native_cancel_not_blocked`) or the cancel raises, the note stays submitted, the reason is stored in `custom_last_integration_error` (Needs Attention "Carrier Exception" instead of "Carrier Cancelled") and staff cancel it by hand (the Cancel button still makes no Bosta call). Either result sends one native Notification Log linked to the Delivery Note to the user who submitted it (the Version row that changed `docstatus` to 1, else the note's owner) and to every enabled Stock Manager; a repeated blocked read with the same reason does not notify again. A webhook or refresh showing a live (not 48/49) state returns Cancellation Unknown to Created and clears the stale error text (Pending is left alone: its terminate call is still in flight).

**Edit (#410).** `integrations/bosta/editing.py`: **Edit Bosta Shipment** (Created note, Bosta state in `EDITABLE_STATE_CODES`) opens a dialog with receiver phone, Bosta city and address first line. Only fields that differ from the request snapshot (`custom_carrier_request_snapshot`) are sent with `PUT /deliveries/business/{tracking}`; `dropOffAddress` city and first line go as one object. On 2xx the note's `contact_mobile`, Bosta city fields and the snapshot are written (`db_set`). Sync-first: Bosta is called first and the note is written only after Bosta answered 2xx (the dialog never saves the form); a refusal or a network error changes nothing and shows the error. The Integration Request log operation is "Edit". The Address, the Sales Order and Shopify are not changed. Once a shipment is started, `contact_mobile`, `shipping_address_name` and `shipping_address` are read-only in the form and refused by `guard_changes`, so this dialog (which writes with `db_set`, skipping `validate`) is the only way to change them.

**Returns (#411, partial).** State codes 46 and 60 (`statuses.RETURNED_STATE_CODES`, the same pair the Needs Attention "Carrier Return" row uses) on a submitted note queue `returns.create_returned_draft`: one draft Sales Return via ERPNext's `make_sales_return`, `custom_return_source` = "Returned by Bosta", `lr_no` cleared, never submitted (stock moves when staff submit it). Idempotent under the original note's row lock. The draft is also a Needs Attention row "Carrier Return Review" (`role` "Stock User", informational; visibility follows Delivery Note read permission) until it is submitted or cancelled. The damaged-goods warehouse is chosen by the user per item row of the draft; nothing is built for it. `statuses._note_for` ignores return notes that are not a Customer Return Pickup, because a Sales Return copies `lr_no`. `delivery_note_shipment.guard_always` refuses a person setting or clearing the source "Returned by Bosta" (only the app sets it, via `AUTOMATIC_RETURN_FLAG`), and a new pickup return clears the copied `lr_no` / `lr_date`.

**Customer Return Pickup (type 25, #411).** Staff create the native Sales Return (`make_sales_return`) and choose `custom_return_source` = "Customer Return Pickup" on the draft (the field is editable on a draft return; "Returned by Bosta" is set by the app). That makes the return a Bosta note (`delivery_note_shipment.applies_to`: transporter Bosta and that source; a plain return and a "Returned by Bosta" draft belong to no carrier and stay submittable). Staff enter **Returned COD** (`custom_returned_cod`, shown only for such a return, editable only while Not Created / Creation Failed, refused below 0; no other ceiling is checked because the spec's business-policy limit is not defined) and press **Request Bosta Return Pickup** (same wait dialog, Unknown / Check with Bosta / retry as the outbound create). It runs the neutral `carrier_shipments.request_create` -> `run_create` (job id `bosta-create|<return note>`, log operation "Return Pickup", external reference = the return note's name, the same lookup-first duplicate prevention, row lock and Integration Status). `build_payload` sends `type` 25, `cod` = `-custom_returned_cod` (500 -> -500, 0 -> 0), `dropOffAddress` = the customer address from the same `_address_for` builder as a delivery, and `businessLocationId` = the Bosta pickup location of the settings (docs.yaml: "the location id from which your order will be picked up or returned to"). Per the user's decision of 2026-11-01 this is the company pickup address; no `returnAddress` object is sent (its schema needs a `districtId` the app does not hold) and no `returnSpecs`. The user's statement that the customer address goes in the same field as a normal shipment is not spelled out in docs.yaml (the `dropOffAddress` description there is "address of the customer to which the order will be delivered"); it is recorded here as the user's decision. No label job runs for a return and the return is not counted in the Sales Order shipping summary. Submitting the return is the receipt (stock posts to the row warehouses; damaged goods are a per-row warehouse edit): there is no receipt status, no confirm button and no receipt guard. `carrier_shipments.require_shipment_created` lets a return submit whatever its pickup status except Creating / Creation Unknown. Status (decided 2026-11-01): the pickup is tracked like a delivery. Bosta webhooks, Refresh and the nightly run apply to it (`statuses._note_for` matches a return only when its `custom_return_source` is Customer Return Pickup; any other return copies the delivery's tracking number and is ignored). Its terminal states are 45, 49 and also 46 / 60 (the goods reached the merchant: `statuses.terminal_state_names(is_return=True)`, so it is polled no further), and 46 / 60 never queue a draft return for it (`_write_state` skips `queue_returned_draft` for a return note). Needs Attention lists it like any carrier note: Creation Failed / Unknown (Carrier Creation Problem), exception states 47, 100-105 (Carrier Exception), Cancelled; the Carrier Return row ("submit a return against it") is never raised for a pickup, and it is not counted in the Sales Order summary. Cancel works as for any note (Cancel Bosta Shipment on the draft, `before_cancel` on a submitted return).

**Costs (#412, partial).** `_write_state` stamps `custom_actual_cost_received_on` whenever Bosta's `shipmentFees` is read, so a real 0 differs from "not received"; `custom_actual_shipping_cost` shows only once stamped.

No estimate, collected, remitted, difference or COD status fields were built.
- Publish to prod only after #410 is accepted (epic order).

**Verified on a real terminated delivery (2026-11-01).** A `GET` of a terminated delivery answers HTTP 400 `{"message":"Delivery not found.","errorCode":1066}`. Built: `is_terminated_answer` reads it as state 48 (Terminated): `refresh_note` resolves a Created, Cancellation Pending or Cancellation Unknown note to Cancelled on it (decided 2026-11-01: a Created note whose delivery was cancelled in Bosta's own app reads the same; a submitted one is then cancelled automatically; any other status keeps the read a failure), and the one read after an unclear terminate answer counts it as cancelled. A 404 on the read stays "missing" (Cancellation Unknown). Refresh of a note that is already Cancelled gets the same 1066 answer: `refresh_note` closes the log as Success, writes nothing (no `_write_state`, so no second automatic cancel) and returns "Terminated"; the form shows a green "The carrier shows this shipment as cancelled. Nothing else to refresh." alert. Any other failed read shows a plain sentence ("Bosta could not return this shipment's status...") and keeps Bosta's raw text only in the Refresh Integration Request log; a note with no `lr_no` says it has no tracking number to refresh.

**Nightly safety valve (decided 2026-11-01).** A wrong API key or account would answer 1066 for every Created note and cancel them all. In the nightly run (`run_reconcile`), 1066 answers on Created notes are held (the read is logged "held"), not applied. After the loop (`_settle_held_terminations`): up to `MASS_1066_LIMIT` (3) held notes are real cancellations and are applied as Terminated; more than that applies none, writes one message (`_mass_1066_message`, "the Bosta API key or account may be wrong") into the first held note's Last Integration Error (one Needs Attention "Carrier Exception" row) and sends one Notification Log to the Stock Managers. A rerun finding the same message sends nothing again. Single reads (Refresh button, webhook, the cancel flow's own check) are unchanged, and Pending / Unknown notes are not held. A 200 terminate sets the shipping status to Terminated (48); the Sales Order summary no longer counts Cancelled shipments.

**Sequences (final).**
- Create and submit: Submit -> `request_shipment` -> create at Bosta -> store delivery id / AWB, status Created -> the job submits the note as the requester (`before_submit` needs Created) while the form polls and reloads -> `on_submit` (`carrier_shipments.after_submit`, optional adapter hook) queues the label job after the commit. The label job is no longer queued at Created: it raced the form's submit (MySQL 1020, stale `modified`) and left the note Draft. A failed label is only logged; Fetch Bosta Label retries and the note stays submitted.
- Cancel of a submitted note: form `before_cancel` -> server `carrier_shipments.cancel` first checks the links the native cancel would refuse on (`check_if_doc_is_linked`, a submitted Sales Invoice or Sales Return), BEFORE the irreversible terminate -> Cancellation Pending -> terminate -> Cancelled -> the form reloads, then the native cancel (docstatus 2) runs; `guard_changes` ignores a cancel. If the native cancel then fails the note stays submitted with Integration Status Cancelled (no further Bosta call) and Cancel is simply pressed again. Every stop path reloads the form so no "modified after you opened it" follows.

## Native options checked and rejected

- Shipment doctype with `awb_number` / `tracking_url`: rejected, the Delivery Note is the shipment (decision in `docs/marketplace-integrations/delivery-note-first.md`) and one native `lr_no` already holds the tracking number.
- Separate status doctype, GL posting, workflow: rejected. One Integration Status field plus native `docstatus` is enough; no accounting entry is needed.
- Custom Integration Log doctype: rejected, the native Integration Request plus Custom Fields is used (service = the carrier name).

## Provider contract (standing convention for every future carrier)

A carrier is an adapter module `integrations/<carrier>/delivery_note_shipment.py` registered in `services/carrier_shipments.CARRIERS`. Neutral code (`services/carrier_shipments.py`, `services/carrier_log.py`, `api/carrier_shipments.py`, `public/js/delivery_note_shipping.js`, the Needs Attention carrier collector) never names a carrier and holds no carrier logic or carrier field; a grep test (`services/test_carrier_contract.py`) enforces it. The adapter exposes exactly these members:

- `SHIPPING_CARRIER`, `SERVICE_NAME`: the Supplier name the Shipping section shows for, and the service name of the log rows.
- `applies_to(doc)`: does this note belong to the carrier. `guard_changes(doc)`: `validate` rules (locked fields, items once started). `clear_inherited(doc)`: what an amended note must not inherit. `validate_ready(doc)`: everything refusable before the carrier is contacted.
- `find_remote(doc)`: the shipment data, `None` when the carrier confirms there is none, or raises `Unknown`. `create_remote(doc)`: the data, or raises `Failed` (definite refusal) or `Unknown`. `created_values(doc, data)`: the fields to write once created. `after_created(note, data)`: follow-up work after the Created write (it no longer queues the Bosta label: the note is still a draft). Optional `after_submit(doc)`: called by the neutral Delivery Note `on_submit` (`carrier_shipments.after_submit`); Bosta queues its label job there (`enqueue_after_commit`), Noon has none. Every `refresh` path that writes the Integration Status Cancelled must then call `carrier_shipments.cancel_after_carrier_cancelled(note)` (see Cancel above); it is neutral and needs no contract method.
- `cancel_remote(doc)`: Cancelled, `Refused(reason)` or raises `Unknown`. `refresh(note)`: read the carrier and write the status. `reconcile()`: the nightly check. `refuse_sales_order_cancel(order)`. `problem_states()`: `{problem_type: [shipping statuses]}` for Needs Attention.
- Carrier-only rules (address source, COD) stay inside `validate_ready` / `create_remote` / `guard_changes`, never as contract methods. Client side: `register_carrier(name, {before_send(frm) -> bool, refresh(frm), add_buttons(frm)})`.

Rules every adapter keeps: ask the carrier first before any create or cancel; no automatic retry without an idempotency key; timeout, connection error, 5xx/408/429 or a malformed answer is Unknown, never Failed; a definite 4xx is Failed or Refused; nothing is held open across HTTP; the carrier's status is its own words. Do not add a contract method before a real second carrier needs it.

## Intended extension points for Noon (historical: Noon was built in #415, see `docs/noon-integration/README.md`)

Noon joins the same Shipping section in a separate epic. These are the carrier differences that must stay behind the adapter, so Noon needs no renames or shell rewrite. No hook exists for them yet; add each one when Noon needs it.

- Address source: Bosta reads the Delivery Note shipping address; Noon uses the Marketplace Order data.
- Tracking number: Bosta is API-assigned; Noon takes a manual AWB from a pool before the first save.
- Submit wait: Bosta's Submit waits on a queued job (`request_method`); Noon creates the shipment on save and Submit would not wait.
- Fields editable before creation: Bosta locks carrier, tracking number, COD, city and items once started; Noon locks items and quantities only.
- Status fields: done in #415, Noon uses `custom_integration_status` / `custom_last_integration_error`; `custom_carrier_status` / `custom_carrier_error` were removed.

## Unverified Bosta facts (open questions, safest behavior built)

- Is Bosta search eventually consistent? A lookup that finds nothing after an Unknown does not prove absence; a new create is allowed only on a user-started retry that ran the lookup first.
- The issue text lists state 48/49 on a Created note both as Cancelled and as a conflict; it is treated as Cancelled.
- A blank Shipping Status on a just-created note is counted as "Created" in the Sales Order summary.
- The initial state code after create (10, "Pickup requested") is unverified.
- Notes without a Sales Order are allowed (the platform check is skipped).
- Post-submit API edits of the read-only integration fields are not guarded server side.
- A 429 during the nightly run stops the run early and is logged.
- The exception reason is not stored (not in the minimal webhook payload).
- Bosta cancel/terminate semantics: see Batch B open questions.
- Default COD: the Sales Order total minus advance payments, proportional per note.

## Migration (patch `migrate_bosta_shipments_to_delivery_notes`)

- All checks run before anything is changed, so a stopped run leaves the old fields, columns, permissions and notifications in place and can simply be run again.
- Stops with a list of **every** Bosta Shipment that is not Canceled and has no existing Delivery Note or no Bosta delivery id: a deleted note, a row without ids, a failed or pending row. Cancel them, let them finish, or give them a Delivery Note on the old code, then migrate again.
- Stops when one note has two live shipments with different Bosta delivery ids, or already holds another id. Several shipments of one note: the non-Canceled one wins. Rows are processed by name; a second run changes nothing.
